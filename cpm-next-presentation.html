Introduction

cpm-next

A planning and building method for Claude Code. It turns an idea into working, tested code through a short chain of documents kept in the repository.

Use the arrow keys or space to move between slides. On a touch screen, swipe or use the buttons below.

The problem

Coding with an AI assistant and no plan

The work drifts

Without written requirements, each session decides scope again. What gets built depends on how the request was phrased that day.

"Done" is not defined

If nobody stated a finish line, the assistant stops when it thinks it has finished. That may not be when the work is finished.

Claims without proof

"It works" is a claim. A reviewer needs to see which test or check shows that each requirement is met.

cpm-next's answer: write the plan down before building, give every piece of work a stated finish line, and record evidence for every acceptance criterion.
What it is

Six skills and a set of Markdown documents

  • cpm-next is a Claude Code plugin. You run its skills as slash commands, such as /cpm-next:plan.
  • The skills read and write Markdown files under docs/ in your repository: discussions, briefs, specs, epics, reviews, retros and quick-change records.
  • Those files are the only state. There are no progress files to clean up.
  • Each skill states what "done" means and when to stop. How to get there is left to the model.
  • Four optional mods add model and effort control, a progress page, a live pane of remaining work, and automatic reloads after updates.

The six skills

Each skill has a finish line

party

Discussion with named specialist personas (PM, Architect, Developer, UX, QA and others) who disagree with each other.

Finished when the discussion record is concluded and the next step is named.

plan

Writes whatever is missing of brief, spec and epics, from whatever already exists.

Finished when the artefacts down to the epics exist and trace upward.

review

Independent challenge of the epics before they are built.

Finished when Critical and Warning findings are fixed or waiting on you, and a review record is written.

do

Builds stories, verifies each acceptance criterion with evidence, and has each story audited.

Finished when every story in scope is Complete and the test suite is no worse than its baseline.

library

Curates reference documents in docs/library/ that planning and building read.

Finished when the documents carry complete front-matter.

status

Read-only report of where things stand and the next command to run.

Finished when the report is given. Nothing is written.

Library

docs/library/. Every skill reads it.

  • Each level traces to the one above it. A story's **Satisfies** line names the spec requirements it covers.
  • The epic doc is the task list. It is what you read to see where a run is, and what the next session resumes from.
  • A level that would only restate the one above is skipped. A small change can go straight to an epic.
Planning

plan works from what already exists

1. Take stock

Reads docs/, other planning material such as a PRD or README, and in an existing codebase the code itself. It then says what exists, what is missing and what this run will produce.

2. Ask once

Questions that only you can answer, and that change scope, cost or a hard-to-reverse choice, are asked together in one batch, each with a recommended default.

3. Record its own decisions

Everything else it decides itself and writes into the document's Assumptions section, so you can overturn it when you read the plan.

4. Write only what is missing

A brief, a spec with MoSCoW requirements and measurable non-functional requirements, then epics. A change of direction is an amendment to the existing file.

plan is done when every Must Have requirement is covered by at least one story, every acceptance criterion can be checked by a test or a concrete manual step, and no decision you still have to make is hidden inside a story.
Inside an epic

A story states its finish line

## Export loans as CSV
**Story**: 2
**Status**: Complete
**Blocked by**: Story 1
**Satisfies**: FR3
**Effort**: high

**Acceptance Criteria**:
- The export includes every loan in
  the selected range `[feature]`
  - Evidence: {test name and command}
- {next criterion} `[manual]`
  - Evidence: {manual step taken and
    what was observed}

**Audit**: pass ({date})
  • Status is one of Pending, In Progress or Complete. Tools read it.
  • Blocked by names real ordering constraints. Unblocked stories that share no files or runtime state are built in parallel.
  • Satisfies links the story to spec requirements.
  • Acceptance criteria each carry a tag: unit, feature, integration or manual.
  • Evidence sits directly under the criterion it proves.

The story and criterion text come from Starling Library, an imaginary lending-library app; the field names and layout are the real format.

Building

How do builds one story

  • A criterion without its own Evidence line is not met.
  • Evidence is a test name and command, a file:line, or the manual step taken and what was observed.
  • The auditor's Critical and Warning findings are fixed; suggestions are not.
  • A story that fails the second audit is blocked, with each unresolved finding recorded.
  • At the end of the run the full suite must pass, or any failures must have been failing before the run started.
Independent audit

A second model checks every story before it closes

Sonnet builds the story. The auditor agent, on Opus, checks it. It gets none of the builder's conversation, so it checks what is on disk, not what the builder says is there.

What it checks

  • Each criterion against its evidence, re-running the cited tests
  • The diff for defects, including security problems and data loss
  • Scope: changes nobody asked for, and anything missing
  • Departures from the project's conventions
  • Tests that assert nothing, or were weakened or skipped

How it is limited

  • Read-only. It never edits files.
  • It may run the project's tests, but nothing that changes state outside them.
  • It reports what it can show, not what might be true.
  • The result is recorded on the story, for example **Audit**: pass ({date}), 2 findings fixed.

Small changes made without an epic are audited the same way and recorded in docs/quick/.

Effort per story

EffortWhen plan sets it
highA mistake is costly or hard to see: security, authorisation, migrations and data changes, concurrency, scripts and hooks.
mediumThe default when a story has no Effort field.
lowMechanical edits: a config value, a copy change, a rename. A fully determined low story may go to Haiku.

With the cpm-next-models mod, do builds each story at its effort, raises it to high (or xhigh) for a fix after a failed audit, and keeps every story at high or above in a do all run. Without the mod, do builds at the session's effort.

When you are asked

do keeps going unless it has to stop

do stops and asks when

  • A test fails for a reason it cannot explain after investigating.
  • An acceptance criterion contradicts reality, and fixing that would change scope.
  • The next action is destructive or reaches outside the repository: deleting data, rewriting history, touching shared infrastructure.

Otherwise it keeps going

  • No pauses to summarise progress, offer to carry on, or report that a story finished.
  • In an unattended do all run, the first two cases mark the story blocked and work moves on. A destructive action always stops the run.
  • Commits, branches and pushes are left to you.

Elsewhere

plan asks its questions once, in one batch. party asks you only about intent, priorities and preferences. review lists findings that need a decision under "Needs you".

A hard criterion is not a wrong one

"The tests fail" never justifies changing a criterion. It can change only when something specific contradicts it: a file:line, a named requirement, or another criterion.

Seeing progress

Three ways to see where the work stands

/cpm-next:status

Part of cpm-next. A read-only, one-screen report from the artefacts and git: what has been built, what is in flight or blocked, what is waiting on you, and the next command to run.

/next

From the whats-next mod. A live pane listing every story not yet Complete, in build order, and each spec with no epics yet. It reads the files directly, with no model calls.

/progress-tracker

From the cpm-next-progress mod. A private claude.ai page showing a spec's stories as a table grouped by phase. The mod keeps it in step with the epic docs. Anyone it is shared with can read it.

Every do run ends with three headings: Blocked on me (decisions and anything held back), Changed (stories completed, files touched, test result against the baseline) and Found (anything surprising).

In summary

  • The plan is written down in docs/, and those files are the only state.
  • Every story has acceptance criteria, and every criterion gets its own evidence.
  • Opus plans, reviews and audits; Sonnet builds; Haiku looks things up and reports status.
  • do stops for unexplained failures, scope changes and destructive actions, and otherwise keeps going.
