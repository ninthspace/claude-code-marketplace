The Challenge

Planning documents drift

  • A plan written as prose is a plan nothing can check
  • Cross-references rot silently — a story cites an epic that was renumbered months ago
  • Simple questions need a grep across hundreds of files, and the answer is a guess
  • "Which requirements has nothing verified?" should be a query, not an afternoon
The Solution

DPM changes the substrate

  • Every artefact — spec, epic, story, requirement — is a row with typed columns
  • Every cross-artefact reference is a foreign key, not a path in prose
  • Markdown under docs/ is a generated projection — committed so pull requests still read well, never read back
  • Skills write through typed tools, so no skill contains SQL and nothing parses prose
The Difference

What the substrate buys

Planning as prose

  • A story can name an epic that does not exist
  • Renumbering means search-and-replace, and missing one is silent
  • Coverage is a table someone maintains by hand
  • A hand-edit to a generated file survives until something overwrites it

Planning as rows

  • A dangling reference is rejected at write time
  • A renumber updates every reference by construction
  • Coverage is a query, and a gap is a row that isn't there
  • A pre-commit guard regenerates both artefacts and refuses a commit that disagrees

The New Step

Publish, and a guard that cannot be fooled

  • /dpm:publish regenerates the markdown and the committed dump from the database — it names every file it would remove and asks first
  • Nothing generates the projection as a side effect of writing, which is exactly why the next point can exist
  • A pre-commit hook regenerates both artefacts and compares them byte for byte, so a hand-edit to a generated file is caught rather than silently overwritten later
  • It fixes nothing, deliberately — a hook that regenerated and staged the result would destroy the edit it exists to protect
  • The database is never committed: .dpm/dpm.sql is its text form, and a fresh clone rebuilds from it automatically
Flexibility

Scales to the work

  • Small change? Use /dpm:quick — root-caused, recorded and closed against its own criteria, with no pipeline ceremony
  • Autonomous overnight run? Use /dpm:ralph — wraps /dpm:do across epics, or works a spec from scratch, reading readiness from the dependency graph rather than from a list someone kept
  • Clear problem, need requirements? Start at Spec
  • Big new feature? Use the full pipeline
Quality

Built-in quality checks

  • Review — the roster examines an epic through nine professional lenses; findings carry severity and category as typed references, and remediation becomes tasks on the epic
  • Audit — codebase health across the project's dimensions, pinned to the commit it was taken at, with each finding citing file and line
  • Retro — observations are rows that keep their origin, so a lesson promoted into the library still names the epic it came from
  • Pivot — amend an artefact through its update tools, then walk everything hanging off it, gating each downstream change on its own
  • Coverage — a requirement is verified only when the criterion covering it has actually passed. Ctrl+G on the board lists every requirement nothing traces
Manager Benefits

What you get

🔗

Referential integrity

A story cannot point at an epic that does not exist. Traceability is a property of the schema rather than a discipline someone has to keep up.

🔎

Queryable state

"Which requirements have no covering criterion" is a question with an exact answer, not a grep across four hundred files.

📄

Readable diffs

The projection is committed, so a pull request still shows planning changes as prose anyone can review — it is simply never the source.

🔐

Restorable from text

.dpm/dpm.sql is the committed form. The binary database is derived, gitignored automatically, and rebuilt on the first tool call after a clone.

📊

Progress visibility

Run /dpm:status for a narrative briefing over the rows and read-only git history — it writes nothing. The companion DPM board shows every registered project at once and launches the right session for whichever you pick. Unlike a board that reads files, a blocked epic names its blocker from a dependency row rather than having one inferred.

Differentiation

How DPM differs from CPM

🤝 The same facilitation

Twenty-two of the twenty-three skills are the CPM pipeline, one for one. The conversation, the gates and the roster are unchanged — teams still make the decisions.

🗃 Rows, not files

The difference is where the answers land. /dpm:publish is the one skill CPM has no equivalent of, because in CPM the file was the artefact.

🚫 Nothing parses prose

No skill reads a planning document back. That is what makes an answer exact rather than inferred — and it is why there is no importer from CPM.

🔄 One-way projection

Markdown is output. Editing it is writing into something with a generator behind it, and the guard is there to say so before the edit is lost.

Bottom Line

DPM keeps the planning conversation exactly as it was, and moves the result somewhere a machine can check it.
