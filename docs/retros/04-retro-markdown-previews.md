# Markdown previews — the controls that discriminated, and the ones that could not

**Number**: 04  
**Source epic**: 02-04  
**Status**: complete  

## Observations

- Criteria gap · Testing gap — Two criteria in this epic passed against an implementation that did none of what they claimed, and in both cases the only thing that found it out was deleting the code and watching the test stay green. The resize criterion — "the preview re-renders at the new width" — is satisfied by a stale raster, because a Textual `Content` re-wraps itself to whatever panel it is put in: the paragraph reflows either way, so "the text changed" says nothing. What discriminates is a construct laid out *at the raster's width* rather than wrapped to the panel's, and a heading is centred, so a stale one arrives carrying the old width's padding and spills onto a second line. Story 4's control was worse than weak, it was unsatisfiable: "the same input takes the board down" cannot be shown, because no input takes it down.

Run the control before believing the criterion, and run it by removing the implementation rather than by reasoning about it. A criterion whose control cannot be made to fail is either a claim about something the system does not do or a claim with no observable — and the second one is indistinguishable from a passing test until someone deletes the code.

- Codebase discovery · Scope surprise — The epic budgeted a story for surviving bad markdown and found there is no bad markdown. Eighteen pathological sources went through the raster before any guard existed — 20,000 nested blockquotes, 2,000 list levels, an unclosed fence, a 100,000-character line, 5,000 unbalanced brackets, NUL bytes, ANSI escapes, an unpaired surrogate, a 200-column table rendered at ten cells — and every one came back with something paintable, because Rich and markdown-it treat malformed markdown as text. The guard was kept anyway, and the reason is a property of the *path* rather than of the input: the resize render runs on the event loop with nothing catching for it, and eighteen inputs that did not raise is not a proof about the nineteenth. Its fallback is the source itself, so the worst case is a panel showing unrendered markdown.

A robustness story is worth checking against the library before it is scoped: the interesting question was never "which input breaks the renderer" but "which caller has nowhere to put an exception". Where the input probe comes back clean, keep the guard on the strength of the path and say in the test file that the inputs proved nothing — otherwise the next reader deletes it as dead weight, correctly reasoning that twelve named sources all rendered.

- Criteria gap · Testing gap — The timing criterion names the fixture's largest document, and the fixture's largest document is about 130 characters. It renders in well under a millisecond, so "within 50 ms at 80 columns" was a budget nothing could fail — a criterion that reads as a performance bound and is in fact a bound on the fixture. The test times that document and the same source repeated forty times, which is the size of a real epic doc and the one that could actually blow the budget, and the shortfall is recorded rather than fixed: enlarging a fixture every test in the suite reads would change the ground under three other stories to make one criterion mean what it says.

A criterion that quantifies over a shared fixture inherits that fixture's size, and a fixture kept small on purpose is the wrong thing to quantify over. Where a threshold is about the production shape, name the shape — "a document of N lines" — and let the test build it, so the criterion cannot be satisfied by the test data being small.

- Codebase discovery · Pattern worth reusing — Three times this epic the right answer was to ask the runtime the question rather than to model it. Story 1's criteria are read from `rich.markdown.Markdown(source).parsed` — the same markdown-it token stream story 2 rasterises — rather than from a leading `#`, which would have been a second markdown parser living in a test file; that is what caught "subordinate to the task", since a two-space indent with no marker is a lazy paragraph continuation that merges into the parent's inline token, and only the token's `level` knows. Story 2's re-render moved onto the widget's own `Resize`, which carries the panel's new size, because the app's `on_resize` fires before the columns beneath are laid out and rasterises at the width the panel had a moment ago. Story 3's render went to `asyncio.to_thread`, the idiom the tmux poll already uses, with the width read on the loop and only the arithmetic off it.

Where the framework already models the thing under test — a parse, a layout, a size — read its answer instead of writing a parallel one, and prefer the event delivered *to the widget* over the one delivered to the app. The CPM board drives both panels from the app's resize and gets away with it because its panels are wide and its documents wrap at paragraph level; that is luck holding a design up, not the design being right.
