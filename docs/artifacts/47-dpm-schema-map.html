Spec 47 · Data model

dpm / schema map

Thirty-eight tables that hold CPM's planning artefacts as rows instead of prose. Every relationship a markdown file records in a sentence is a foreign key here; every vocabulary it names in a paragraph is a table. The thirteen rules that cannot be constraints are written down too, because an unenforceable invariant nobody listed is one nobody checks.

Identity 5 tables

Everything that produces a file shares one table. A kind declares how it is numbered and what may parent it, and both declarations are enforced against the rows rather than merely recorded beside them.

document + numbering + parentage

Numbering is two-level: a spec is numbered globally, an epic within its spec, restarting at 1 per parent — and a third scheme, none, for kinds that carry no number at all. Which scheme applies is the kind's business, so numbering is carried on the row and pinned by a composite key, letting one CHECK enumerate all three.

dir is nullable, and the null case is load-bearing: a kind with no directory produces no file and renders inside its parent. The ADR is the one member — an architecture decision written inside a spec keeps decision_status, its options and their tradeoff axes, instead of degrading into prose the way it would if a document had to mean a file.

Cannot happenAn epic hanging off a review, or any document parented onto a kind its own kind does not allow — the allow-list is a table and the claim is checked against the parent's own row, so it cannot be satisfied by lying about it. A kind declared root-numbered storing a sequence instead. A retired number returning to circulation.

Two kinds of identity, and only one of them is a number. Every primary key in the schema is a ULID held as text. The human-facing number — 47 in 47-spec-dpm — is a separate column, allocated by number_sequence, and it is the only one anybody ever reads.

The split exists because the committed form of this database is a text dump that two branches are expected to merge. An auto-incrementing integer is a per-database counter, and a per-database counter cannot be unique across databases edited independently: two branches from a common base each adding an epic both allocate id = 2, and the merged dump fails to restore. Executed, that is what happened — which is how the property turned out to be needed on every table rather than on documents alone.

The number still collides, and that rejection is correct: both artefacts are real and one must be renumbered. So the merge tool re-allocates the loser, renames its projection file, and re-renders whatever referenced it — nothing is rewritten, because no reference ever stored a number. A ULID sorts by its timestamp prefix, which also hands every table a stable default order — the tiebreak a byte-stable dump needs, obtained for free.

A reference in prose is a marker, never a number. A reference between artefacts is a foreign key, which renumbering does not touch. But a sentence naming another artefact — an epic's notes citing another epic, a retro observation citing the spec it came from — is not a foreign key and never was. It is written {{ref:<ulid>}} and resolved by the renderer to the target's current human identifier.

The alternative was a reference table, and it was designed and then rejected on the corpus it had to hold: this project's retro 33 cites spec 47 from inside observation.text — a child row, not a section. A section-scoped table cannot reach it. A marker lives in any text column, so the question of which columns may hold a reference stops being a schema decision.

This is why the merge tool re-renders rather than rewrites, and why it writes no text into any row. It is also the only mechanism here that a foreign key cannot police, which is why register entry 13 exists: a marker naming a deleted document is a dangling reference no foreign_key_check will ever see.

The spine 12 tables

Spec to requirement to epic to story to task, joined back by coverage. This is where drift costs the most, and where 1,479 lines of CPM shell parsing become a query.

requirements → coverage

Two criterion sets exist, not one: a spec states its own, an epic states different ones per story. Coverage joins them at the grain of a verbatim fragment, so one requirement with three obligations gets three independently verified rows.

Cannot happenA verified coverage row surviving an edit to the text it verified — three triggers clear verified_at and binding_hash the moment the requirement, the criterion, or the stored fragment changes. The same fragment bound to the same criterion twice, inflating the covered count: identity is (requirement, fragment, criterion), and display order is no part of it. Two milestones in one spec sharing a label, or a position.

Completeness is claimed, not counted. Each coverage row's ✓ decays when the text it was bound to changes. Nothing made the set of rows decay — so a requirement with one of five obligations bound read exactly like one fully covered. Every row current, every row correct, and the roll-up wrong.

That is the failure this whole schema exists to remove, with the sign flipped: the stated problem was a roll-up matching nothing and reporting success, and a roll-up matching something does the same thing less visibly. So coverage_claimed_at is a deliberate assertion on the requirement — somebody says these fragments account for it — paired with a hash of the set claimed, and four triggers clear it the moment a coverage row arrives or leaves, a bound fragment is edited, or the requirement's own text moves.

Four triggers rather than one column, because a claim that outlives its binding set is a green mark attesting to something that no longer exists. The control case is a criterion in its own right: an edit leaving the text byte-identical must not clear the claim. A trigger that fires on every write passes all four decay tests and makes the claim worthless.

The build order is data. A milestone is a row scoped to its spec and ordered by position, and document_milestone is many-to-many on purpose: an epic that spans two milestones says so instead of being filed under one. This spec's own breakdown produced exactly such an epic — the projection and its guard are M2, the merge tool is M4 — and with the build order stated only in a prose table there was nowhere to record it.

Two specs may each hold an M1; one spec may not hold two. The pairing rule that a document and its milestone belong to the same spec is not a constraint — it needs parent_id walked to the root — so it is register entry 12.

Edges 3 tables

Blocking is a relationship, not a status. Kinds are rows, so a new relationship is data rather than a migration, and gates_work separates the edge that stops work from the ones that only record lineage.

Judgement 5 tables

Retro observations, review findings and audit findings all reach the same vocabulary table — and each reference names the domain it may draw from, so the vocabulary and the choice of vocabulary are both enforced. Their categories were the least durable thing in CPM, so they are the most constrained thing here.

taxonomy-driven records

An observation is written against a story and later gathered into a retro, so it may hold both parents at once: the story is where it came from and survives the promotion, the retro is where it ended up. Retirement keeps its date and reason and reverses by setting both back to NULL.

Cannot happenAn artifact register and a document backlink disagreeing about the same association. A search index lagging a write — triggers maintain both, so a result set is never quietly incomplete.

Two indexes, because most of the searchable prose is not in a section. document_section holds narrative bodies, but a requirement's text, a story criterion, a retro observation and a review finding are all rows in child tables. A search covering only sections misses the majority of what anyone would look for — "which requirement mentioned the coverage helpers" returns nothing while the answer sits in requirement.text, and an empty result is indistinguishable from an absent one.

Neither index is external-content. An external-content FTS5 table addresses rows by content_rowid, which must be an integer — and every id here is a ULID. The tables therefore hold their own copy of the text and carry the row's id in an unindexed column. The cost is the text stored twice; the alternative was a per-database integer of exactly the kind that makes two branches collide.

Why the vocabularies are tables

CPM fixes seven retro categories, named in a prose sentence inside a shared procedure. Across 22 real retro files in one project they were written twelve different ways.

The control case sits in the same project, by the same author, in the same period. Review finding categories held almost perfectly — all ten used, roughly seven strays across a hundred headings.

The difference is not discipline, it is form. Review categories appear as literal headings in an output template and get copied. Retro categories appear as prose inside a shared procedure and get restated in the author's own words.

Twelve spellings of seven categories cannot occur when the category is an id.

The rules a constraint cannot hold 13 invariants

Some rules span rows the way a foreign key cannot — reachability across a graph, a row's existence conditional on a column elsewhere, agreement between two ends of a four-table join. Writing them down is the whole point: an invariant with no constraint and no register entry is enforced by nothing and is invisible, because nothing fails and nothing warns.

Every entry is closed twice — refused at the write path so it cannot arrive, and reported by the integrity tool so it can be found if it arrives another way, chiefly by restoring a dump. Each has an acceptance criterion; the register itself is under test, so a check the tool performs that no entry names is a failure as much as the reverse.

#3 is the one that matters. It is the only entry whose violation produces a plausible result rather than an obviously broken one — a matrix joining one spec's requirement to another spec's criterion renders perfectly, rolls up to a percentage, and is wrong.

Three more started here and left. Parentage by kind, numbering scheme, and library promotion all turned out to be row-local given one denormalised column, and became real constraints — which is the intended direction of travel for anything on this list that can make the trip.

#12 and #13 were found by executing the amended schema, not by designing it. Both arrived with the same batch of changes that added milestones and prose markers, and neither was predicted — the probes refused something that should have been allowed, or allowed something that should not. Two entries out of thirteen exist because the schema was run rather than read.

#10 is the entry that makes retirement mean something. It was previously enforced against nothing: retired_at kept existing rows valid, which is half the promise, while nothing stopped a new row citing a retired category. A project could retire a term and find it still on offer and still accepted, with no failure anywhere.

Running the schema is what found most of these, and running it again is what found the rest. A second review of an already-remediated schema turned up eight further criticals, every one of them invisible on the page: sixteen of eighteen references to a document accepted the wrong kind of document, so a story could hang under a spec. Then applying the fixes broke something no fix had named — moving to ULIDs invalidated the search index outright, because an external-content FTS5 table addresses rows by an integer and a ULID is not one. It surfaced on the first row inserted afterwards. A schema review that does not execute the schema is proofreading; one that executes it once and then edits it is proofreading again.

Five things the schema now accepts that it used to refuse, which is the same work in the other direction. A kind declared to carry no number was previously impossible to insert at all — the vocabulary offered the value and the constraint forbade it. An observation gathered into a retro had to surrender the story it came from, so promotion destroyed its own provenance. And three more arrived with the amendment above.

A retro whose source is a spec — the parentage allow-list seeded retro→epic only, which made this project's own retro 33 unstorable. An architecture decision written inside a spec, now that a document kind may produce no file. An epic that spans two milestones, because the join is many-to-many rather than a column.

All three were found the same way, and it is worth saying how: by attempting to load this project's real planning corpus into the schema designed to hold it. Each was something the corpus already contained and the model could not represent. Two different fragments of one requirement, cited against the same criterion, were also rejected once — because identity had been keyed to display order rather than to the fragment.
