# Spec: Cheaper red-first evidence

**Date**: 2026-10-31  
**Source**: docs/discussions/23-discussion-cost-of-red-first-evidence.md, and conversation  
**Amended**: 2026-10-31 — after review 07 (docs/reviews/07-review-red-passes.md): the guard and resume key on each pass directory's `tree` (FR4, FR5, user's decision); a per-path manifest replaces the single hash and `Evidence` lines are written after the pass (FR2, FR3, FR7, AD3); builder directories go (FR4); FR6's audit rule judges scope from the file list given; FR14 names the file of undone lines; FR16 names the lead's part

## Problem Summary

cpm-next 0.9.0 (spec 47) made every test-proven criterion carry a red, and routed criteria by who can prove them. The benefit is real, but the cost falls on every story of every run, and some of it buys nothing:

1. **Time per story.** Each red takes about ten tool calls (`cpm-next/skills/do/SKILL.md:49-52`): a directory, a `**Scratch**` line, a copy, the undo, the run, the copy back, a green re-run, deleting the directory and the line, and the `Evidence` edit. It applies to every test-proven criterion, including one proved by a test that existed and passed before the story.
2. **Working-tree risk.** Red copies live in the session scratchpad (`:81`), which an interrupted run's next session may not find (`:38`); a mutated source file left by a stopped red is committed by any `git add -A`, including the user's `/commitp`, and a worktree subagent's red leaves no trace in the epic doc at all (`:50`, `worktree.md:19`).
3. **Audits block reds.** No red is taken while any auditor runs (`:85`), even an auditor that runs nothing.
4. **A weaker auditor in an unisolated suite.** It runs no tests (`cpm-next/agents/auditor.md:12`, `do/SKILL.md:96`), even when nothing else is using the suite.
5. **Stories waiting on the user look like work.** `do` skips them, but `whats-next` offers them as next (`whats-next/hooks/plan.ts:196-250`) and `cpm-next-progress` shows them Pending or in progress (`cpm-next-progress/hooks/progress.ts:298-303`). A criterion `do` falls back to treating as `[user]` keeps its tag (`do/SKILL.md:47`), so no parser can tell.
6. **Browser checks fall back late.** `do` finds the missing browser or server at the start (`:37`) but says nothing until the end of the run.
7. **Long `Evidence` lines** (`cpm-next/shared/artifacts.md:137`).

The files changed are `cpm-next/skills/do/SKILL.md`, `cpm-next/skills/do/worktree.md`, `cpm-next/agents/auditor.md`, `cpm-next/shared/artifacts.md`, `cpm-next/skills/status/SKILL.md`, a new hooks module in `cpm-next/hooks/` with its packaging, the `whats-next` mod (`hooks/plan.ts`, `hooks/register.tsx`, `types/index.d.ts`) and the `cpm-next-progress` mod (`hooks/progress.ts`, `hooks/register.ts`). Where a file already states a rule this spec changes, the rule is amended in place, never restated beside it.

## Functional Requirements

### Must Have

- **FR1**: A red is required for every criterion proved by a test the story added or changed, and for every criterion that names a control. A criterion that keeps behaviour the code already had (a refactor, a "still works"), names no control, and is proved by a test unchanged in the story's diff that passed in the run's baseline, records `red: n/a — existing (reaches {file:line})`, naming a line the story changed that the test executes. — AC: the contract defines `existing`, the criteria it fits and its form, and no longer says a test-proven criterion never takes `n/a`; `do` step 4 states which criteria take a red; auditor check 5 reports as a Warning an `existing` reason on a test changed in the diff, on a criterion for new behaviour or one naming a control, or naming a line the test does not reach; control: `do`, the contract and the auditor each state the case "a criterion for new behaviour cited with `existing`" as a finding, found by `grep` for the rule's sentence in each file `[manual]`
- **FR2**: The reds of a story are taken in red passes. The inputs probe and the read-through of docs and help text come before the story's full-suite run; a pass starts after that run and its fixes, when no edit to the story's files remains to be made. It creates a fresh directory and writes its path in the `**Scratch**` line; writes to a `manifest` file in it each changed or untracked, not ignored, path with its blob hash (excluding the epic doc or quick record, against the empty tree when the repository has no commit), and to a `tree` file the output of `git rev-parse --show-toplevel`; copies each file there once, at its repository path, before its first mutation in the pass; and takes each red as undo with the Edit tool, run the cited test, read and note the failure, copy back. After the last copy-back it recomputes the manifest and compares, then deletes the directory by its literal, quoted absolute path and removes the line, and only then writes the reds into their `Evidence` lines. Nothing in a pass's directory is used after the pass ends. — AC: `do` step 4 states the pass in that order; `grep` finds the pass instruction in `do/SKILL.md` and no per-red directory or per-red `**Scratch**` instruction left in `do/SKILL.md` or `worktree.md` `[manual]`
- **FR3**: A matching manifest means the tree is the one the suite ran against, so the full-suite result from before the pass stands for the audit and no test is re-run green. On a mismatch, a listed path whose hash differs is copied back and the manifest compared again; a path not listed that is now untracked is test output, named under **Found** and left alone; any other difference, or one that remains, marks the story blocked with the paths, lists it under **Needs you**, and the directory is deleted. A later fix that changes a file a red mutated, or a red's test file, retakes that red in a new pass. — AC: `do` steps 4 and 5 state it; the contract's `Evidence` form has no `green after restore`, and the auditor no longer requires it `[manual]`
- **FR4**: A pass's directory is `{absolute git common dir}/cpm-next/scratch/{epic file stem}-{story}/` (or `quick-{nn}/`), the common directory found with `git rev-parse --path-format=absolute --git-common-dir`, each file kept at its repository path inside it, beside its `manifest` and `tree` files. Builder directories go; auditor directories stay in the run directory under the session scratchpad. At the start of a run, before any other work, `do` restores the files of every such directory whose `tree` names the checkout it runs in, whatever its story or quick record, deletes the directory and removes its line; deletes, naming it under **Found**, a directory whose `tree` no longer exists; and leaves a directory whose `tree` is another existing checkout to that checkout. A `**Scratch**` line whose directory is gone and lay under the common directory is removed; one naming a path outside it (a 0.10.0 session-scratchpad directory) stops the story and lists it under **Needs you**. A worktree subagent's pass uses the same path in the main repository's common directory, with its worktree in `tree`. — AC: `do` (**Scratch directories and isolation**, step 4, **Before the first story**), `worktree.md` and the contract's `**Scratch**` field state it `[manual]`
- **FR5**: cpm-next ships a hooks module that refuses a `git commit` run through the Bash tool, by the main session or a subagent, while the repository's `{common dir}/cpm-next/scratch/` holds a directory whose `tree` file names the checkout the commit runs in. The refusal names each such directory (and so each story) and tells the user to resume `/cpm-next:do` on it or copy its files back. The checkout is the session's working directory, its common directory found by following a `.git` file to its `commondir` in a worktree. A Bash command that is not a `git commit` returns before reading anything. — AC: tests in `cpm-next/hooks/` cover: a commit refused while a scratch directory names this checkout, naming it; a commit passed when the scratch folder is absent, when it exists but is empty, and when its only directory names another checkout (a worktree's pass does not block the main checkout, nor the reverse), each in a fixture that otherwise holds a repository; `git commit` reached through `cd x &&` and through `git -C . commit`, each refused; a non-commit command passed in a fixture that holds a scratch directory, with no file read; a worktree whose `.git` file points to the main repository's directory, refused while a directory names that worktree. Control: removing the check makes the refused-commit tests fail `[unit]`
- **FR6**: A red may be taken while an audit runs only when it mutates no file the audited story changed and that auditor was told to run no tests and no probes, judging scope from the file list it is given; two full-suite runs, or a full-suite run and a red, never overlap in one checkout. — AC: `do` **Scratch directories and isolation** states it, replacing the rule that no red is taken while any auditor runs `[manual]`
- **FR7**: The auditor checks that each recorded failure text is what the cited assertion would print for the recorded change; a mismatch is a Warning. The audit prompt says the red pass ended with a matching manifest and that the full-suite result predates it; a story with test-proven criteria and no such statement is a Warning. — AC: auditor check 5 and `do` **Audit** state it `[manual]`
- **FR8**: In an unisolated suite the lead may tell an auditor the suite is free only when the lead waits for that audit in the foreground and makes no test-running call, starts no red and no other test-running audit until it reports; only an auditor told so runs tests or probes. Otherwise the auditor is told the suite is not free and runs nothing. — AC: `do` **Audit** and the auditor's opening rules state it `[manual]`
- **FR9**: When `do` treats a criterion as `[user]` that isn't tagged `[user]`, it writes an indented `- Waiting on user: {steps}` line under the criterion, and removes it when it writes that criterion's `Evidence` line. The contract defines the line, and states once the grammar both mods use to read criteria: a criterion is a `- ` line under `**Acceptance Criteria**:` (continued on indented lines that are not sub-bullets), its tag the last backticked word in it, and its indented `- Evidence`, `- Evidence (user, …)`, `- Not met:` and `- Waiting on user:` lines; a legacy story-level `**Evidence**:` field counts as evidence for every criterion. `status` reads the line. — AC: the contract, `do` step 3 and `status` state it `[manual]`
- **FR10**: `cpm-next-progress` shows a story waiting on the user as `Waiting on input`, whether its status is `Pending` or `In Progress`: every story and epic its own and its epic's `**Blocked by**` name is `Complete` (archived epics included), its `**Status**` carries no ` — blocked:` note, no criterion has a `- Not met:` line, at least one criterion has no `Evidence` line, and every such criterion is tagged `[user]` or has a `- Waiting on user:` line. The overview counts it as waiting. Story timing is unchanged. — AC: tests on a shared fixture set (two-story epics) cover a waiting `Pending` story and a waiting `In Progress` story; controls, each leaving the story not waiting: a story blocker not `Complete`, the epic's own `**Blocked by**` not `Complete`, a blocker epic `Complete` in `docs/archive/epics` (waiting, not outstanding), a ` — blocked:` note, a `Not met` line, an untagged criterion without `Evidence`, and every criterion evidenced `[unit]`
- **FR11**: `whats-next` never offers a story waiting on the user as next or counts it among the stories left, lists such stories in a "Waiting on you" group with each unproven criterion's text, and labels a story that depends on one as waiting on that check, not as a cycle or unknown dependency. `hasWork`, the `/next` text, the band and the pane show the group when it is the only thing left. — AC: tests on the same fixture set cover the group, its absence from `order`, a dependent labelled as waiting on the check and not ready, `hasWork` true with only waiting stories, and the FR10 controls `[unit]`
- **FR12**: When the scope holds a `[browser]` criterion the run cannot check (no browser test tool, and no app answering at a local `APP_URL`, no connected browser, or no login session where one is needed), `do` says what is missing and how to fix it in its first message, then carries on; with the user present, it asks once before building whether to fix it first. — AC: `do` **Before the first story** states it `[manual]`
- **FR13**: In the **Needs you** walk-through, browser checks that fell back to the user are one question: fix the environment and have `do` run them all, or report the results. Once fixed, `do` checks them through claude-in-chrome and records them `browser-observed`, removing their `- Waiting on user:` lines. — AC: `do` **Finishing** states it `[manual]`
- **FR16**: In a one-checkout parallel batch, once the batch has finished and nothing else is running, the lead hands each story's red pass to a fresh `sonnet` subagent, one at a time, giving it the story, the cited tests, the contract's path and the absolute path of `do/SKILL.md` for the pass rules. The lead writes the `**Scratch**` line and the manifest before the hand-off, compares the manifest itself afterwards, and writes the `Evidence` lines from the subagent's reported failures after checking each against the test file. The red tool calls stay out of the lead's context; no pass overlaps another, a test run or an audit that runs tests. — AC: `do` step 4 and the parallel-work rules state it `[manual]`
- **FR14**: The contract's test-proven `Evidence` form is `{test name, file:line}{ ({command})} — red: {message} with {lines undone in {file:lines} | mutation of {file:line}: {change}}`, `{message}` being the first line of the failure message, or for a multi-line diff the first line naming the expected and actual values, and the command omitted when it is the project's test command run on the named test. — AC: the contract shows the form; auditor check 5 reads it `[manual]`

### Should Have

- **FR15**: `docs/maintenance/README.md` amends its "Scratch location" and "Waiting stories in the mods" records, which become false, and records the scratch path, the `- Waiting on user:` line, the criterion grammar, `red: n/a — existing`, and that cpm-next ships a hooks module. — AC: the record names each, and neither amended record still describes the old behaviour `[manual]`

### Won't Have (this iteration)

- Subagents taking reds while batch siblings still run, in a shared checkout: a sibling's tests run code a red has mutated, even in an isolated suite. FR16 delegates reds to subagents only after the batch, one at a time (user's decision, 2026-10-31).
- Offering the user a change that would isolate their suite.
- A nudge in `status` or the overview when only a spec's user-checks epic is open.
- Back-filling reds or `existing` reasons into epics built before this release.
- Blocking commits made outside Claude (a terminal, an IDE, a git hook).
- Two `do` sessions working on the same story in one checkout.

## Architecture Decisions

### AD1: The commit guard lives in cpm-next and reads the scratch folder, not the docs
cpm-next gains `hooks/hooks.json`, a hooks module, a test file, a `tsconfig.json` and a `.gitignore` entry for its laid types, so the guard is installed wherever `do` can leave a red behind. It checks one folder, `{common dir}/cpm-next/scratch/`, which the main session and worktree subagents both write to, so it needs no docs search and sees reds the epic doc never records. It refuses only commits in a checkout a pass directory's `tree` names, so up to three worktree subagents, and the lead committing before each fan-out, are blocked only by their own open passes. Rejected: `cpm-next-progress` or `cpm-next-models` as its home (user's decision, 2026-10-31); scanning epic docs for `**Scratch**` lines (misses worktree reds, and would be a third copy of the `docs/` and `docs/cpm/` search).

### AD2: `existing` only for behaviour the code already had, and only where the test reaches the change
A test that passed before the story cannot show new behaviour works, and a criterion naming a control needs that control seen failing, so `existing` fits only a behaviour-keeping criterion with no control, cited by an unchanged test that passed at baseline and that executes a line the story changed. Naming that line lets the auditor check the test reaches the change, which is what today's mutation fallback would otherwise prove. Rejected: any unchanged test skipping the red. User's decision on the scope, 2026-10-31; the reaches rule planned here.

### AD3: A red pass is short-lived, proved by a manifest, and kept under the git common directory
Copies are only safe while nothing else edits the files, so a pass begins after every pending fix and ends, directory deleted, before the next edit; a later red starts a new pass. A per-path manifest of the working tree's changes, taken before and compared after, proves every file came back, names any that didn't, tells test output (new untracked files) from a real difference, and lets the earlier full-suite result stand. It leaves out the epic doc or quick record, which the pass itself edits, and is kept in the pass directory so it survives compaction; the `tree` file beside it says which checkout the copies belong to. `{common dir}/cpm-next/scratch/` survives sessions, needs no `.gitignore` entry, cannot be staged, and is shared by every worktree. Directories are removed by literal absolute path, since Claude Code refuses an `rm` whose target is a command substitution. Rejected: one copy kept for the whole story (a fix between reds is undone by the stale copy); a gitignored folder in the tree.

### AD4: One criterion grammar in the contract, one fixture set in both mods
The waiting rule is computed from the epic doc alone, so neither mod needs state of its own. The contract states the criterion grammar once; both mods' tests run the same fixture epics, kept identical, so the two parsers cannot drift apart without a test noticing. `cpm-next-progress` reuses its `Waiting on input` status, which now wins over `In progress`, and reads `docs/archive/epics` for blockers as `whats-next` already does.

## Scope

### In Scope
The files named in the Problem Summary; `docs/maintenance/README.md`; the cpm-next README (log entry and upgrade note); the root `README.md`, which holds the `whats-next` and `cpm-next-progress` documentation (the Statuses list and the `waitingOn` description); `cpm-next/.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json` (descriptions that say cpm-next is skills only, and versions: cpm-next 0.11.0, whats-next 0.3.0, cpm-next-progress 0.8.0, marketplace 4.0.6); the root `.gitignore`.

### Out of Scope
`plan`, `review` and `library`; any project's docs; the items under Won't Have.

## Testing Strategy

Skill, agent and contract changes are prose, checked by reading the changed file against the requirement, with `grep` for required and removed strings (`[manual]`). The hook and the two mods are TypeScript, tested with `claude plugin test {plugin}` (`[unit]`), each new test shown failing once with the code under test broken. The two mods' waiting tests read one fixture set, copied byte for byte into each mod's `hooks/fixtures/`, compared with `cmp` at release. NFR1 by `wc -w`; NFR3 by the commands it names. Behaviour in a live run is seen only through an installed release, in the final user-checks epic, using a scratch repository.

## Assumptions

- The main saving is FR1: a criterion keeping existing behaviour no longer needs a red. FR2 saves little for a story with one red (a pass costs about five calls besides its reds: directory and line, manifest, copies, manifest compare, deletion) and more for a story with several; dropping the green re-run saves one call per red.
- The `existing` check is made against the diff the auditor is given (the uncommitted changes, or a worktree story's merge commit). A story whose work was committed part-way, between sessions, loses that check for the committed part.
- Writing and removing files under `.git/cpm-next/` ran without a prompt in this repository (probe, 2026-10-31); a project whose permission settings or sandbox refuse it would stall a red pass, which the user-checks epic covers by running a pass in a scratch repository.
- `git rev-parse --path-format=absolute` needs git 2.31 or later.
- The hook resolves the repository from the session's working directory; a `git commit` aimed at a different repository by `cd` elsewhere is checked against the session's repository, so it may be refused while a red pass runs here, never passed when one runs there.
- `status` keeps its rule for stories waiting on the user and adds the `- Waiting on user:` line as a way a criterion counts; it gains no other change.
- The marketplace version moves to 4.0.6, and the three plugin versions as listed under Scope.
- The challenge pass (Casey, Margot, Bella) found: subagent reds in a shared checkout faking a sibling's red (moved to Won't Have, reversing the discussion's decision; raised under **Needs you**); a copy kept across reds undoing fixes (AD3); stale reds after a fix (FR3's file-level retake); `existing` on a test that never reaches the change (AD2); worktree reds invisible to a docs-based guard (AD1); the auditor running code while a red mutates it (FR6, FR8); the waiting rule in five places (AD4); missing archive reads, UI paths and packaging files (FR10, FR11, Scope); and a saving overstated (above). Not taken: recording the commit SHA in `existing` (the diff check, with the assumption above, is enough for the common case); an owner file per scratch directory (two sessions on one story is out of scope).
