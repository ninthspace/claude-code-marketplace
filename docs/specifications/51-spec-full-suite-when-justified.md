# Spec: The full suite when a story justifies it

**Date**: 2026-11-09  
**Source**: conversation (2026-11-09): "I have projects where a full suite takes 15-20 minutes"; "We could determine per story whether a full suite is justified. No need for a per project setting"  
**Amended**: the three Pivot deferred notes of 51-01 Story 1 and 51-02 Story 1 settled to match the built text — FR5's closing story and `none` rule, FR2's `deleted` and `renamed` reasons, FR4's `HEAD` line, and FR6, FR11 and AD2 on a story that closes no epic (2026-11-09)  
**Amended**: review 08 (docs/reviews/08-review-targeted-runs.md) and the user's decisions — exempt files by kind with a blob-hash snapshot (FR4), tests through one caller and iterating tests in the targeted set, code file and behaviour defined (FR1), a run counter and `none` in the line (FR2), flaky and order-dependent split with full runs after an order-dependent failure (FR3), waiting stories and no-change stories (FR5), the baseline fix's place (FR6), the auditor's extra Warnings and a run that settles one (FR7), the rules in `shared/test-runs.md` (NFR3, AD3) (2026-11-09)

## Problem Summary

`/cpm-next:do` runs a project's full suite once for the baseline, then about three times per story: in step 4 (`cpm-next/skills/do/SKILL.md`, "Run the full suite and fix what it shows, running it again after any fix that changes a file, until a run needs no fix"), and again after each audit round's fixes (step 5, "so the next audit has a full-suite result for the code as it stands"). The auditor is handed that result (`cpm-next/agents/auditor.md`, the opening paragraphs and checks 1 and 8). In a project whose suite takes 15 to 20 minutes, an epic of five stories spends hours waiting on runs that mostly re-prove what the story's own tests show.

The rerun rule counts any changed file, so an edit to an `Evidence` line or the epic doc itself forces another full run though no test reads it.

What a full run adds beyond the tests that run a story's code is catching a regression elsewhere in the suite. That matters when the story changed something many files or tests rely on, and rarely otherwise.

## Functional Requirements

### Must Have

- **FR1**: Before a story's step 4 run, `do` decides between a full run and a targeted run by `cpm-next/shared/test-runs.md`. The targeted set is the tests the story's `Evidence` lines cite, the test files the story added or changed, and, for each changed code file (any file that is not exempt, FR4), the tests that run it: tests that call it, or reach it through one caller, directly or by the name the framework resolves it by (a route's URL or name, a view name, a component tag, a command signature, an event it handles), and tests that iterate its directory, namespace or registry (architecture tests, snapshot and route-list sweeps); not counting a test that fakes or mocks it, and selected by file path, never a name filter. A full run is justified when the story changes a file of wide reach, when a changed code file has no test that runs it, or when it is deleted or renamed. Wide reach is: a migration or schema; a dependency manifest or lock file; config, environment and test-runner config; shared test setup, fixtures, factories and seeders; boot-time registration and route files, console routes included; anything the framework wires by convention or by a string (listeners, observers, policies and gates, middleware, layouts and view components, translations, scheduled and console commands, model events and global scopes); and a change to what callers can observe (signature, return value, side effects, thrown exceptions) of an existing symbol that more than one non-test file uses, found by a grep for its qualified use (`Class::method`, `->method(` on that type). Adding a symbol nothing uses yet is not wide reach. There is no per-project setting. — AC: `test-runs.md` states the targeted set, the triggers and the wide-reach list; `do` step 4 applies them by reference; control: they say a story whose changed code files are all of narrow reach and each run by a test takes a targeted run, and that a test file the story adds is in the targeted set, not wide reach `[manual]`
- **FR2**: `do` records each run in a `**Test run**` line in the story's header block, before `**Acceptance Criteria**` (a `docs/quick/` record carries it too), one line with no sub-bullets, rewritten on every run: `**Test run**: {n} ({f} full, {t} targeted) — {full | targeted | none} — {command}: {passed} passed, {failed} failed — tree {hash} — {reason, or for targeted the changed file → tests; …}`. `{n}` counts the story's runs and `{f}` and `{t}` its full and targeted runs; `{failed}` counts failures and errors; a run of zero tests is not a pass; a run over more than one test runner gives a command and counts per runner; `{hash}` is FR4's snapshot; `none` is written when no non-exempt file changed (FR5), with no command. Red-pass runs and auditor probes do not rewrite it. The contract defines the field and its place; `test-runs.md` gives the reasons a full run records (`closes epic`, `small change`, `wide reach: {file} ({entry})`, `untested: {file}`, `deleted: {file}`, `renamed: {file}`, `targeted failure: {test}`, `order-dependent: {test}`, `sibling Story {n}`, `merge conflict`, `audit: run too narrow`). — AC: the contract shows the field, its forms and its place; `test-runs.md` gives the reasons; `do` says to write it on every run `[manual]`
- **FR3**: A targeted run that fails or errors in a test the story did not add or change, and that passed at the baseline, is followed by a full run before any fix, in step 4 or step 5. When the full run fails there too, the failure is fixed and every rerun includes each test that failed in the previous run. When it passes, the targeted set is run once more: a pass names the test under **Found** as flaky; a second failure names it under **Found** as order-dependent, and the story's runs stay full until it closes (`order-dependent: {test}`). — AC: `test-runs.md` or `do` step 4 states each branch, and step 5 applies it; control: a failure in a test the story added or changed triggers no full run `[manual]`
- **FR4**: Exempt files are, by kind, the epic doc, the `docs/quick/` record, and prose (Markdown and plain text) that no code, test, test config or build config reads; every code, config, fixture, test, view, template, translation or asset file is a code file and makes a run stale. After each run `do` takes a snapshot, whose first line is `git rev-parse HEAD`, of every changed and untracked non-exempt path with its blob hash (`git hash-object`, as the red-pass manifest does) and records its hash in the `**Test run**` line; a result stands while a fresh snapshot hashes the same. A rerun after a fix runs the story's targeted set, the fix's tests, the tests that run any newly changed code file, and every test that failed in the previous run, and is full when the fix has wide reach or the story is one FR5 names. Only a full run stands for the baseline. — AC: `test-runs.md` lists the exempt kinds and the snapshot; `do` **Scope and finish line** and steps 4 and 5 apply them; control: `do` says a run is repeated after a second edit to a file that was already changed at the previous run `[manual]`
- **FR5**: The full suite is run for a story that closes an epic (at its step 4 run, every other story in its epic is Complete or has only `[user]` criteria, or criteria treated as `[user]`, left) and for a small change (`docs/quick/`). For such a story every rerun in steps 4 and 5 is full, and it closes only on a passing full run against the code being closed; its fixes are made wherever the failure lies, as step 4 already makes them. A story whose diff holds no non-exempt file (a user-checks story answered later) takes no run and records `none`; when it closes its epic it takes one full run unless a full run's recorded snapshot, the baseline's included, matches a fresh one. Any other story closes on its targeted runs, including the only story a run builds, since a story short of its epic's close is not deployed. The baseline stays one full run per run. — AC: `do` states the definition and the rule; control: it says a story that would otherwise run targeted runs full when it closes its epic, and that a story not closing its epic runs targeted though it is the only story the run builds `[manual]`
- **FR6**: A run's finish line needs every story it closed to have closed on a passing run of the kind FR1 and FR5 set, and every epic it closed to have closed on a passing full run; there is no separate end-of-run full run, and a story that closes no epic takes a full run only when `shared/test-runs.md` makes it full. At a baseline, a failing test that a story closed on a targeted run in an In Progress epic explains is not accepted as pre-existing: it is fixed in the next story this run builds in that epic, named in that story's audit prompt with the failing test, or, when this run builds none there, listed under **Needs you** with the test and the story, with a signal. A baseline failure no such story explains is pre-existing as before. — AC: `do` **Scope and finish line** and **Before the first story** state it; control: `do` says a run that closes no epic takes a full run only for a story `test-runs.md` makes full, and a baseline failure no targeted-closed story explains is still accepted as pre-existing `[manual]`
- **FR7**: The audit prompt quotes the story's `**Test run**` line in place of a full-suite result, and lists the targeted tests as the run's coverage, not for the auditor to run. Fixes made outside the story's files to answer a failure its full run or the baseline showed (FR5, FR6) are named in the prompt with the test whose failure each answers. The auditor (`auditor.md`, the opening paragraphs, **What you are given**, checks 1, 3, 5 and 8):
  - treats a targeted result as covering only the tests it ran, checking the line's mapping against the test tree rather than searching afresh;
  - reports as a Warning a test an `Evidence` line or a fix cites that is not in the last run's set, a test that runs a changed code file but was left out, a targeted run on a story with a wide-reach file or an untested code file, and a targeted run on a story that closes its epic or a small change;
  - treats the named out-of-story fixes as in scope and checks them as new code;
  - given a targeted result, runs no further suite, and keeps its rules that it runs tests only when the suite is isolated or free and never repeats a run it was given.
  `do` settles a Warning about a missing or too narrow run by making the run, with no test and no red; when that run passes, the finding counts as fixed in the `**Audit**` line and needs no further audit round; only a failure it shows goes through step 5 as a fix. — AC: `do` **Audit** and step 5 and `auditor.md` state it; control: the auditor's text says the choice of a targeted run on a story with no wide-reach or untested code file that does not close its epic is not a finding `[manual]`
- **FR8**: Every rule that names the full suite or a test run applies to both kinds: two test runs, full or targeted, or a test run and a red pass, never overlap in one checkout; the result before a red pass stands for the audit whether full or targeted; a resumed story takes its step 4 run before its red pass and audit, and a `**Test run**` line whose snapshot hash no longer matches never stands; a full run means every test runner the baseline used, and a cited browser test is in the targeted set. — AC: `do` (**Scope and finish line**, **Before the first story**, steps 3 to 6, **Scratch directories and isolation**, **Audit**, **Finishing**) and `auditor.md` read against it, with no sentence left that assumes a full run per story `[manual]`
- **FR9**: In a parallel batch, the lead's run after the batch is the union of the stories' targeted sets, or full when any story in it justifies a full run (FR1) or FR5 names it (a batch that leaves no story of an epic open outside it closes that epic); each story's `**Test run**` line gives the run, with `sibling Story {n}` when a sibling forced a full run. A one-checkout subagent's run of its own story is that story's targeted run. In `worktree.md`, the subagent's prompt gives the paths of the contract and `test-runs.md`, the lead's run after merging is the one handed to each audit, each story's tests are its targeted set, and after resolving a merge conflict the lead runs the full suite as that batch's run. — AC: `do`'s parallel rules and `worktree.md` state it `[manual]`
- **FR10**: `do`'s **Changed** heading reports how many full and targeted runs the run made, from the `**Test run**` lines' counts, in place of a bare test result against the baseline. — AC: **Finishing** states it `[manual]`

### Should Have

- **FR11**: The cpm-next README (a new log entry, its skills table's `do` finish line, an upgrade note; the 0.8.2 and 0.11.0 entries stay), the root README's CPM Next section, `cpm-next-training-guide.html`, `cpm-next-onboarding.html` and `cpm-next-presentation.html` (every passage stating the per-story full run, the end-of-run full run or the standing rule, and the field tables), and `docs/maintenance/README.md` (`**Test run**` among the contract strings a mod may later parse, the mods' parsers, and `test-runs.md` among the files only some skills read) describe the targeted run, the wide-reach list, the `**Test run**` line, the full run for a story that closes an epic or a small change, and that a story that closes no epic takes a full run only when `test-runs.md` makes it full (a wide-reach file, an untested, deleted or renamed code file, a failing targeted run, a small change, a parallel sibling or merge conflict), so a story of narrow reach with tested code pays only the baseline (one-story runs in fresh sessions still pay a full baseline each). — AC: each names them `[manual]`

### Won't Have (this iteration)

- A per-project setting or a suite-duration threshold.
- Test-impact analysis by coverage tooling; the targeted set is found by reading.
- Changes to the baseline being one full run, to the red pass, or to the isolation and suite-free rules beyond FR8's wording.

## Non-Functional Requirements

- **NFR1**: No added sentence in a SKILL.md, the auditor, the contract or `test-runs.md` records history, per `CLAUDE.md` "A SKILL.md is not a change log"; each describes the current rule, never what it replaced.
- **NFR2**: `claude plugin validate cpm-next` passes, and `claude plugin test` still passes for cpm-next, cpm-next-models, cpm-next-progress and whats-next. A `**Test run**` line in the header block is ignored by the mods' parsers (`docs/maintenance/README.md`, "Unknown fields in the mods"); `cpm-next-progress/hooks/progress.ts` and `whats-next/hooks/plan.ts` count `- ` lines after `**Acceptance Criteria**:` as criteria, which is why the field has no sub-bullets and sits before them.
- **NFR3**: The targeted set, the triggers, the wide-reach list, the exempt kinds, the snapshot and the reasons are stated once, in `cpm-next/shared/test-runs.md`, which only `do` and the auditor read; the contract holds only the `**Test run**` field and a **Where things live** row, since every skill reads the contract.

## Architecture Decisions

### AD1: The choice is judged per story, from the diff
A story's reach decides its run, so a project with a slow suite pays for a full run only where a regression elsewhere is plausible, and a project with a fast suite loses nothing. Rejected: a per-project setting (the user's decision, 2026-11-09), and a suite-duration threshold (the run's cost does not change which stories can break other tests).

### AD2: The closing story carries the full run, through its audit
The story that closes an epic runs full in step 4 and on every rerun until it closes, so a regression an earlier story caused is found and fixed while a story is still open to carry the fix, and no Complete story is reopened. An epic, not a story, is what gets deployed, so a story short of an epic's close takes a full run only for its own reach or failures (the user's decision, 2026-11-09). Rejected: a full run for the last story a run builds (it repeats today's cost for one-story runs), a separate full run after the epic closes (a failure there has no open story), and a full step 4 run followed by targeted fix reruns (the epic would close on code no full run saw).

### AD3: The rules live in one file only `do` and the auditor read
The targeted set, the wide-reach list and the exempt kinds are read by `do` and the auditor, which disagree when each keeps its own copy, and no other skill needs them. Rejected: stating them in both files; putting them in the contract, which every skill reads (review 08; the user's decision, 2026-11-09).

## Scope

### In Scope
A new `cpm-next/shared/test-runs.md` (the targeted set, the triggers, the wide-reach list, the exempt kinds, the snapshot, the reasons); `cpm-next/shared/artifacts.md` (the `**Test run**` field and a **Where things live** row); `cpm-next/skills/do/SKILL.md` (**Scope and finish line**, **Before the first story**, steps 3 to 6, the parallel rules, **Scratch directories and isolation**, **Audit**, **Finishing**); `cpm-next/skills/do/worktree.md`; `cpm-next/agents/auditor.md`; the docs in FR11; versions: cpm-next 0.13.0, marketplace 4.0.9.

### Out of Scope
The mods (they ignore the field); `plan`, `review` and `status`.

## Testing Strategy

Prose changes are checked by reading the changed file against the requirement, with `grep` for required strings and for every remaining "full suite" or "full-suite" phrase (`[manual]`); `claude plugin validate cpm-next` and `claude plugin test` on the four plugins for NFR2. Behaviour is seen only in a live run of an installed release, in the final user-checks epic, in a Laravel project with a test suite, through scenarios that each name the expected `**Test run**` line and run count.

## Assumptions

- The tests that run a changed file are found by reading names, imports, the framework's resolution names and the project's test layout. This is the builder's judgement, written per file in the `**Test run**` line where the auditor can check it.
- A test file the story adds or changes belongs in its targeted set; only shared test setup, fixtures, factories and seeders are wide reach.
- A story with only `[user]` criteria (or criteria treated as `[user]`) left counts as done when deciding which story closes an epic, even before it is unblocked; otherwise the last built story of an epic with a user-checks story would never run full.
- "Through one caller" stops at one hop: a regression two hops away is left to the epic's closing full run, which is the trade the user accepted for the saving.
- `test-runs.md` sits beside the contract and is found the same way (two levels above the skill's or agent's directory); `do` gives its path to the auditor and worktree subagents.
- The red pass needs no change beyond FR8's wording: it runs only the cited test per red.
- An `existing` red still needs its test to have passed at the baseline, which stays a full run.
- A small change (`docs/quick/`) is its own whole scope and is often deployed at once, so its runs are full (FR5); the saving is for stories that don't close their epic, including one built alone with `/cpm-next:do {story}`.
- Each run still takes its baseline as a full run, so one-story runs pay one full run each; a baseline from earlier in the conversation stands while only exempt files changed.
- In a Laravel project much of the code is wired by convention, so a fair share of stories will still run full; FR10's counts show the saving actually achieved.
- Challenge pass (two personas, Test Engineer and Developer): folded in the closing story staying full through its audit (AD2), the definition of a closing story, the baseline rule (FR6), the convention-wired entries and the behaviour-change test in the wide-reach list, test files the story adds staying targeted, the exempt-file list with a `git status` note, the overlap and resume wording (FR8), the auditor's coverage checks and in-scope fixes (FR7), settling a too-narrow run by a run, the parallel and worktree rules (FR9), the field's single-line shape, and run counts (FR10). Not acted on: a targeted run only for leaf file types (the reach list with the behaviour test gives the saving the user asked for; the counts will show if it is too loose); a hash of the working tree at each run (the `git status --porcelain` note does the same job more cheaply); per-runner targeted sets beyond FR8's clause.
