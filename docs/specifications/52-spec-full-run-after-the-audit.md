# Spec: The full run after the audit

**Date**: 2026-11-10  
**Amended**: review 09 (docs/reviews/09-review-deferred-full-run.md) and the user's acceptance of its recommendations — the story snapshot's paths and no `HEAD` line (FR4), the still checkout in a batch (FR1), `none` closing stories (FR1), reruns after an FR3 full run (FR3), the pass floor's terms and a resumed baseline (FR4), the flaky run's pass, the red form, the red retake, the scoped round's signal and count, step 5's last audit (FR5), the `fix due` resume, an in-run mismatch and the `skipped` form (FR6), waiting-on-user and blocked batch stories, the story that takes a shared run, worktree batches sharing files (FR7) (2026-11-10)  
**Source**: conversation (2026-11-10): "Why do we audit after we've run a full suite? Why not audit before?"; "we could split that audit into two … This way we don't run a suite on code that will end up changing?"; the recommendation the user accepted: keep the targeted run before the audit, and give a story that must run full its one full run after the audit's fixes

## Problem Summary

Under spec 51 (cpm-next 0.13.0), a story that `cpm-next/shared/test-runs.md` makes full (a wide-reach file, an untested, deleted or renamed code file, closing its epic, a small change, a sibling or a merge conflict) runs the full suite at step 4, before its audit, and again on every fix rerun in step 5 (`cpm-next/skills/do/SKILL.md` step 4, "it and a small change run full on every run in this step and step 5"; `test-runs.md`, "Every rerun after a fix for a story that is full for one of the reasons in the list above … is full"). Most audits return `fix needed`: 42 of the 50 `**Audit**` lines in `docs/epics/` record findings fixed. So the pre-audit full run usually runs on code that then changes, and in a project whose suite takes 15 to 20 minutes such a story pays two or three full runs where one, on the code being closed, would prove the same.

The audit does not need the full run: it checks each criterion against the tests its `Evidence` lines cite, which a targeted run already runs (`cpm-next/agents/auditor.md`, check 1). What only a full run adds is a regression elsewhere in the suite, and that need be found only once, on the final code, provided any code that finding it changes is audited too.

## Functional Requirements

### Must Have

- **FR1 — The deferred full run.** A story `test-runs.md` makes full takes targeted runs in step 4 and on every step 5 fix rerun, and one full run after its last audit has passed, against the code being closed: the **deferred full run**. It is taken at once: in a single build, before any other story's work; in a batch, as FR7 says. No non-exempt file of the story's own paths (FR4) is edited from its last passing audit until the run has finished, except by a fix FR5 makes; in a batch, siblings' audit fixes go on meanwhile, and nothing runs while the deferred run does. A `none` story that closes its epic takes its full run deferred, after its audit, unless a recorded passing full run stands for it (FR4). The story closes only when the run passes. A story becomes one that needs a deferred run whenever `test-runs.md` makes it full, including through a fix with wide reach. The deferred run rewrites the story's `**Test run**` line as a `full` run with every reason that made the story full. — AC: `test-runs.md` and `do` steps 4 to 6 state it; control: `do` says no other story's work starts between a story's last passing audit and its deferred run `[manual]`
- **FR2 — The pre-audit set of a full story.** For a story that needs a deferred run, the targeted set is the tests its `Evidence` lines cite, the test files it added or changed, and the tests that run each changed code file that is of narrow reach and tested; each wide-reach, untested, deleted or renamed file is mapped `{file} → deferred full run` in the `**Test run**` line. — AC: `test-runs.md` states it; control: it says a wide-reach file's tests are not listed in the targeted set `[manual]`
- **FR3 — Runs that stay before the audit.** Two full runs are not deferred, since each decides how a failure is fixed: the full run after a failing targeted run (`test-runs.md`, **A failing targeted run**), and the runs of a story found order-dependent, which stay full until it closes. Reruns after the first of these, once its failure is fixed, are the story's targeted set with every test that failed in the previous run. — AC: `test-runs.md` states both; control: it says a failing targeted run on a story with a deferred run due is followed by a full run before any fix `[manual]`
- **FR4 — A passing deferred run.** The deferred run is a pass when it has no failure the baseline did not have and its passed count, per test runner, is at least the baseline's less the test cases removed by the stories the run covers. On a resumed run, baseline failures a `full run due` or `fix due` story explains (FR6) are left out of the baseline for this comparison. A pass closes the story with no further audit when the **story snapshot** recorded at its last passing audit still matches: the blob hashes (`git hash-object`, `deleted` for a path that no longer exists) of the paths the story's `**Test run**` mapping names (each changed code file and each test file the story added or changed, which the mapping lists), sorted and hashed with `git hash-object --stdin`, with no `HEAD` line, so it holds across a commit and is recomputed on resume from the line. A story whose story snapshot no longer matches (a file of the story changed since its audit, outside FR5's fix) is audited again as a whole story, as on resume (FR6), before the deferred run is taken. A passing full run already recorded, whose whole-tree snapshot matches a fresh one (the baseline's, or a story's `**Test run**` line reading `full`), stands for the deferred run. — AC: `test-runs.md` and `do` step 6 state it; control: they say a deferred run with fewer passing tests than that floor is not a pass `[manual]`
- **FR5 — A failing deferred run.** A failing test that failed at the baseline is pre-existing as `do` already says. Any other failure is run alone by path: a failure there is a regression; a pass is followed by one more full run, whose pass names the test flaky under **Found** and is the deferred run's pass, and whose failure names it order-dependent, a regression too. Every regression is fixed, wherever its cause lies (the story, an earlier story, a batch sibling, or several together), in the open story whose change explains it or, when none does, in the story that took the deferred run; the failing test, with its failure text from the deferred run, is the fix's red, recorded `red: {failure text} — deferred full run, before the fix` (a contract form the auditor accepts); an FR5 fix that changes a file a red mutated, or a red's test file, retakes that red before the scoped audit. The fix rerun is the one `test-runs.md` gives for a fix rerun, with every failed test added. Then one audit scoped to the fix, handed the failing tests, their failure text and the fix's files, then the deferred run again. One such scoped round is allowed per story whatever its earlier rounds, and step 5's "that audit is the last" applies to step 5's own rounds only; a second failing deferred run, or a scoped audit that returns `fix needed`, marks the story blocked with a `Not met` line and a signal, as step 5's last audit does. Every scoped round writes a `missed-regression` signal (`project`, added to the contract's seed slugs) on the story it is made in, and counts in that story's `n findings fixed`. — AC: `do` step 5 and `test-runs.md` state it; control: `do` says a regression no story's change explains is still fixed under a scoped audit, not unaudited `[manual]`
- **FR6 — The state on disk.** When a story's last audit passes and its deferred run is due, `do` writes `**Audit**: pass ({YYYY-MM-DD}){, n findings fixed} — full run due: {reason}; … — story tree {hash}`, the hash being FR4's story snapshot; on a failing deferred run, `**Audit**: fix due ({YYYY-MM-DD}) — full run failed: {test}; … — story tree {hash}`; on the run's pass, the closing edit writes the `**Audit**` line without the suffix (with a scoped round counted in `n findings fixed`). A story with either form is `In Progress`, so its dependents stay blocked, and `do`'s re-read after a story accepts it. In a `docs/quick/` record the same forms mark the change unfinished. On resume, before other work: a `full run due` story whose story snapshot matches takes its deferred run with no further audit; one whose snapshot does not match is audited again as a whole story (a first audit, with step 5's rounds), then takes its deferred run; a `fix due` story finishes its fix, takes the fix rerun with the failed tests, retakes the reds whose files the fix changed, and is then audited as a whole story, that audit being its scoped round. With no auditor, a full story still takes its deferred run: `**Audit**: skipped — auditor unavailable — full run due: {reason}; … — story tree {hash}`. A failing baseline test that a `full run due` or `fix due` story explains is that story's FR5 regression, not pre-existing. — AC: the contract's `**Audit**` field gives both forms; `do` **Before the first story** (the baseline-failure and resume bullets), step 6 and the re-read rule state them; control: the resume bullet says a `fix due` story is audited before its deferred run `[manual]`
- **FR7 — Batches.** In a parallel batch, the lead's run after the batch is the union of the stories' targeted sets (or an FR3 full run). When any story in the batch needs a deferred run, the batch takes one, shared: every story of the batch waits for it, so none closes before it; it is taken once each story's audit has passed, the story is blocked, or it waits on the user, with nothing else running in the checkout; a story that waited on the user takes its own deferred run when it later closes. A failure is placed by FR5 among the batch's open stories; the story that takes a shared run, for FR5's placing, is the lowest-numbered open story of the batch. A regression a blocked batch story explains blocks the batch's other stories too, listed under **Needs you** with it. In a worktree batch whose stories share files, a sibling's fix to a shared file gives the other story a whole-story audit (FR4). A batch that leaves no story of an epic open outside it gives that epic's stories in the batch the reason `closes epic`; a story is closing when every other story of its epic is Complete, has only `[user]` criteria (or criteria treated as `[user]`) left, or is in its batch. `sibling Story {n}` is no longer a reason. **Changed** counts a shared run once. In `worktree.md`, a subagent whose story needs a deferred run takes its targeted run and red pass when the worktree's results count, as any other; the lead's targeted union after merging is the run each audit is handed; resolving a merge conflict gives the conflicting stories the reason `merge conflict` and retakes each red whose files the resolution changed. — AC: `do`'s parallel rules, `worktree.md` and `test-runs.md` state it; control: `do` says a batch story that needs no full run still waits for the batch's deferred run `[manual]`
- **FR8 — The audit.** The audit prompt for a story with a deferred run due says so and gives its reasons. The auditor (`auditor.md`):
  - reports as a Warning a story `test-runs.md` makes full whose prompt names no deferred run; `do` settles it by naming the run, with no fix round;
  - does not report as left out the tests of a file mapped `→ deferred full run`;
  - still reports a targeted run on a story whose runs FR3 keeps full (`targeted failure`, `order-dependent`);
  - in **A later audit**, takes a scoped round after a failing deferred run, whose prompt gives the failing tests, their failure text and the fix's files in place of earlier findings.
  — AC: `do` **Audit** and `auditor.md` state each; control: the auditor's text says a targeted run on a story whose runs are full as `order-dependent` is a Warning `[manual]`

- **FR9 — Every passage.** Each of these states the deferred run, and none still states a full run before the audit or a full fix rerun for a story `test-runs.md` makes full: `do/SKILL.md` lines 29 (finish line), 31 (small change), 38 and 40 (baseline and resume), 53, 56, 58, 59, 61, 65, 98-99, 110 and 149; `test-runs.md` lines 5, 21, 23, 27, 45 and 58; `worktree.md` lines 14, 18 and 24; `auditor.md` lines 12, 16, 24, 27 and 54-58; `artifacts.md` lines 163 and 165; `status/SKILL.md` line 24, which does not count a story with ` — full run due` or ` — fix due` as a suspect record and names the deferred run as its next action. The finish line keeps its meaning: every epic a run closes closed on a passing full run. — AC: each passage read against it; a case-insensitive grep for `full` over those files, each hit read and accounted for in the `Evidence` line `[manual]`

### Should Have

- **FR10**: The cpm-next README (a log entry, an upgrade note; earlier entries stay), the root README's CPM Next section, `cpm-next-training-guide.html`, `cpm-next-onboarding.html` and `cpm-next-presentation.html` (every passage on when a story runs full), and `docs/maintenance/README.md` (` — full run due`, ` — fix due` and `story tree` among the contract strings a mod may later parse) describe the deferred run. — AC: each names it, the floor being those files `[manual]`

### Won't Have (this iteration)

- Splitting the audit into a code audit and a results audit (a code audit still needs the targeted run to check evidence, and fixes for failures found after it would go unaudited).
- Changes to the baseline, the targeted set of a story that needs no deferred run, the wide-reach list, the red pass or the isolation rules.
- A full run for a story `test-runs.md` does not make full.

## Non-Functional Requirements

- **NFR1**: No added sentence in a SKILL.md, the auditor, the contract or `test-runs.md` records history, per `CLAUDE.md` "A SKILL.md is not a change log". — AC: the epic's grep for "now", "no longer", "used to", "replaced", "previously" over the changed passages, each hit accounted for `[manual]`
- **NFR2**: `claude plugin validate cpm-next` passes, and `claude plugin test` passes for cpm-next, cpm-next-models, cpm-next-progress and whats-next. The mods ignore `**Audit**` (`docs/maintenance/README.md`, "Unknown fields in the mods").
- **NFR3**: The deferred-run rules are stated once, in `test-runs.md`; `do` and the auditor apply them by reference, and the contract holds only the `**Audit**` forms.

## Architecture Decisions

### AD1: The full run follows the audit's fixes
A regression elsewhere in the suite need be found only once, on the code being closed. Since most audits change the code, a full run before the audit is usually repeated. Rejected: splitting the audit in two (above); a full run before the audit only for a fast suite (a per-project threshold, rejected in spec 51); deferring the FR3 runs (they decide how a failure is fixed).

### AD2: A passing deferred run on unchanged audited code needs no audit; any fix it causes does
A pass changes no code, so the auditor's reading of the story still holds. A failure changes code wherever its cause lies, so its fix is audited, in one scoped round, before the deferred run is repeated. This replaces spec 51's AD2 rejection of "a full step 4 run followed by targeted fix reruns (the epic would close on code no full run saw)": the epic closes on code the full run saw, after the fixes.

### AD3: A batch shares one deferred run, and every story in it waits
One-checkout batch stories share no files, so a story snapshot over each story's own paths holds through a sibling's fix, and one full run covers the batch. Waiting keeps every story open to carry a fix, so no `Complete` story is reopened. Rejected: a deferred run per story (the cost the spec removes, times the batch size); letting stories that need no full run close first (a failure their code explains would land on a closed story).

## Testing Strategy

Prose changes are checked by reading the changed file against the requirement, with `grep` for the required strings and for every remaining full-run phrase, each hit accounted for (`[manual]`); `claude plugin validate cpm-next` and `claude plugin test` on the four plugins for NFR2. No `[user]` checks: the behaviour is seen in normal use of a real project. A wide-reach story with one fix round there reads `3 (1 full, 2 targeted) — full — … — wide reach: …` where 0.13.0 gives `3 (3 full, 0 targeted)`.

## Assumptions

- Every reason `test-runs.md` gives for a full run is deferred, wide reach included: the user's case is any story that must run full, and a regression a wide-reach change causes is still found before the story closes. The audit then reads a wide-reach change without the full run's result; a regression found after is fixed under a scoped audit.
- The red pass stays before the audit; it runs only cited tests, and a fix that changes a red's file retakes it, as today. A deferred-run regression's failing test is its fix's red, since it failed against the unfixed code.
- One scoped round per story bounds the loop; past it the story is blocked for the user, who has accepted unaudited last fixes before.
- A resumed story whose snapshot changed, or whose fix was under way, is audited whole again, since its `**Audit**` line cannot say which files changed; this costs an audit only after an interrupted run.
- The pass floor counts tests the run's stories deleted from the baseline's count; a test added by a story is not required, since the baseline did not run it.
- A scoped round always writes a signal, so status does not read a story whose findings-fixed count it raised as a suspect record.
- Challenge pass (Developer, Test Engineer; 2026-11-10): folded in the whole-tree snapshot in batches (AD3, FR4's story snapshot), the deferred run taken at once with a still checkout (FR1), the `fix due` state and resume (FR6), the round cap (FR5), fixes for every regression audited (FR5), a batch waiting together (FR7), the pre-audit set of a full story and the auditor's left-out check (FR2, FR8), classification of a full-run failure (FR5), the baseline rule for unclosed stories (FR6), the pass floor (FR4), the closing-epic batch rule and `sibling` (FR7), the worktree red pass (FR7), the unsettleable Warning (FR8), the passage list (FR9), status (FR9), and shared counts (FR7). Not acted on: a re-audit scoped to the changed files on resume (the line holds one hash, not a per-file list); a separate status for a story awaiting its deferred run (the status vocabulary is parsed by the mods).
