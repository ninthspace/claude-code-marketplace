# Review: Spec 47 — dpm SQLite-Backed Artefact Persistence (re-review)

**Date**: 2026-08-08  
**Source**: docs/specifications/47-spec-dpm-sqlite-persistence.md  
**Scope**: Spec (no epic exists — reviewed against the spec directly)  
**Agents**: Jordan, Margot, Bella, Casey  
**Findings**: 15 (8 critical, 7 warnings, 0 suggestions)  
**Supersedes**: docs/reviews/03-review-dpm-sqlite-persistence.md

## Summary

All fifteen findings from review 03 are genuinely closed, and the four criticals were fixed properly rather than papered over — coverage's natural key now rejects a duplicate binding and accepts two fragments at one position, both unverify triggers fire while the byte-identical control case does not, FTS5 builds and stays consistent across update and delete, and the domain-scoped composite foreign keys reject a severity in a category slot. All of that was re-confirmed by executing the DDL.

What this pass found is a different class. The schema is now internally correct and externally under-constrained: the `(id, kind)` composite-FK pattern the spec argues for at length is applied to two of eighteen references into `document`, so a story can be created under a spec. And the storage story around the database — the deterministic dump, the merge, the restore — carries four verified defects, one of which (two branches each adding an epic produce a dump that will not restore) falsifies the criterion the spec itself names as deciding whether AD3 and AD4 work together.

Two findings are not about the schema at all. The spec's stated user is a project at 393 artefacts and AD8 guarantees every dpm project starts blank; and the ~20 skill files, which are the whole of what a human touches, are specified in one clause. The spec is not ready to feed `cpm:epics`. Most of the schema findings are narrow corrections; the dump-and-merge story and the value question are the two that need real decisions.

**Method**: every `sql` block was extracted and executed against SQLite 3.51, and against `node:sqlite` on Node v22.18.0 for the runtime findings. Each finding below states whether it was verified by execution or established from the text.

## Findings

### Architectural Risks

- **[critical]** 🏗️ **Margot**: Sixteen of the eighteen foreign keys into `document(id)` do not pin the kind, so AD7's supertype enforces existence and almost nothing else. **Verified by execution.**  
  → Data Model, all sections: Exactly two references are kind-pinned — `document(parent_id, parent_kind)` and `observation(library_doc_id, library_doc_kind)`. Unpinned: `requirement.spec_id`, `story.epic_id`, `finding.review_id`, `audit_finding.audit_id`, `retro_application.retro_id` and `.applied_to_id`, `observation.retro_id`, `number_sequence.parent_id`, `dependency.source_document_id` and `.target_document_id`, and all four AD7 detail tables (`library_document`, `adr`, `review`, `quick`), each of which is `document_id INTEGER PRIMARY KEY REFERENCES document(id)` with nothing stopping an `adr` detail row attaching to a runbook. Executed: a story inserted under a spec, a requirement under an epic, and a `library_document` row on a spec were all accepted. AD7's stated consequence is that "`artifact → document`, `retro → epic`, `review → epic` … all reference one enforceable primary key" — they reference it; none of those arrows is enforced. The spec argues this exact case for parentage at line 244 ("guarantees the parent *exists* … but not that it is the right sort of thing"), builds the `document(id, kind)` unique index that makes the fix available, and then applies it twice. False-pass register #12 covers `parent_id` and nothing else, though a story under a spec renders just as plausibly.

- **[critical]** 🏗️ **Margot**: AD3 and AD4 do not add up to a working branch-and-merge story, and the collision is on the surrogate key *and* on the human-facing number. **Verified by execution.**  
  → AD4 (104–110) / FR8 criterion (916): Two branches from a common base each adding an epic both allocate `document.id = 2`; the merged dump fails to restore with `UNIQUE constraint failed: document.id`. Moving to ULIDs does not close it — `document_root_number` is `UNIQUE (kind, number)` and two branches each creating a spec both allocate 48 from their own `number_sequence`, so the merge then fails on the number index instead. This is structural rather than a bug: FR5 promises a monotonic never-reused counter and a per-clone counter cannot be monotonic across clones. AD4's whole argument is that the dump is "the only remaining place where branching can work"; the design needs an explicit answer — branch-scoped id space, renumber-on-merge with the projection filenames following, or a declared single-writer model that retracts the merge claim. Line 980 already names this criterion "the one that decides whether AD3 and AD4 together actually work" and, in the same sentence, the one most likely to be skipped.

- **[critical]** 💻 **Bella**: NFR4 byte-stability is unattainable for the dump as specified, and the component that would produce a stable one does not exist in the stated stack. **Verified by execution.**  
  → NFR4 (71) / AD4 (104) / AD5 (112) / Scope (866): Three separate legs, each confirmed. (i) `.dump` emits the FTS5 shadow tables (`document_fts_data`, `_idx`, `_docsize`, `_config`) as hex blob literals; two databases with byte-identical logical content built in different insertion orders produce different blobs, so the same logical state does not produce the same bytes, and a merge conflict inside a segment blob has no correct hand-resolution — the exact failure AD4 rejected the binary `.db` for. (ii) Stock `.dump` emits rows in physical rowid order, so for the fifteen tables without an `INTEGER PRIMARY KEY` the byte order follows insertion history; identical `test_approach` content inserted in two orders produced two different dumps. (iii) `node:sqlite` has no dump: its exports are `DatabaseSync, StatementSync, backup, constants`, and `backup` is binary-to-binary. So the deterministic dumper is dpm's own code — it must produce `X'…'` BLOB literals (the naive version returns `Uint8Array` and stringifies to `'153,0,178,0'`, silent corruption), skip the virtual table, emit triggers after data so the load does not double-index, and impose a total row order per table, all under a byte-equality contract. Scope gives it one bullet and AD4 gives it one word ("sorted"). Restore must also end with `INSERT INTO document_fts(document_fts) VALUES('rebuild')`, and the server must reopen afterwards — a restore through `node:sqlite` succeeded and then failed `MATCH` with `no such table: document_fts` on the same connection, because the schema cookie is not reloaded.

- **[critical]** 💻 **Bella**: FR21 names two texts and the schema watches one — editing `coverage.spec_fragment` leaves the ✓ standing. **Verified by execution.**  
  → FR21 (44) / `coverage` (489–499) / triggers (511–525): FR21 reads "editing either the **requirement fragment** or the story criterion resets it to unverified automatically". The two triggers fire on `requirement.text` and `story_criterion.text`. `coverage.spec_fragment` — which is the requirement fragment, and which `binding_hash` is documented at line 496 as hashing — has no trigger. Setting it to a completely different string on a verified row left `verified_at` and `binding_hash` unchanged, now attesting to a fragment that no longer exists. That is false-pass register entry #2 verbatim, still open, in the one subsystem this spec was written to fix, and it is the third draft in which this table has carried a verification defect. No criterion covers it: lines 923–926 test the criterion edit, the requirement edit, the lockstep `CHECK` and the control case, and none touches the fragment. A third trigger `AFTER UPDATE OF spec_fragment ON coverage` closes it.

- **[critical]** 🏗️ **Margot**: Nothing regenerates or guards the committed `.sql` dump, and the failure mode is silent loss of everything since the last dump.  
  → AD4 (106) / FR7 (39) / false-pass register (986–1001): The `.db` is gitignored and the `.sql` is the only committed copy of the source of truth. FR7 specifies a pre-commit guard for *markdown* divergence and there is no counterpart for dump divergence — no requirement, no acceptance criterion, and no register entry, though the condition has every property of registered entries #3 and #4. A user who commits after a session of writes commits a stale dump; git reports success, the diff looks plausible because the markdown *was* regenerated, and the work is gone at the next clone. It runs the other way too: after a merge, the guard regenerates markdown from a local `.db` that has not absorbed the merged `.sql`, so it compares merged markdown against unmerged data and blames the markdown. The spec needs to say which of `.db` and `.sql` is authoritative when they disagree, and when the dump is written.

- **[warning]** 🏗️ **Margot**: The seam the spec names as its own biggest risk has no decision, no requirement and no acceptance criterion.  
  → Integration Boundaries (1007, 1012): "Seam 1 is where drift would re-enter the system if it re-entered anywhere … One definition, generated into both, or a test asserting correspondence." That is an unresolved either/or between two very different architectures — schema-as-source with codegen, versus two hand-maintained definitions plus a conformance test — presented in the Testing Strategy rather than as an AD. Across ~50 tools and 36 tables it is plausibly the largest single piece of work in the project and it determines whether the MCP layer is generated or written. No criterion tests it: criterion 901 ("Creating an epic with a non-existent `spec_id` fails") is satisfied by a raw FK violation surfacing from SQLite, which is validation at the database layer — the thing seam 1 exists to detect. FR3's actual promise, "a malformed call is rejected at the tool boundary **before it reaches the database**", and AD2's justification for choosing MCP over a CLI, are both untested. This deserves AD9.

- **[warning]** 🏗️ **Margot**: The cross-row invariant register is missing entries of exactly its own shape, and FR14's closure criterion turns that from a gap into a prohibition.  
  → Cross-row register (807–818) / criterion 954: Verified missing cases include a review whose `scope_story_id` names a story outside the epic it reviews (accepted; the same four-table-join shape as #3 and #4); `adr_option` permitting two rows with `chosen = 1`; `coverage.spec_fragment` not actually being a substring of its requirement (accepted, and a genuine cross-row rule on the register's own terms); a retired `taxonomy` / `test_approach` / `dependency_kind` row still accepted on *new* rows, which makes FR24's retirement decorative; and `session.superseded_by` admitting an adoption cycle. Separately, `.dump` opens with `PRAGMA foreign_keys=OFF`, so the one path the register expects violations to arrive by — "chiefly by restoring a dump" — is the path on which every FK is advisory, and `PRAGMA foreign_key_check` appears nowhere in the spec. Because criterion 954 says "the tool has no check absent from the register", an unregistered invariant is not merely unchecked; the criterion specifies that its check must not exist.

- **[warning]** 🏗️ **Margot**: FR9 indexes `document_section` only, so the majority of dpm's text is unsearchable and the miss is silent.  
  → `document_fts` (765) / FR9 (41): The FTS5 table is external-content over `document_section`. But the thrust of the schema is that the meaningful text is not in sections — requirements, stories, tasks, acceptance criteria, story criteria, coverage fragments, findings and observations are all child tables with their own `text` columns. FR9 says "artefact bodies are indexed"; line 797 defends the omission of *titles* and does not address the child tables at all. Today a user greps `docs/` and finds a requirement by its wording; after dpm, the search tool returns nothing and no error — false-pass register entry #3's shape ("a query misses what was just written and returns 0 hits, not an error"), arriving by design rather than by a missing trigger. Either a contentless index fed by triggers on every text-bearing table, or FR9 should say plainly that search covers narrative sections only.

### Unclear Requirements

- **[critical]** 📋 **Jordan**: The person the spec names as its user is the one person AD8 guarantees cannot use it.  
  → Problem Summary (9–11) vs AD8 (157–169) and Out of Scope (871): The document opens by naming its user precisely — "projects running CPM at a volume where prose reconstruction stops holding", evidenced by one real project at 393 artefacts — and says of the degradation, in the same paragraph, "None of that appears in a project with nine artefacts." AD8 then rules that every dpm project starts blank with no importer, and Out of Scope makes that permanent. So the only user whose pain is evidenced cannot bring that pain to dpm, and every project that *can* adopt starts at the volume where, by the spec's own sentence, the problem does not exist. The value arrives only after a fresh project independently accumulates hundreds of artefacts — a horizon the spec never names or prices. Both halves of the argument are individually well made; together they leave the first release with no user who benefits on day one. This needs an explicit answer: who adopts and when the payoff lands, or a reconsideration of AD8's blanket no-importer. Adoption cost is also never stated — install a plugin, run Node ≥22.5, configure an MCP server, abandon every existing artefact, learn ~20 new skills and a deliberately different vocabulary — and hand-editing a planning document, which is how a user fixes a typo today, becomes a pre-commit failure by design with no replacement workflow specified.

- **[warning]** 🧪 **Casey**: Six hand-maintained counts disagree with what they count, including the one carrying the document's strongest evidence.  
  → Lines 696, 268, 275, 855/857, 142, 1005: (i) "they appear as **eleven distinct headings**" — the table directly beneath lists twelve (`Smooth Deliveries`, `What Went Smoothly`, `Smooth Delivery`, `Codebase Discoveries`, `Codebase Discovery`, `Testing Gaps`, `Testing Gap`, `Testing Notes`, `Scope Surprises`, `Scope Surprise`, `Criteria Gaps`, `Patterns Worth Reusing`), and the figure is repeated at lines 9, 714 and 836. (ii) Line 855 correctly says "Thirty rows"; line 857, two sentences later, says "the twenty-seven rows above". (iii) Line 268 says the kinds "land in three places" over a four-row table. (iv) Line 275's "thirteen document kinds, seven child tables, two standalone … accounts for twenty of the twenty-one" reconciles only if `coverage matrix` and `coverage` are the same FR10 item, which the Data Model treats as two things. (v) M3's "remaining nine kinds" is ten under any reading of M2. (vi) Integration Boundaries opens "Four seams:" and lists three. The prior review flagged two stale counts; the fix corrected one table's own count and left the sentence two lines below it. In a document whose thesis is that hand-maintained facts drift out of step with what they describe, the eleven-versus-twelve is the one a reader will check.

### Missing Acceptance Criteria

- **[critical]** 📋 **Jordan**: The only part of dpm a human ever touches has no functional requirement, no scope definition, and one negative acceptance criterion.  
  → In Scope (867) / AD6 (134) / M4 (143) / criterion 905: "dpm skill files mirroring CPM's pipeline, rewritten against the tool surface" is the entire specification of roughly a quarter of the build. No FR governs them; FR3 mentions skills only to forbid SQL in them, and its criterion — "Every dpm SKILL.md contains no SQL keyword" — is the sole check on the whole corpus. (That criterion is also unrunnable as worded: `UPDATE`, `TABLE`, `ORDER` and `VALUES` are SQL keywords and ordinary English, and NFR5 mandates tool names like `dpm_update_epic`, so every skill documenting its own tool surface contains the string.) Nothing says which twenty skills, what "mirroring" means, or how anyone judges one done, while 77 criteria cover the schema in forensic detail. `cpm:epics` will invent this, late, in M4, against no criteria. Relatedly, M2 is described as "the first point at which a project could actually be planned" and the skills that make planning possible are in M4, so the one design risk that survives — whether the pipeline works against a typed tool surface — is the last thing anyone finds out.

- **[warning]** 💻 **Bella**: FR6 tests that the projection is deterministic and never that it reflects the database, and three projected collections have no ordering at all.  
  → FR6 criterion (912) / `finding`, `audit_finding`, `observation`, `coverage.position`: "Regenerating the projection twice from one database state yields byte-identical output" is passed by a renderer that emits an empty file for every document, and by one that renders the wrong epic. Nothing asserts that a value written through a create tool appears in the rendered markdown — the property FR6 exists for ("pull requests show a readable prose diff of what changed"). Worse, byte-identical regeneration is not a property the schema currently supports: `finding`, `audit_finding` and `observation` have no `position` column, so a review's findings render in whatever order SQLite returns them, and removing `position` from `coverage`'s key (correctly) left it with no uniqueness, so two rows at position 1 have undefined tie-breaking. That will pass on a small fixture and fail intermittently on a real corpus, which is the worst available failure schedule. Every projected collection needs a unique `(parent, position)` or a declared sort with a tiebreak on `id`.

### Testability Concerns

- **[critical]** 🧪 **Casey**: Two FR14 criteria cannot both pass — one requires an orphan check, the other forbids it.  
  → Testing Strategy, 953 and 954: 953 is "The integrity tool reports a deliberately orphaned row"; 954 is "Every numbered entry in the cross-row invariant register has a check in the integrity tool, **and the tool has no check absent from the register**". The register has six entries and none of them is orphans or dangling links — yet FR14 itself requires "orphans, dangling links, **and** each entry in the register". The moment 953 passes, 954 fails. The closure clause was added to make the register-ranging criterion falsifiable and was written as if the register were the tool's whole job. It needs to be scoped to *register-derived* checks, or the register needs orphans and dangling links as entries 7 and 8. The same clause also makes register entry #6 unsatisfiable: line 818 states the legal endpoint set "is not yet known" and that inventing it "would fix guesses in a constraint", while 954 and 955 require the integrity tool to check it — so the guess gets fixed in a test instead, where it is less visible.

- **[warning]** 🧪 **Casey**: Two criteria added by the last remediation reference artefacts the spec does not contain, and one of them rejects a tool AD6 requires.  
  → Testing Strategy, 972 and 974: FR13's only positive criterion is "the response for a 20 KB epic stays **under the stated ceiling**" — no ceiling, byte budget or token figure exists anywhere in the document. FR13 is a number-shaped requirement with no number, and it is the requirement the Problem Summary leans on for not pulling 20 KB into context; whoever writes the test picks the number, and the number becomes the spec. NFR5's criterion is "matches `dpm_[a-z_]{6,}` and contains **no abbreviation absent from the project glossary**" — there is no glossary, nothing in scope creates one, and `adr` is an abbreviation the schema requires. The regex half also rejects `dpm_link`, one of the four utility tools AD6 names. Both criteria closed the prior review's "FR13 and NFR5 have nothing" gap with text that still cannot be executed.

### Hidden Complexity

- **[warning]** 📋 **Jordan**: AD6's sizing is computed against thirteen kinds when parity is twenty-two entity types, so the estimate the last review asked for is understated at its base.  
  → AD6 (134) vs FR10 criterion (920) and the enumeration (266–275): The sizing says "roughly 45–55 MCP tools (thirteen kinds across create, read and update, plus link, search, integrity and migrate)" and "thirteen projection templates" — arithmetic of 13×3+4 = 43. FR10's own criterion is "The thirteen seeded `document_kind` rows, **seven child tables and two standalone tables** … each have a create tool and a projection template" — 22 entities, so 22 create tools and 22 templates. One of the two standalone tables is `session`, and line 758 says session state is not a file, so the criterion requires a projection template for something that renders nowhere. The register names three further tools the count omits (link tool, "ADR status tool, which sets both or neither", coverage link tool), and nothing covers allocate, archive, verify or unverify. Separately the enumeration covers 22 of the 36 tables, leaving `acceptance_criterion`, `dependency`, `document_section`, `taxonomy` and `retro_application` — several of them load-bearing — outside any parity criterion. The number that decides whether AD6 is affordable is wrong, and wrong low.
