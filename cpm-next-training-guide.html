cpm-next training guide

A reference for developers who plan and build with cpm-next in Claude Code: what to install, what each skill reads and writes, how do builds and audits work, how model and effort are set, and how to follow progress.

Covers cpm-next 0.12.0, cpm-next-models 0.3.2, cpm-next-progress 0.8.0, whats-next 0.3.0 and plugin-sync 0.1.0. The artefact formats are defined in cpm-next/shared/artifacts.md.

What changed since 0.8.0.

  • Every test-proven criterion's Evidence line records a red: the failure seen with the covered lines undone. Reds are taken in one red pass per story, and a commit guard refuses git commit while a pass is open.
  • New tags [browser] and [user]; a story waiting on you is skipped, listed apart by /next and shown as Waiting on input by the tracker.
  • No retros: do records signals, and a failure that recurs becomes a lesson you approve. library learn promotes them, and library sweep looks across repositories.
  • Audits read the recorded tests rather than re-running them, later audits are scoped to the fixes, and severity weighs how likely the failure is.
  • A small change gets a docs/quick/ record with criteria before any code; do all {spec} runs one spec unattended; --parallel is for stories that share files.
  • Every run ends with Needs you, and plan, review and do take you through each item with a recommendation.

1What cpm-next is

cpm-next is a Claude Code plugin for planning and building software. It turns an idea into working, tested code through a short chain of Markdown documents kept in your repository's docs/ folder: a discussion record, a product brief, a specification, and epics made of stories with acceptance criteria.

Six skills cover the whole path:

SkillWhat it doesFinished when
/cpm-next:partyDiscussion with named specialist personas (PM, Architect, Developer, UX, QA and others)A discussion record is saved and the next step is named
/cpm-next:planWrites whatever is missing of brief, spec and epics, from whatever already existsThe artefacts down to the epics exist and trace upward
/cpm-next:reviewIndependent challenge of the epics before they are builtCritical and Warning findings are fixed or waiting on you
/cpm-next:doBuilds stories, verifies each acceptance criterion with evidence, and has each story auditedEvery story in scope is Complete and the tests pass
/cpm-next:libraryCurates reference documents in docs/library/ that planning and building readDocuments carry complete front-matter
/cpm-next:statusRead-only report of where things stand and the next command to runNothing is written

Three principles run through all of them:

  • The artefacts are the only state. The discussion record and the epic doc hold everything a later session needs. There are no progress files to clean up.
  • Each skill states a finish line. Every skill says what "done" means and when to stop; how to get there is left to the model.
  • Different models for different jobs. Opus plans and reviews, Sonnet builds, an Opus auditor agent checks every story before it closes, a Haiku scout agent answers lookups, and status runs on Haiku.

A typical path through a piece of work:

  1. /cpm-next:party to talk an idea through (optional).
  2. /cpm-next:plan to write the brief, spec and epics. It reads what exists, asks its questions in one batch, and fills only the gaps. In a brownfield project it grounds every requirement in the current code.
  3. /cpm-next:review before a large or risky epic (optional).
  4. /cpm-next:do to build: one story (/cpm-next:do 3), one epic, one spec's epics (all 04), or all, which runs unattended and marks a blocked story instead of stopping. Each acceptance criterion gets an Evidence line, and each story is audited before it closes.
  5. /cpm-next:status whenever you return to the project.

cpm-next replaced CPM's twenty-one skills and reads CPM v3 artefacts as input, including legacy flat epics ({nn}-epic-{slug}.md) and coverage matrices. CPM and DPM, the earlier planning plugins, were withdrawn from the marketplace on 2026-10-08.

2Installation

Add the marketplace once, inside Claude Code:

/plugin marketplace add ninthspace/claude-code-marketplace

The suffix is the marketplace's name, not the repository's. marketplace.json declares ninthspace-marketplace, and every installed plugin is keyed by it, so cpm-next@claude-code-marketplace resolves to nothing.

The cpm-next set

Install these at user scope (the default), so one install serves every repository:

/plugin install cpm-next@ninthspace-marketplace           # the six skills, the auditor and scout agents
/plugin install cpm-next-models@ninthspace-marketplace    # mod: holds each skill's model and effort, per-story effort
/plugin install cpm-next-progress@ninthspace-marketplace  # mod: /progress-tracker, claude.ai trackers per spec and an overview of every project
/plugin install whats-next@ninthspace-marketplace         # mod: /next, a live pane of the work left in the repository
/plugin install plugin-sync@ninthspace-marketplace        # mod: reloads open sessions when a plugin here is updated
/reload-plugins

Only cpm-next is required. The four mods are optional, and each adds one thing:

What mods are

Mods are plugins of function hooks that run inside Claude Code. They load like any plugin, run no model calls of their own unless stated, and are switched off and on with the plugin. (The whats-next pane's Ask Claude button is the stated exception: it asks Sonnet for a short note.)

A session that was open before you installed a mod needs /reload-plugins to load it.

Per-project setup

Nothing has to be configured per project for the skills or for cpm-next-models, whats-next and plugin-sync. The progress tracker is set up per spec: in a repository whose spec has epics in docs/epics/, run /progress-tracker 01 (the spec's number); the mod writes the page and asks Claude to publish it. See section 7.

To have /cpm-next:library sweep read other repositories, list them with /cpm-next:library sweep add {path}; the list lives at ~/.claude/cpm-next/repos.txt.

To replace the default personas used by party and review, copy cpm-next/agents/roster.yaml to docs/agents/roster.yaml in your project and edit it. The project copy replaces the plugin default entirely; the two are not merged.

Keeping up to date

The marketplace auto-updates when Claude Code starts. plugin-sync then reloads sessions that were already open: every five minutes, and after each answer, it compares ~/.claude/plugins/installed_plugins.json with the versions of this marketplace's plugins that the session loaded. When one differs, it shows a one-line notice naming the plugins and versions and runs /reload-plugins, which waits until the session is idle. A project-scope install is compared for sessions in that project, and the user-scope install for all others.

plugin-sync does not install updates. To update straight away, from any directory:

claude plugin marketplace update ninthspace-marketplace
claude plugin update cpm-next@ninthspace-marketplace      # and each other plugin that changed

A session that was open before plugin-sync was installed needs one manual /reload-plugins to load it; after that it reloads itself.

To remove the set:

/plugin uninstall cpm-next@ninthspace-marketplace
/plugin uninstall cpm-next-models@ninthspace-marketplace
/plugin uninstall cpm-next-progress@ninthspace-marketplace
/plugin uninstall whats-next@ninthspace-marketplace
/plugin uninstall plugin-sync@ninthspace-marketplace

3The artefacts

The skills keep their procedures short and their data strict. The whats-next and cpm-next-progress mods parse these files, so the formats are a contract: the skills write them exactly and read them tolerantly. If you edit an artefact by hand, keep to the same formats.

Two further files belong to the progress mod, not to cpm-next itself: the build-order file docs/specifications/NN-build-order.json, and the generated folder .claude/cpm-next-progress/. Both are described in section 7. A red pass keeps its copies under the repository's git directory, in .git/cpm-next/scratch/, outside the working tree (see Red passes).

Numbering

  • {nn} is max + 1 over the integer prefixes in both docs/{type}/ and docs/archive/{type}/, compared as integers, never as strings.
  • Numbers are padded to at least two digits: 01, 99, 100.
  • Numbers are never reused, and existing files are never renamed.
  • Epic prefixes have two parts. {parent} is the source spec's number, or 00 when the epic comes from a brief, discussion or description with no spec. {seq} is max + 1 over existing epics with that parent, again across active and archive. So spec 04-spec-loans-export.md produces epics 04-01-epic-…, 04-02-epic-… and so on.

Status vocabulary

The first token of a **Status**: value is what tools read. Anything after — is a note for people.

Applies toValues
Stories and tasksPending, In Progress, Complete
EpicsThose three, derived from their stories, plus the user-set terminal values Superseded and Withdrawn. The skills never set the terminal values.
DiscussionsIn progress or Concluded
  • Done is read as Complete; the skills always write Complete.
  • A story is unblocked when its **Blocked by** is — or every item it names is Complete, and every item its epic's **Blocked by** names is Complete. (do also waits for a blocking story's **Audit** line before starting its dependents.)
  • A Superseded or Withdrawn epic never satisfies a dependency.
  • A story do has to stop on (a Not met line, an unresolved audit finding, a failure it can't explain) is marked blocked: it keeps its status and gains the note — blocked: {reason}, for example **Status**: In Progress — blocked: export still buffers rows. The note comes off when you settle what blocked it.
  • A story is waiting on the user when it is unblocked, not marked blocked, and every criterion still lacking Evidence is [user] or carries a - Waiting on user: line. It keeps its status; do skips it and counts it as done for its finish line. A waiting story is not blocked.

Epics, stories and tasks

The epic format:

# {Epic Name}

**Source spec**: {path, or the brief/discussion path for a 00- epic}
**Date**: {YYYY-MM-DD}
**Status**: Pending
**Blocked by**: —

## {Story Title}
**Story**: {N}
**Status**: Pending
**Blocked by**: —
**Satisfies**: {FR1, NFR2 — omit only for 00- epics}
**Effort**: {low | high — optional}
**Model**: haiku {optional, on a low story only}

**Acceptance Criteria**:
- {criterion} `[tag]`

### {Task Title}
**Task**: {N.1}
**Description**: {what this task covers within the story}
**Status**: Pending

---
  • Stories are numbered from 1 within each epic. Tasks are numbered {story}.{seq}.
  • Dependencies inside an epic name stories (Story 2). Dependencies across epics name the epic by filename prefix (Epic 28-01-epic-setup).
  • **Satisfies** names the spec requirements the story delivers. It is omitted only in 00- epics, which have no spec.
  • **Effort** is how hard do thinks while building the story. A story without one is built at medium.
  • **Model**: haiku marks a low story as a fixed, mechanical edit that a Haiku subagent can make.
  • Neither **Effort** nor **Model** changes what the story must deliver or how it is audited.
  • Acceptance criteria carry a tag naming who or what proves them, matching the spec's tags: [unit], [feature] or [integration] (a test suite); [browser] (only a rendered page proves it); [manual] (a step do performs in the session outside the test suite); [user] (only you can prove it: a production run, a deploy, a sign-off, a third-party account). A tool reads the last backticked word of the criterion as its tag.
  • The epic header may carry a **Lessons** line naming the library lessons and recurring signals that bear on the epic (see Fields).

Things to notice:

  • Each Evidence line is indented directly under the criterion it proves. The criterion line itself is never edited to record verification.
  • Each test-proven criterion records its red: the first line of the failure the cited test gave with the covered lines undone, or with a covered line mutated. A criterion no test proves records red: n/a with a reason. See Evidence.
  • A story is Complete only when every criterion has an Evidence line. A Not met line in its place leaves the story marked blocked: 
    **Status**: In Progress — blocked: export still buffers rows
…
- Every export streams its rows, so memory does not grow with the date range `[integration]`
  - Not met: chunked query tried; peak memory still grows with the range because the formatter buffers rows
  • A criterion only you can prove waits for your answer, and its evidence is written only from it: 
    - Library staff confirm the exported file opens in the council's finance system `[user]`

  • The **Audit** line is written in the same edit that sets the story to Complete.
  • The epic's own **Status** moves to Complete with its last story.
  • A legacy story-level **Evidence**: field from CPM v3 is read as valid input, but never written.

Signals

A signal records a failure do found, on the story (or in the docs/quick/ record) where it happened, so that a second occurrence can be recognised. Nothing is learned from a one-off.

**Signal**: {class-slug} — {project | process} — {what failed, one line} ({file and step, rule or check involved}){ — cpm-next {version}}{ — recurs: {reference} ({why it matches})}{ — raised {YYYY-MM-DD}}{ — promoted {YYYY-MM-DD}}{ — declined {YYYY-MM-DD}}
  • project: the cause is in this codebase. process: a cpm-next rule could have prevented it, and the parenthesis names the cpm-next file and step. A process signal also carries — cpm-next {version}, the version in the installed plugin's .claude-plugin/plugin.json; a project signal carries none.
  • A class slug is kebab-case and names the kind of failure, not the instance. An existing slug, a library lesson's **Class** or a seed is reused before a new one is made. Seeds: check-cannot-fail, shared-state-collision, unprovable-in-session, instance-not-rule, spec-drift, fix-not-carried-through, definition-in-two-places.
  • A signal reference is {epic path} → Story {N} → {slug} or {quick path} → {slug}.
  • — recurs: marks a signal matching a library lesson, a signal in a different epic or quick record, or an unretired legacy retro observation. — raised marks one listed as a promotion candidate, — promoted one written to the library, — declined one you refused (a signal matching a declined one is declined too).
  • do, plan and review read library lessons, signals that recur and unretired legacy retro observations. A signal that never recurs is never read as context or reported.

How do writes and routes them is under Signals and recurrence.

Legacy retros

Retros in docs/retros/ are legacy input: no skill writes one. do, plan and review still read their unretired observations, status counts them, and /cpm-next:library learn promotes or retires them. An observation is a bullet under ## Observations, usually in a ### {Category} group:

## Observations
### {Category}
- {observation}: {what it means for the next piece of work}

An observation that has been promoted to the library, or has stopped being true, is retired in place rather than deleted, by appending **Retired {YYYY-MM-DD}**: {reason, or "promoted to {library path}"} to its bullet. Every skill skips a retired observation. Removing the marker restores it.

Amending an existing artefact

An amendment is an edit in place with an **Amended**: {YYYY-MM-DD} — {summary} line under the header. A Complete story's criteria are never rewritten; new work becomes a new story. When an upstream change alters what a Pending story must do, that story is updated in the same pass.

4The skills

Each skill below lists when to use it, what it reads and writes, where it stops, the model and effort in its frontmatter, and what it asks you. Every skill reads the artefact contract before writing anything.

/cpm-next:party

model: sonneteffort: mediumwrites: docs/discussions/
When to use it
Brainstorming, weighing trade-offs, or testing an idea before committing to a plan, whether or not any planning documents exist yet. It is the divergent part of the method: it widens the options and sharpens the trade-offs. Converging into requirements is plan's job.
What it reads
Personas from docs/agents/roster.yaml if it exists, otherwise the plugin's agents/roster.yaml. Files and URLs you pass. The project's docs/ artefacts and, when the topic touches code, the code itself, so the team argues from the actual state of the project.
What it writes
A discussion record, created at once and updated every few substantive exchanges, not only at the end. It is what survives context compaction and what plan reads later.
Finish line
On "wrap up", "done" or similar: the record is finalised with **Status**: Concluded, its path is given, and the next move is named in one line, usually /cpm-next:plan {record path}.
What it asks you
Questions to you are only about intent, priorities and preferences. Anything discoverable in the code or docs is looked up before anyone speaks.

How a round works

  • Two or three personas speak per round, chosen by the expertise the point needs, favouring anyone who hasn't spoken for a while. A persona you name always speaks.
  • Each contribution is formatted {icon} **{displayName}**: {response}, makes a recommendation, and responds to the others by name. Disagreement is left standing rather than smoothed into consensus.
  • When the discussion has landed, a line follows the round: 💡 **The team recommends**: … or 💡 **Two paths**: ….
  • Each round ends with Type wrap up to finish, or keep going. Do not type "exit" or "quit": those close Claude Code itself.
  • A lone persona name, or "consult {name}", starts a one-to-one: that persona leads every turn and others join only when you invite them.
  • If a session finds a record with **Status**: In progress, it carries on from it.

/cpm-next:plan

model: opuseffort: mediumwrites: briefs, architecture, specifications, epics
When to use it
Whenever you want to plan, scope, specify, break down or re-plan work, even if you name only one of brief, spec or epics. It works for greenfield and brownfield projects from any starting state, and amends existing documents when direction changes.
What it reads
docs/ in full (discussions, plans, briefs, architecture, specs, epics with their status and signals, library, quick, legacy retros); planning material outside CPM's shape such as PRD.md, README.md, docs/*.md, CLAUDE.md and issue text you paste; and in a brownfield project, the code: stack, conventions, the modules the work touches, the test setup and test command. For a large codebase it gives each area to its own Opus subagent in parallel and checks what each reports against the files it cites. Plain lookups go to the scout agent on Haiku.
What it writes
Only what is missing, top-down from the first missing artefact: a brief, a spec, ADRs for decisions that outlive the spec, and epics. It skips any level that would only restate the one above it; a small, well-understood change can go from a discussion or description straight to a 00- epic.
Finish line
Unless you name a nearer target, the run is done when every artefact from where the project stands down to epics exists and traces to the one above; every Must Have requirement is satisfied by at least one story and every **Satisfies** names real requirements; every acceptance criterion is something do can check, by a test or a concrete manual step, or is a [user] criterion written with its exact steps and the observation that proves it; and nothing you still have to decide is hidden inside a story.
What it asks you
One AskUserQuestion call with up to four questions, each with options and a recommended default, and only for answers that you alone hold and that would change scope, cost, or a choice that is hard to reverse. Everything else it decides and records in the artefact's Assumptions section, so you can overturn it at review. If there are no such questions it says so and writes.

What it puts in each artefact

  • Brief, when the problem, users or value aren't written down anywhere: two or three different approaches, one chosen with reasons, the rest kept as alternatives considered.
  • Spec: MoSCoW requirements with stable labels, measurable NFRs, architecture decisions with the alternatives rejected, explicit scope boundaries, and a testing strategy tied to the project's real test command. In a brownfield project every requirement names the existing models, routes or components it extends.
  • Challenge pass: for a non-trivial spec, two or three roster personas, each as an Opus subagent, look for what would make the plan fail. What holds up is folded in; what isn't acted on is noted in Assumptions with the reason.
  • Epics: split by coherent deliverable, not by layer. **Blocked by** only for real ordering constraints, since do runs unblocked stories, in parallel where they are independent.
  • Criteria that can fail: a criterion saying what must not happen, must not change or never occurs names its control in its own text: the same inputs with the forbidden outcome present fail the check, and a compared set gets a floor naming members it must contain. A negative assertion with no control passes when the feature does nothing.
  • The rule, not an instance: each criterion states the rule its requirement sets ("every export streams its rows", not "the January export streams its rows"). A regression for one reported input goes beside the rule's criterion, not instead of it.
  • Tags by who proves it: each criterion is tagged by who or what can prove it, and one needing two kinds of proof is split. A spec's [user] criteria go in one final user-checks epic that no other epic is blocked by, so no other work waits on you; in a 00- epic they go in a final story that nothing else is blocked by.
  • Lessons: before writing an epic's criteria it decides which library lessons, recurring signals and unretired legacy retro observations bear on the epic, reflects each one about the result in a criterion of the story it applies to, and names them all in the epic's **Lessons** line.
  • Story effort: **Effort**: high where getting it wrong is costly or hard to see (security, authorisation, migrations and other data changes, concurrency, executable scripts and hooks, or code the plan found hard to understand); **Effort**: low for mechanical edits (a config value, a copy change, a rename, a row in a table); no field otherwise. **Model**: haiku is added to a low story only when the edit is fully determined by the story.

Existing material

  • It adopts existing briefs, specs and epics rather than regenerating them, and does not convert documents that aren't going to change.
  • Foreign epics or task lists that do needs to run are converted into the epic format, with the original's path in **Source spec**, and clearly finished items mapped to Complete.
  • A change of direction is an amendment in place with an **Amended** line, carried down to every affected Pending story. A Complete story is never rewritten; a new one is added. Every **Pivot deferred** line pointing at a file it amends is resolved and removed.
  • Conflicts between documents, or between documents and code, are reported with both sources cited.

The run ends with three headings: Needs you (open decisions and the assumptions most worth checking), Written (each path, one line each) and Next (normally /cpm-next:do {first epic}, or /cpm-next:do all {spec} when the spec's epics are ready to run unattended, with /cpm-next:review {epic} first when an epic is large, touches unfamiliar code, or is about to run unattended). It then takes you through each Needs you item one at a time, as described under Finishing a run, and amends the document it concerns before raising the next.

/cpm-next:plan a CSV export for the loans report
/cpm-next:plan docs/discussions/05-discussion-export-queueing.md
/cpm-next:plan just the brief
/cpm-next:plan up to spec

/cpm-next:plan

With no argument it picks the most recent unconcluded discussion or the most recent spec without epics, and says which.

5do in depth

The epic doc is do's task list. It is what you read to see where the run is, what survives context compaction, and what the next session resumes from, so do keeps it current as it goes.

Before the first story

  • Restores a stopped red pass, before anything else, in every run: any pass directory left in .git/cpm-next/scratch/ for this checkout has its files copied back and is deleted, whatever its story (see Red passes).
  • Reads CLAUDE.md, docs/library/, the epic, its source spec and any ADRs it cites, and the library lessons, recurring signals and unretired legacy retro observations about this area.
  • Finds the test command and runs the full suite to record a baseline before changing anything. A full-suite result already in the conversation stands while git status and git diff show nothing changed since.
  • Probes for browser checks. When the scope holds a [browser] criterion and the repo has no browser test tool that runs in the session, it lists the browsers connected through claude-in-chrome and checks that the app answers at a local APP_URL (localhost, 127.0.0.1 or a .test host), and whether the page lands on a login. If it can't check, it says what is missing and how to fix it in its first message after the probe; with you present it asks once, before building, whether to fix it first.
  • Resumes honestly. A story left In Progress by an earlier session may be partly done, so the code is checked before anything is redone or skipped. A story marked blocked is not resumed until you settle the blocker; it is listed under Needs you. If every criterion of a story already has an Evidence line, do confirms the evidence still holds, takes a red pass for any test-proven criterion without a red, audits it if it has no **Audit** line, and closes it before picking any other work.

The loop

For each unblocked story, lowest number first. A story counts as unblocked only when every story in its **Blocked by** is Complete with an **Audit** line, since fixes from that audit would rework code built on top of it, and every epic its epic's **Blocked by** names is Complete.

  1. Start. The story (and the epic, if it was Pending) is set to In Progress. With cpm-next-models installed, do calls the mod's set_story_effort tool with the story's **Effort** (medium when it has none) and its number. Without the mod it builds at the session's effort.
  2. Build, task by task. Each task is set In Progress when started and Complete when done. The project's existing conventions take precedence. In a Laravel project the laravel-simplifier agent, if available, runs over the story's changes before verification, so the evidence is gathered against the final code.
  3. Verify every acceptance criterion with the tests its tag names, or with the check and what was observed, in an Evidence line under that criterion. A [browser] criterion uses the repo's browser test tool, or claude-in-chrome driven by the lead; a [user] criterion, or one that can't be carried out in the session, waits on you (see Stories waiting on you).
  4. Check as the auditor will, in this order: feed the new code inputs it doesn't expect (empty, missing, null, non-numeric, boundary) and read every help text, doc and Evidence line the story touched against the code; run the full suite until a run needs no fix; then take the story's reds in one red pass.
  5. Audit the story before closing it (below).
  6. Close the story in the same edit that writes its **Audit** line: remaining tasks and the story's **Status** go to Complete, and the epic too if this was its last open story.

Before starting the next story, do re-reads the one it just finished. It must read Complete with an **Audit** line, be marked blocked (its status kept, with the — blocked: {reason} note and a Not met line under any unmet criterion), or wait on you. An evidenced story left In Progress blocks every story that depends on it.

Evidence

Evidence sits on an indented line directly under the criterion it proves, never in a separate block, so each proof sits beside its claim. Its forms:

- {criterion} `[tag]`
  - Evidence: {test name, file:line}{ ({command})} — red: {message} with {lines undone in {file:lines} | mutation of {file:line}: {change}}
- {criterion} `[tag]`
  - Evidence: {proof} — red: n/a — {manual | browser-observed | static | existing (reaches {file:line})}
- {criterion} `[user]`
  - Evidence (user, {YYYY-MM-DD}): {what the user reported} — red: n/a — user
- {criterion} `[tag]`
  - Not met: {what was tried and why it fell short}
- {criterion} `[tag]`
  - Waiting on user: {the steps the user carries out}
  • The red shows the cited test can fail. {message} is the first line of the failure message (for a multi-line diff, the first line naming the expected and actual values). The failure must come from the cited assertion: an error such as a missing class, method, route or table doesn't count, though a stub returning a wrong value does. The command is left out when it is the project's test command run on the named test.
  • n/a reasons fit particular tags: manual a [manual] criterion; static one proven by reading code or by grep with no test; browser-observed a [browser] criterion checked with claude-in-chrome (the local URL, the steps and a page excerpt); user only the Evidence (user, …) form, written from your own answer.
  • existing fits a criterion that keeps behaviour the code already had, names no control, and is proved by a test whose body is unchanged and that passed at baseline; {file:line} is a line the story changed that the test executes. A criterion for new behaviour, or one naming a control, always takes a red.
  • A Not met line leaves the story marked blocked. A - Waiting on user: line marks a criterion do treats as [user], and is removed when its Evidence line is written.

Red passes

A story's reds are all taken in one pass, after its full-suite run and fixes, once no edit to its files remains to be made. A story with no test-proven criterion, or only existing ones, takes no pass.

  1. A new pass directory is made at {git common dir}/cpm-next/scratch/{epic file stem}-{story}/ (quick-{nn}/ for a small change), and its path goes in a **Scratch** line under the story. The directory holds a manifest of every changed or untracked path with its blob hash, and a tree file naming the checkout.
  2. Each file the pass will change is copied into the directory, once, before its first mutation.
  3. For each red, the lines the cited test covers are undone and only that test is run. Where that leaves it green or makes it error, the file is copied back and a covered line is mutated instead. The failure text and the undone lines or mutation are noted, and the file is copied back from the directory, never reverted with git checkout, git stash or reset, which would take uncommitted work with them.
  4. After the last red the manifest is computed again. On a match every file came back: the directory and the **Scratch** line are removed, the reds are written into the Evidence lines, and the full-suite result from before the pass stands for the audit, so no test is re-run green.
  5. On a mismatch, every path with a copy is copied back and the manifest compared again. A new untracked path is test output, named under Found. Any difference that remains marks the story blocked, with the paths, under Needs you.

Because the directory lives in the repository's git directory rather than the session's scratchpad, a pass interrupted by a crash or a closed session is found by the next run, which restores it before anything else. Every worktree of the repository shares it.

The commit guard

While a pass is open its source files are mutated, and a git add -A would commit them. The cpm-next plugin's hooks module therefore refuses a git commit run through the Bash tool, by the session or a subagent, while a directory under {git common dir}/cpm-next/scratch/ has a tree file naming the session's checkout. The refusal names each open pass; resume /cpm-next:do on that story, or copy the directory's files back to their repository paths, then commit. Commands that are not a git commit pass straight through, and if the guard can't read the directory it lets the commit through.

The audit and fix pass

do builds on Sonnet; the auditor agent checks each story on Opus before it closes. It is started with the Agent tool (subagent_type cpm-next:auditor), one auditor per story, and given the epic path and story number (or the docs/quick/ record), the files changed (or a worktree story's merge commit), the test command and the result of the full-suite run after the story's last change, that the red pass ended with a matching manifest, the contract's path, its own scratch directory, whether the suite is isolated or free, and the resources it must leave alone. It receives none of the conversation, so it checks what is on disk rather than what the builder says is there.

The full-suite result already ran every test the Evidence lines cite, so the auditor reads the tests and their recorded reds rather than re-running them. It runs tests or probes only when the suite is isolated (every test process gets its own database and its own copy of every file tests write, and no test binds a fixed port) or free (the lead waits for this audit in the foreground and runs nothing else that uses the suite until it reports).

The auditor checks:

  1. Each criterion against its evidence. Evidence citing a test that doesn't exercise the criterion, passes for an unrelated reason or doesn't exist is a finding, as is a criterion met only for the happy path when its wording covers more. A [user] criterion's evidence not in the Evidence (user, …) form is Critical; a [browser] criterion with neither a test and its red nor a browser-observed record is a Warning.
  2. The diff for defects: wrong logic, unhandled error states, off-by-one and boundary mistakes, security problems, data loss, race conditions, and queries whose memory grows with the data they read.
  3. Scope: changes the story didn't ask for, and anything it asked for that the diff lacks.
  4. Conventions: departures from the project's patterns, CLAUDE.md and docs/library/.
  5. Tests: whether each would fail if the code were wrong. A missing red, a red from another test, failure text showing an error or not what the cited assertion would print, an undo the assertion doesn't depend on, a misused existing reason, or a missing statement that the pass ended with a matching manifest is a Warning; an n/a reason that doesn't fit its criterion's tag is Critical. So is a test that asserts nothing meaningful, mocks the thing under test, or was weakened, skipped or deleted.
  6. Inputs the code doesn't expect: empty, missing, null, non-numeric, NaN and boundary values.
  7. Words against the code: help text, error messages, docs and Evidence lines the story touched.
  8. The full suite: a failing test the story's change explains.

It reports:

Verdict: pass | fix needed
- [Critical|Warning|Suggestion] {file:line or criterion}: {what is wrong, and the evidence that shows it}

The verdict is fix needed when there is any Critical or Warning finding. Severity weighs how likely the failure is as well as how bad: from normal use it follows the harm; from unusual use (a double click, two tabs, the back button mid-submit, a request cut off) it is a Warning at most; from an input no caller can produce today it is a Suggestion at most. Security findings, and data lost, corrupted or duplicated, keep their severity on any path.

What do does with it:

  • Checks each finding against the code and drops any that don't hold up. A finding that holds gets a **Signal** (see Signals and recurrence).
  • On fix needed: raises the effort for the fix with set_story_effort (high, or xhigh for a story already at high), fixes every Critical and Warning finding wherever the same mistake occurs, gives each fix a test with its red, updates the Evidence lines the fixes affect, runs the full suite again, and audits once more.
  • A later audit is scoped: it gets the earlier findings, which were dismissed and why, and the files the fixes changed, but no description of the fixes. It checks each finding is resolved everywhere and audits the fix code as new code; outside the fixes it reports only a Critical, marked missed earlier.
  • If the second audit returns a Critical, do fixes it and audits a third time, scoped the same way. There is never a fourth.
  • If the last audit still returns fix needed: each unresolved finding goes into a Not met line under the criterion it concerns, or a signal when it concerns none, and the story is marked blocked.
  • Suggestions are neither fixed nor recorded.
  • A finding that contradicts the story's criterion rather than the code is a criterion question, handled as in When a criterion looks wrong.
  • The result is recorded as **Audit**: pass ({date}), adding , {n} findings fixed when the first audit returned fix needed. If the auditor agent isn't available: **Audit**: skipped — auditor unavailable, reported under Found at the end of the run.

A small change with no epic is audited the same way, against the criteria and Evidence lines in its docs/quick/ record, which also holds the verdict.

Each audit round gets a fresh scratch directory under the run's directory in the session scratchpad, passed by absolute path, so no two auditors share one. Audits of stories that share no files may run in parallel.

Parallel subagents

Stories that are unblocked together are built in parallel by default, one subagent each, when they share neither files nor runtime state. do judges overlap from the files each story's tasks name and the code they touch, and asks the scout agent where that isn't clear. It builds them one at a time when they overlap, or when you are working alongside it on a single story or task. Shared runtime state includes databases, migrations, dependency installs and lock files, cache and queue state, storage directories, .env, and ports.

  • The lead agent owns everything shared. It runs migrations, dependency installs and the full test suite. A story needing a schema or dependency change goes first, run by the lead, before any fan-out.
  • A subagent runs only its own story's tests, and only when the suite is isolated (every test process, even a single run, gets its own database and its own copy of every file tests write, and no test binds a fixed port; do checks this once per run). Otherwise the subagent writes code only and the lead runs its tests after it reports.
  • A subagent leaves [browser] criteria to the lead, who checks them after the batch.
  • Each subagent's prompt names the resources it must leave alone.
  • Parallel subagents start on sonnet, the model do builds on.
  • After a parallel batch the lead runs the full suite once, since conflicts between stories show only when the pieces are combined.
  • Once the batch has finished and nothing else is running, the lead hands each story's red pass to a fresh sonnet subagent, one at a time, so the red tool calls stay out of its own context. It creates the pass directory first, then compares the manifest, removes the directory and writes the Evidence lines itself. No pass runs while batch siblings run, since a sibling's tests would run the code a red has mutated.
  • The lead checks each report against the files and test output before the story goes to audit, and makes every audit fix in its own checkout.
  • Two full-suite runs, or a full-suite run and a red pass, never overlap in one checkout.
  • A story isn't finished while a subagent or background command it started is still running.

Worktree mode (--parallel)

Stories that share files are built one at a time, unless you ask for --parallel. With it, unblocked stories are built together even when they share files, each subagent in its own git worktree, and the lead merges the branches in story order with git merge --no-ff, so each story's audit reads one merge commit. The flag is never needed for stories that share nothing; do already builds those in parallel.

  • Worktrees isolate files, not the running app, so stories that depend on another in the batch, change a lock file, .env or shared config, migrate a table another story uses, or need the running app (a [browser] criterion, a real webhook or third-party call) still run one at a time, after the batch. At most three run at once.
  • A worktree's test results count only when the suite is isolated, outbound HTTP, queues and mail are faked, and no build output the checkout lacks is needed; otherwise the subagents write code only and the lead runs each story's tests and red pass after merging. Where results count, each subagent takes its own story's red pass before committing.
  • Asking for --parallel is your leave for do to commit and merge locally on the current branch, never to push. If the tree holds changes the run didn't make, it doesn't use worktree mode and builds one at a time.
  • --parallel check builds and writes nothing: it reports the batches worktree mode would form, why any story stays out, whether the suite is isolated (citing the config lines), and the setup each worktree would need.
  • Without the flag, when unblocked stories that share files are waiting, do makes the same check; if a batch qualifies it names the stories, what they share and /cpm-next:do {scope} --parallel in one line (repeated under Found), and carries on one at a time.

Haiku stories and scout lookups

A story marked **Model**: haiku goes to a subagent on haiku even when nothing runs beside it, so the lead keeps its own model and the conversation's cache. The lead makes any fixes the audit asks for.

Plain lookups (where something is defined or used, which files a change touches, what a read-only query returns) go to the cpm-next:scout agent on Haiku, which returns only the answer and keeps search output out of the main conversation. When the answer depends on understanding the code rather than finding it, do reads the code itself.

Stop rules

A message without a tool call ends the turn, and work stops until someone replies. While stories in scope remain open, do does not end a turn with:

  1. a progress summary that announces the next step without taking it;
  2. an offer to carry on unless you would prefer otherwise;
  3. a list of decisions for you when none of them blocks the remaining work;
  4. a report because a story finished or the turn has run long.

Status notes and recommendations go in the same message as the next tool call. It stops and asks only when:

  • a test fails for a reason it can't explain after investigating;
  • an acceptance criterion contradicts reality and resolving it would change scope;
  • the next action is destructive or reaches outside the repository: deleting data, rewriting history, touching shared infrastructure.

While stories remain, it carries on with whatever doesn't depend on an answer, and keeps what waits on you for Needs you.

Unattended all runs and blocked stories

In an all run (with or without a spec: all 04 covers only spec 04's epics), or whenever you have said you won't be watching, do does not stop for the first two reasons above. It marks the story blocked with the reason (and a signal) and moves on to other unblocked work. The third reason, a destructive action or one outside the repository, always stops the run.

With cpm-next-models installed, an all run, spec-scoped or not, is held at high effort, and no story in it is built below high, because Sonnet tends to stop and check in during long runs at medium. See section 6.

A blocked story keeps its status with the note — blocked: {reason}, and a Not met line under any criterion concerned. do neither picks nor resumes it, and every story that depends on it stays blocked. Blocked stories, **Pivot deferred** items and anything held back appear under Needs you at the end of the run, and /cpm-next:status lists them under the same heading.

Stories waiting on you

A [user] criterion, and any criterion do can't carry out in the session whatever its tag (a deploy, a production run, a sign-off, a browser check with no browser or app to check against), is never claimed as met. do lists its steps under Needs you, and a criterion not tagged [user] gets a - Waiting on user: {steps} line so that tools can tell. Its Evidence line is written only from your own answer, never in a run with no user present.

A story whose only unproven criteria are of this kind waits on you: do skips it and counts it as done for the run's finish line, so the rest of the work carries on. /next lists it under Waiting on you rather than offering it as next, and the progress tracker shows it as Waiting on input. When you answer, do writes the evidence and, once every criterion has some, takes the story's red pass, audits it and closes it. Because plan puts a spec's [user] criteria in one final user-checks epic, nothing else waits for them.

Signals and recurrence

Learning starts where a failure happens, not when an epic ends. do writes a **Signal** (format under Signals) on the story, or in the docs/quick/ record, whenever an audit finding holds, a story is marked blocked, or it writes an **Amended**, **Inline change** or **Pivot deferred** line: one per class per story, reusing an existing slug where one fits.

After writing each signal it checks whether the failure has happened before: a library lesson with that **Class**, a signal with that slug in a different epic or quick record (the archive included), or an unretired legacy retro observation. It reads both to confirm, and on a match appends — recurs: {reference} ({why it matches}).

  • A recurring project signal with no library lesson becomes a promotion candidate under Needs you, raised once, with the matching signals and the constraint proposed. A yes writes an entry in docs/library/lessons-learned.md and marks the signals — promoted; a no marks them — declined, and a later match is declined too.
  • A process signal (a cpm-next rule could have prevented it) ends with — cpm-next {version}, read from the installed plugin's .claude-plugin/plugin.json; a project signal carries no version. A process signal, and a signal recurring against an existing library lesson, go under Found only. /cpm-next:library sweep gathers process signals across repositories.
  • A signal that never recurs is never reported or asked about.

When a criterion looks wrong

A criterion that is hard to meet is not a criterion that is wrong. "The tests fail", "this approach didn't work" and "it's slower than the target" are reports about the implementation and never justify changing the criterion. The criterion stands, the story is marked blocked, and a Not met line records what was tried, with a signal.

A criterion is wrong only when something can be cited that contradicts it: a file:line, a named requirement in the spec (FR3, AD1), or another criterion in the same epic that can't be satisfied at the same time. Then:

SituationWhat do does
Wording fix, no change of scopeEdits the criterion and adds an **Inline change** line, with a signal
Change of scope, you are presentAsks you, showing the citation
Change of scope, unattended runAmends the criterion in this epic only, with an **Amended** line carrying the citation, and adds a **Pivot deferred** line for each upstream document that now disagrees. The spec and every other document are left untouched; plan resolves them later with you.

Finishing a run

Every run ends with three headings, in this order:

  • Needs you: only what won't happen unless you act, each line naming the action and what it unblocks: decisions only you can make, blocked stories and what would unblock them, **Pivot deferred** items (each with /cpm-next:plan {path}), promotion candidates, the steps of each [user] criterion of a story waiting on you, anything destructive held back, and steps outside the repository such as a migration on a deployed database, a secret or a service restart. Optional follow-ups and things already done stay out. "Nothing" if so.
  • Changed: stories completed, the main files touched, and the test result against the baseline.
  • Found: anything surprising about the codebase, the plan or the tests. Nothing here asks you to act.

The run then takes you through the Needs you items one at a time, the one blocking most work first. For each it says what the item is and where, what each way of settling it leads to, and what it recommends and why, then asks a single AskUserQuestion with the recommendation as the first option and Leave it for now as the last. It acts on your answer before raising the next: amending a criterion you changed (and clearing its Not met line and blocked note), carrying out an approved step, writing a lesson you accepted, recording a [user] result you report. Browser checks that fell back to you are one question: fix the environment so do runs them all, or report the results yourself. An item left for now stays recorded where it is. Once the last item is settled, do builds what the answers unblocked and ends with the three headings again.

plan and review walk through their own Needs you lists the same way. status writes nothing, so it gives each item a recommendation and leaves the walk-through to the skill that settles it.

What cpm-next-models does

A skill's model and effort frontmatter normally lasts only for the turn that invoked it. Without the mod, later turns of a run (including your replies to the skill's questions, and the turns that continue a do run) fall back to the session model.

With cpm-next-models installed:

  • When a cpm-next skill starts, typed as a slash command or invoked through the Skill tool, the mod reads the model and effort lines from the installed skill's SKILL.md and holds them for every later turn of the run.
  • A bare family name in the frontmatter (sonnet) takes the session model's version.
  • Only the main conversation is affected. Subagents keep the model and effort they were started with.
  • The footer shows what is held as one of its mode labels, for example cpm-next:do · story 3 · sonnet · low.

The hold ends when:

  • another skill runs: a different cpm-next skill replaces the hold with its own frontmatter, and a skill from outside cpm-next releases it;
  • you switch model yourself (/model or the model picker); a fallback or resume does not count;
  • you run /clear;
  • you run /cpm-models off.

Running /effort during a run releases only the held effort: your effort applies from then on, and the held model stays.

The mod works under Claude Code's built-in sec-default mod, which keeps some events from user-installed plugins: it reads skills from the typed prompt and the Skill tool, and a typed built-in such as /cost leaves the hold alone.

Per-story effort

The mod gives do a tool, set_story_effort, which takes an effort of low, medium, high or xhigh and an optional story number. do calls it as each story starts, with the story's **Effort** (or medium), and again to raise the effort for a fix after a failed audit. The tool:

  • changes nothing outside a do run, and replies that the session effort applies;
  • leaves an effort you set with /effort alone, and replies that your effort applies;
  • never goes below the run's floor; when it raises a request it says so, for example "Effort high (raised from low: this run's floor is high) for story 3."

The model stays Sonnet throughout, so the prompt cache survives a change of effort.

The do all floor

When /cpm-next:do all or /cpm-next:do all {spec} starts (the mod tests for a leading all), it holds high effort instead of the frontmatter's medium, and sets high as the floor for the run, so a low story cannot bring the effort back down. do all stays on Sonnet; the per-story Opus audit covers the quality risk, and high effort covers Sonnet stopping early.

A greenfield plan that needs more thought, or a subtle party discussion that would benefit from Opus, is a /effort or /model away.

7Progress

Three ways to see where the work stands: a shareable claude.ai tracker page (cpm-next-progress), a live pane in the terminal (whats-next), and a one-screen report on request (/cpm-next:status). All three read the same epic docs.

/progress-tracker

The cpm-next-progress mod keeps a private claude.ai artifact showing a spec's stories as a table in build order, grouped by phase. Status, titles and outstanding blockers come from the epic docs; the order, phase labels, notes and open decisions come from a build-order file you can edit. Each check also saves the tracker's counts to the mod's own store, which feeds an overview of every project. A project that keeps its CPM documents under docs/cpm/ (with no docs/specifications/) is read from there.

Setting one up

  1. Plan the spec's epics first; they must exist in docs/epics/.
  2. Run /progress-tracker 01 (the spec's number; a spec file or a build-order file also works, and init before the name still works). The mod writes docs/specifications/01-build-order.json from the spec's epics if it doesn't exist yet, writes the page to .claude/cpm-next-progress/01-build-order.html, and adds /.claude/cpm-next-progress to the project's .gitignore. For a spec that already has a tracker, it rewrites the page from the current template and republishes it to the same link, keeping the rows.
  3. The mod then submits a prompt asking Claude to publish the page. Asking in words ("publish the progress tracker") works too: Claude has a publish_tracker tool that does the same, so you get the plugin's page rather than one written by hand.
  4. When Claude publishes it, the mod saves the link into the build-order file's artifact field and gives Claude the first rows to write.

The build-order file

docs/specifications/NN-build-order.json:

{
  "title": "01-Series Build Order",
  "spec": "docs/specifications/01-spec-requirements-matrix-todos.md",
  "decisions": ["Questions still open, shown in a box above the table"],
  "phases": [
    { "label": "No visible change", "items": [
      { "epic": "01-05", "story": 1, "note": "Default value keeps today's text" },
      { "epic": "01-05", "task": "3.1" }
    ] },
    { "label": "Waiting on input", "note": "Shown beside the phase label", "items": [
      { "epic": "01-05", "story": 2, "waitingOn": "new name from the client" }
    ] }
  ]
}
  • A file needs a title string and a phases array.
  • An item is a story (story) or one task (task) of an epic, named by the epic's number prefix (01-05).
  • note on an item is shown in its row; note on a phase is shown beside the phase label.
  • waitingOn shows the item as Waiting on input until it is removed from the file.
  • artifact holds the tracker's link. The mod adds it when Claude publishes the page, and refuses anything other than a claude.ai artifact link.
  • Items naming an epic, story or task that doesn't exist are skipped and reported as "not found in the epics".

The first build order is written from the spec's epics (those whose number starts with the spec's): one phase per epic, epics ordered by their **Blocked by** epics, each epic's stories ordered by their **Blocked by** stories and then by number. Superseded and withdrawn epics and stories are left out. Edit the file afterwards to reorder, regroup, split a story into tasks or add waitingOn. Epics planned with no spec (00-01 and so on) get a tracker too: /progress-tracker 00 writes docs/specifications/00-build-order.json from the 00- epics.

What a row shows

  • Status: Complete; Waiting on input (a waitingOn item, or a story waiting on you, whether Pending or In Progress); In progress (the story says so, or one of its tasks has started); Pending. The page shows a Pending row with no blockers as Ready; the stored status stays Pending.
  • Blocked by: the story's and epic's **Blocked by** items not yet Complete (archived epics count), earlier unfinished tasks of the same story, and any waitingOn. Empty once the item is Complete.
  • Date: moves only when the row's status changes.
  • Time in: for a story in progress, how long it has run, and the typical range once the project's timings are steady (see Overview and timings).

Data layout in the artifact's database: collection items, one document per row (01-05-s1 for a story, 01-05-t3.1 for a task), a timed story in progress carrying started and, when steady, typical; document meta/tracker with the title, spec, last update and decisions. Anyone the artifact is shared with can read it; editors can write.

How rows sync

  1. After any tool call that writes (Edit, Write, MultiEdit, NotebookEdit, Bash), the mod checks whether an epic doc or build-order file changed since the last check. If none did, it does nothing more. It also checks when a session starts.
  2. If one did, it reads the tracker through ArtifactData and works out the writes that would bring it in line. If there are none, it says nothing.
  3. If there are some, it saves them to .claude/cpm-next-progress/NN-build-order.pending.json as ready-made batches of at most 50, shows a one-line notice, and gives Claude a note with the artifact link and the writes.
  4. Claude applies up to eight writes itself with one ArtifactData batch.
  5. Large updates: more than eight writes stay in the pending file, and Claude hands them to a Haiku subagent, which reads the file and applies each batch, so the writes never enter the main conversation.
  6. When Claude's turn ends with a tracker still behind, the mod submits a prompt of its own asking for the same writes. After two such prompts in a row it stops and shows you a notice instead.

A tracker whose rows are all Complete and in step, or whose artifact you deleted, is settled: later checks skip it until its build-order file changes, though a bare /progress-tracker still checks it. A deleted tracker is reported once; /progress-tracker 01 removes the dead link and publishes a new one.

The mod only reads. It lists the artifact's rows through ArtifactData, which auto mode does not ask about, and never writes to the artifact. Claude's own ArtifactData calls do the writing, so no permission rule is needed.

Commands

/progress-tracker            # check every tracker in the repository now; prints what differs, or "up to date"
/progress-tracker 01         # prepare spec 01's tracker (build-order file, page, .gitignore) and ask Claude to publish it
/progress-tracker 01-build-order.json
/progress-tracker init 01
/progress-tracker all        # pane of every project's trackers; add "finished" to list finished ones too
/progress-tracker all publish  # the same overview as a claude.ai page
/progress-tracker times      # how long this project's stories have taken, and time left for those in progress

Overview and timings

  • /progress-tracker all opens a pane with one row per tracker in every project, grouped by project, those with work left first: the title, a bar, done of total, and the stories in progress. It reads only the mod's own store, so a project appears once a session there has run a check.
  • /progress-tracker all publish writes the same overview as a claude.ai page, a card per project with a row per tracker linked to it, and keeps it in step as the trackers change. Its rows carry each project's folder name, never its path.
  • Story timings: each check that sees a story move from Pending to In Progress, and later to Complete, records the time. Once a project has 10 timed stories, /progress-tracker times gives the median and middle half of their times, overall and per **Effort**, and roughly how long is left for each story in progress, while the times are steady enough to predict. Claude's story_times tool answers "how long until story 5 is done?" the same way.

/next (whats-next)

The whats-next mod reads docs/epics/ and docs/specifications/ in the repository the session runs in, or the nearest folder above it that has either (up to the repository's top, never the home folder; docs/cpm/ is read in projects that keep their CPM documents there), and shows every story not yet Complete in the order to build them, the stories waiting on you apart from them, and every spec no epic has been planned from yet. It reads the files directly, with no model calls, so it stays current as do or you edit the epics.

  • Pane: the story in progress and its next task, every remaining story in order (doing, ready, or after Story 1 / after Epic …, with (your check) after a dependency that is a story waiting on you), a Waiting on you block listing each story only you can finish with each criterion still unproven, and each open epic's story count. It opens by itself in a repository with work left when the terminal is at least 144 columns wide; /next opens it at any width and prints the ordered list into the conversation.
  • Specs without epics: each spec no epic was planned from, in number order. A spec counts as planned when an epic is numbered after it (03-spec-… → 03-01-epic-…) or an epic names its file in **Source spec**. Specs with their own **Status** of Complete, Superseded or Withdrawn, and withdrawal notices, are left out.
  • Band: one line above the prompt with the next story, its next task and how many stories are left; with nothing left to build, the first story waiting on you (Waiting on you … (n waiting · /next)), and with none of those, the first spec to plan.
  • Next steps: an Ask Claude button (hotkey a) that asks Sonnet for a short note on what to do next. The note is kept per repository across sessions and dimmed once the epics change after it was written; with nothing left to build it asks what to do about the stories waiting on you.

Order of execution: stories waiting on you are not work to build, so they leave the order and are never offered as next. Of the rest, stories already In Progress first; then the other stories of epics under way; then everything else. Within each group, repeatedly, the ready story with the lowest epic number and story number. A story is ready when everything its own and its epic's **Blocked by** name is Complete; epics in docs/archive/epics/ count when resolving dependencies. Stories whose dependencies can never be met (an unknown epic, a cycle), and stories that depend on a story waiting on your check, are listed last.

/cpm-next:status

The read-only report described under status. Use it when you want an explanation rather than a list: what has been built, what is in flight, what is waiting on you with paths (blocked stories, user checks, promotion candidates, pivots), suspect records, and the commands to run next. It is also the fallback when neither mod is installed.

8Day-to-day practice

Greenfield

With no code and no documents, start from an idea:

/cpm-next:party a reading-room reservation system for Starling Library      # optional: hear the trade-offs first
/cpm-next:plan docs/discussions/01-discussion-reading-rooms.md
/cpm-next:review                                         # optional, for a large or risky epic
/cpm-next:do all 01

plan writes a brief when the problem, users or value aren't written down anywhere, then the spec, then the epics. In a greenfield project it has no code to ground requirements in, so its Assumptions section carries more of the decisions; read it before running do.

Brownfield

In an existing codebase, plan reads the code before asking anything: the stack, conventions, the modules the work touches, the test setup and test command. Every spec requirement names the existing models, routes or components it extends. A small, well-understood change can skip the brief and spec and go straight to a 00- epic, or need no epic at all:

/cpm-next:plan a CSV export for the loans report        # brief or spec only if needed, then epics
/cpm-next:do add a "last exported" column to the loans table   # small change, no epic: docs/quick/ record with criteria first

Existing planning material (a PRD.md, a README, issue text, a CPM v3 spec) is adopted rather than regenerated. Foreign task lists that do needs to run are converted into the epic format.

Re-planning when direction changes

  • Run /cpm-next:plan with the change described. It amends the existing brief, spec or epic in place with an **Amended** line and carries the change down to every affected Pending story in the same pass.
  • Complete stories are never rewritten; new work becomes a new story.
  • Any **Pivot deferred** lines left by an unattended do run, pointing at a file plan amends, are resolved and removed. /cpm-next:status lists outstanding ones under Needs you.
  • After a pivot, /cpm-next:review is worth running before the next build.
  • Marking an epic Superseded or Withdrawn is your decision; the skills never set those values. Such an epic never satisfies a dependency.

Library documents

Every skill reads docs/library/. Put there whatever should constrain planning and building: coding standards, architecture notes, API contracts, domain glossaries.

  • Import with /cpm-next:library {path or URL} so the document gets front-matter whose summary states its rules.
  • If you add documents by hand, run /cpm-next:library consolidate to back-fill their front-matter.
  • Lessons arrive on their own: do raises a recurring failure as a promotion candidate, and your yes writes it to lessons-learned.md. Run /cpm-next:library learn to promote recurring signals in a batch, and once on any legacy retros, to promote or retire their observations.
  • If you run cpm-next in several repositories, list them with /cpm-next:library sweep add {path} and run /cpm-next:library sweep now and then to find process failures seen in two or more; in the plugin's own repository it can write a discussion record for /cpm-next:plan, and anywhere else it offers an issue draft you read and file only on your yes.
  • When a document has collected several amendment blocks, /cpm-next:library consolidate {path} folds them into a clean version, after your approval.

Habits that help

  • Run /cpm-next:status when you come back to a project, or watch the /next pane.
  • Read the Needs you and Assumptions sections; they are where the skills put what is yours to decide.
  • Commit when you choose to: do leaves commits, branches and pushes to you unless you've said otherwise (or you asked for --parallel). A commit made through Claude while a red pass is open is refused until the pass is finished.
  • When you edit an epic by hand, keep to the contract's format so the mods and skills can still read it.
  • Answer the Needs you walk-through rather than leaving items for later: a user check you report, or a candidate lesson you accept, is acted on straight away.
  • Keep [user] steps concrete (exact steps and the observation that proves them), so you can carry them out and report the result in one go.

9Troubleshooting and FAQ

"cpm-next@claude-code-marketplace" doesn't install.

The suffix is the marketplace's name, ninthspace-marketplace, not the repository's: /plugin install cpm-next@ninthspace-marketplace.

I installed a mod but nothing happens in my open session.

A session open before the install needs /reload-plugins to load the mod. This includes plugin-sync itself; after that one manual reload it reloads the session on later updates.

Later turns of a do run are on my session model, not Sonnet.

Frontmatter model and effort last only for the turn that invoked the skill. Install cpm-next-models to hold them for the whole run. If it is installed, check whether the hold was released: a model switch of your own, /clear, /cpm-models off, or a skill from outside cpm-next all release it. /cpm-models shows what is held.

I set /effort during a run and stories no longer change effort.

That is intended: your /effort wins for the rest of the run, and set_story_effort leaves it alone. Start the skill again to go back to per-story effort.

A story marked **Effort**: low was built at high.

In a do all run with cpm-next-models, no story goes below high. The tool's reply says "raised from low: this run's floor is high".

A story's **Audit** line says "skipped — auditor unavailable".

do could not start the cpm-next:auditor agent. It is shipped with the cpm-next plugin; check the plugin is installed and loaded (/reload-plugins). The run reports the skip under Found.

A story is blocked with a Not met line. What now?

Read the Not met line and the — blocked: note on its status: they record what was tried and why it fell short. do won't pick or resume the story until you settle it, and its Needs you walk-through asks you about it with a recommendation. Either the implementation needs another attempt (a fix or a decision from you), or the criterion itself is wrong, which needs a citation and, if it changes scope, your decision; do then amends it, clears the line and the note, and resumes the story. do never treats "hard to meet" as "wrong".

Dependent stories won't start even though the earlier story has evidence.

A dependent starts only when the story it waits on is Complete with an **Audit** line. An evidenced story left In Progress, or one not yet audited, blocks everything that depends on it. On resume, do confirms, audits and closes such a story before any other work; running /cpm-next:do on the epic fixes it. /cpm-next:status reports inconsistent records as suspect.

git commit is refused: "A red pass is open in this checkout".

A red pass mutates source files while it runs, and a stopped one leaves them mutated. Resume /cpm-next:do on the story the refusal names, which restores the files before anything else, or copy the files in the named directory under .git/cpm-next/scratch/ back to their repository paths and delete the directory. Then commit.

A story isn't being built, and /next lists it under "Waiting on you".

Its only unproven criteria are ones only you can prove: [user] criteria, or ones with a - Waiting on user: line. Carry out the steps listed (in /cpm-next:status or do's Needs you) and run /cpm-next:do {epic} to report the result; do writes the evidence from your answer, then audits and closes the story.

do says it can't check the browser criteria.

Without a browser test tool in the repo, do needs a browser connected through claude-in-chrome, the app already answering at a local APP_URL (localhost, 127.0.0.1 or .test), and a login session in that browser where the page needs one. It starts no server and enters no credentials. Fix what it names and answer its question at the end of the run, and it runs every check that fell back; or report the results yourself.

Where did retros go?

No skill writes them. do records a signal where a failure happened and only a failure that recurs becomes a lesson, with your yes. Existing retros are still read; run /cpm-next:library learn once to promote or retire their observations, and /cpm-next:status counts those that remain. If your own instructions name "Retro" items, point them at promotion candidates and Found instead.

There are **Pivot deferred** lines in an epic.

An unattended do run amended a criterion with a citation and left the upstream documents for you. Run /cpm-next:plan; it resolves each breadcrumb pointing at a file it amends and removes it.

do stopped in an all run.

In an all run only a destructive action, or one that reaches outside the repository, stops the run. The Needs you heading names what was held back.

I typed "exit" in a party discussion and Claude Code closed.

"exit" and "quit" close Claude Code itself. Type wrap up (or "done") to finish a discussion. The record is updated every few exchanges, and a record left In progress is picked up by the next session.

/progress-tracker says "No stories in docs/epics/NN-*-epic-*.md yet".

The tracker is built from the spec's epics. Run /cpm-next:plan for the spec first.

/progress-tracker says "no tracker yet".

The build-order file has no artifact link. Run /progress-tracker {spec number} (or init {file}); the mod asks Claude to publish the page.

A tracker write was refused as stale.

Run /progress-tracker to check again; it works out the writes against the current versions of the rows.

Rows in the tracker are missing.

Items in the build-order file that name an epic, story or task that doesn't exist are skipped and reported as "not found in the epics". Check the epic prefix and the story or task number in the file.

The /next pane didn't open by itself.

It opens unasked only in a repository with work left and a terminal at least 144 columns wide. /next opens it at any width.

Can I use my CPM v3 documents?

Yes. cpm-next reads CPM v3 artefacts as input, including legacy flat epics, coverage matrices, story-level **Evidence** fields and retros. It writes new documents in its own format and does not convert documents that aren't going to change. Epics built under earlier cpm-next versions keep their old Evidence lines; nothing is rewritten or back-filled.

How do I change the personas?

Copy cpm-next/agents/roster.yaml to docs/agents/roster.yaml and edit it. The project copy replaces the default entirely. Each entry has name, displayName, icon, role, personality and communicationStyle.

Why does a number skip, or why was my file not renumbered?

Numbers count the archive too (docs/archive/{type}/), are never reused, and existing files are never renamed.
