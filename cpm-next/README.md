# cpm-next

Six skills that take work from an idea to tested code through Markdown artefacts in `docs/`. They replaced CPM's twenty-one skills, and read CPM v3 artefacts as input. CPM and DPM were withdrawn from the marketplace on 2026-10-08; installation and the companion mods are described in the marketplace README.

| Skill | Absorbs from v3 | Finish line |
|---|---|---|
| `/cpm-next:party` | party, consult | Record concluded, next step named |
| `/cpm-next:plan` | discover, brief, architect, spec, epics, pivot | Artefacts down to the target exist and trace upward |
| `/cpm-next:do` | do, ralph, quick | Stories in scope Complete, suite no worse than baseline |
| `/cpm-next:library` | library, retro learn and retire | Library documents carry complete front-matter; chosen lessons promoted and their signals or retro observations marked at source; `sweep` reports process failures found in two or more listed repositories |
| `/cpm-next:review` | review | Critical and Warning findings fixed in Pending stories or waiting on the user; review record written |
| `/cpm-next:status` | status | One-screen report and the next command; nothing written |

## How cpm-next learns

Learning has two levels. The plugin owns the mechanism and ships by version; each repository owns its own lessons.

**In a repository.** `do` writes a `**Signal**` on the story, or in the `docs/quick/` record, when an audit finding holds, a story is marked blocked, or an `**Amended**`, `**Inline change**` or `**Pivot deferred**` line is written. A signal has a class slug, says whether the cause is the `project` or the `process` (a cpm-next rule could have prevented it), and names the rule involved. A one-off is never promoted and never asked about. When a signal matches an earlier one in a different epic, a library lesson, or an unretired legacy retro observation, `do` marks it ` — recurs:`. A recurring `project` signal becomes a promotion candidate under **Needs you**, raised once: a yes writes an entry in `docs/library/lessons-learned.md` with a `**Class**`, a no marks it declined. `/cpm-next:library learn` promotes the same way in batches and from legacy retros. `plan` then reads library lessons, recurring signals and unretired legacy observations, writes them into criteria, and names them in the epic's `**Lessons**` line; `review` checks each.

**Across repositories.** A `process` signal goes under **Found** in the repository where it happened, since the fix is a change to a skill. `/cpm-next:library sweep` reads the `process` signals in the repositories listed at `~/.claude/cpm-next/repos.txt` (`sweep add`, `remove` and `list` keep it), groups them by the cpm-next file and step they name, and reports each group found in two or more. A `process` signal records the cpm-next version it was seen under, and the sweep leaves out a group that `shared/fixed.md` says a later release fixed. You decide whether a group becomes a plugin change. In the plugin's own repository, ask the sweep to write a discussion record, run `/cpm-next:plan` on it, and review and build the result as with any spec. Anywhere else the sweep offers an issue draft for the plugin's repository instead, with the class, the cpm-next file and step, a generic description, the versions and how many repositories showed it, and nothing from your projects; you read it, and it is filed with `gh issue create` only after your explicit yes. A shipped version reaches every repository on update. Nothing is promoted or changed without your answer.

Retros in `docs/retros/` are legacy: no skill writes one, and `status` counts the unretired observations until `library learn` retires them.

## What changed, and why

- **Outcomes over procedure.** Each skill states what "done" means and when to stop. How to get there is left to the model.
- **State lives in the artefacts.** The discussion record and the epic doc are the state. No progress files, stale-progress checks, compaction hooks or `/cpm:clean`.
- **plan works from inventory.** It takes stock of what exists, asks its questions in one batch, records its own decisions as Assumptions, and writes only what's missing. It covers greenfield and brownfield from any starting state.
- **do stops only when it has to.** Its stop rules follow the Opus 5.5 guidance: keep going when the user isn't needed, and stop for unexplained failures, scope changes and destructive actions. An unattended (`all`) run marks blocked stories instead of stopping.
- **Kept on purpose:** the "unmet isn't wrong" rule from the Change Type Decision, citation-backed amendments, and `**Pivot deferred**` breadcrumbs. This is the one failure mode that is known to be expensive.
- **Dropped:** coverage matrices (`**Satisfies**` carries the traceability), the retro disposition gate, template hints, and the `AskUserQuestion` handoff menus.

## Additions

- **library** (0.2.0): brought over from v3 so reference documents can be imported and consolidated without switching plugins. Same front-matter and amendment formats, now in `shared/artifacts.md`; progress files, the stale-progress check and per-step gates dropped.
- **Per-criterion evidence** (0.2.0): `do` now writes an `Evidence` (or `Not met`) line under each acceptance criterion instead of one story-level `**Evidence**` field. In practice the two blocks drifted apart, and a reader couldn't tell which proof backed which criterion, or whether any criterion had none.
- **library learn, review, status** (0.3.0): `learn` moves durable retro lessons into the library, since otherwise only v3 does it and `consolidate` has nothing to fold in. `review` gives the epics the independent challenge that `plan` gives the spec. `status` is a read-only reading of the artefacts, which are the only state. Retro and review formats and the `**Retired**` marker join the contract, matching v3 so its skills read them unchanged.
- **Prompt audit for Opus 5.5** (0.3.0): `/claude-api prompt-audit` over the skills removed `do`'s self-review of each story's diff and the "Time matters" lines in `do` and `plan`, since Opus 5.5 checks its own work and effort is the control for how long it thinks. It also removed phrasing that only made sense against v3 ("No gate, no dispositions", "Don't present a menu"), and replaced the fixed counts in `review` and `status` with descriptions of what to keep. The persona subagents in `plan` and `review` were flagged and kept, because independent reviewers are the point of those steps. Worth confirming by running one epic with and without the self-review.
- **calibrate** (0.4.0): recommends a model and effort level for an artefact, a skill or a described task, or for a whole set of them as a table, one row per item, with the skill each needs next. It advises rather than setting either, since a skill's `model` and `effort` frontmatter only lasts for the invoking turn and would pin a variable this experiment holds fixed.
- **review personas on Sonnet** (0.4.0): `review` starts its persona subagents on `sonnet`. A per-call model outranks `CLAUDE_CODE_SUBAGENT_MODEL`, so this is the one subagent choice the plugin makes for you; `plan` and `do` subagents follow that variable, or the session model when it's unset. When comparing runs, note that review cost now differs from a v3 review on the same model.
- **Stories close as they finish** (0.4.1): `do` was writing every `Evidence` line and leaving the story `In Progress` and its tasks `Pending`, which also left dependent stories blocked, because the unblocked rule reads only the status. The simplifier pass, which came between verifying and closing, moves ahead of verification. A story now closes in the same edit as its last `Evidence` line, and the epic closes with its last story. `do` re-reads the finished story before starting the next one. On resume, an evidenced story left `In Progress` is closed before any other work.
- **Sonnet builds, Opus plans and audits** (0.5.0): `do` declares `model: sonnet` and starts its parallel subagents on Sonnet; `plan` and `review` declare `model: opus`, and their subagents, including the review personas that 0.4.0 put on Sonnet, now start on Opus. Before closing each story, or a small change, `do` hands it to a new read-only `auditor` agent (`agents/auditor.md`, `model: opus`), which re-runs the cited tests and reads the diff for unmet criteria, defects, scope creep and convention breaches. `do` fixes Critical and Warning findings, audits once more, and records the result in a new `**Audit**` story field; a story that fails the second audit is blocked. This restores a per-story review that the 0.3.0 audit removed on the grounds that Opus checks its own work, which no longer holds once Sonnet builds. Frontmatter models last only for the invoking turn, so a turn that continues a `do` run falls back to the session model unless the `cpm-next-models` mod is installed, which holds the skill's model until another skill runs, the model is switched, or `/clear`; `calibrate` now says so and recommends effort only for these three skills. This pins the model variable the experiment previously held fixed, so compare runs against v3 with that in mind.
- **Model and effort in every skill's frontmatter** (0.6.0): `party` and `library` declare Sonnet at `medium` and `status` Sonnet at `low`, as `calibrate` already recommended; `plan`, `review` and `do` add `effort: medium`. The `cpm-next-models` mod (0.2.0) holds the effort as well as the model, raises `do all` to `high` because Sonnet tends to stop and check in during long runs at `medium`, and lets a later `/effort` win. `do all` stays on Sonnet rather than Opus, which `calibrate` used to recommend for unattended runs: the per-story Opus audit covers the quality risk, and `high` effort covers Sonnet stopping early. `calibrate` now covers only the cases these defaults don't fit, and model advice for work outside cpm-next. Every session no longer runs at the same effort, so the README's comparison protocol no longer holds for `do all` with the mod installed.
- **Effort per story** (0.7.0): stories may carry `**Effort**: low | high` (`medium` when absent), and a `low` story `**Model**: haiku`. `plan` sets `high` where a mistake is costly or hard to see and `low` for mechanical edits. With the `cpm-next-models` mod (0.3.0), `do` sets each story's effort through the mod's `set_story_effort` tool as the story starts, and raises it to `high` (or `xhigh`) for the fix after a failed audit; the model stays Sonnet, so the prompt cache survives. In a `do all` run no story goes below `high`. A Haiku story is built by a Haiku subagent. Subagent and auditor effort are not set per story, because the Agent tool takes a model but not an effort. `status` moves to Haiku. Without the mod, `do` builds at the session's effort as before.
- **scout** (0.7.0): a read-only `scout` agent on Haiku (`agents/scout.md`) answers lookups for `plan` and `do`: where something is defined or used, which files match, what a read-only database query returns. Search output stays out of the main conversation, which every later request would otherwise carry.
- **Parallel by default** (0.7.2): `do` builds unblocked stories in parallel, one subagent each, whenever they share neither files nor runtime state, instead of leaving it as an option; it judges overlap from the files each story touches and asks `scout` when unsure, and builds one at a time when they overlap or the user is working on a single story alongside it.
- **Worktree mode** (0.8.0): `do --parallel` builds unblocked stories together even when they share files, each subagent in its own git worktree, and the lead merges the branches with `--no-ff` so each story's audit reads one merge commit. Same-tree parallel work only ever applied to stories with no shared files, which in most projects is rare. Worktrees isolate files, not runtime state, so the mode is limited to code and tests: stories that need the running app (domains, webhooks, third-party calls), change a lock file or `.env`, or alter a table another story uses run one at a time, and a suite that needs shared services leaves the subagents writing code only. It commits locally, which `do` otherwise leaves to the user. `--parallel check` reports the batches and the suite's isolation without building, and a run without the flag makes the same check whenever two or more stories are unblocked at once, naming any batch that qualifies and the command to run it, but carrying on one at a time; `status` suggests it when two or more stories are unblocked at once.
- **Dependents wait for the audit** (0.8.1): a story's blockers must be `Complete` with an `**Audit**` line before it starts. In opus-opus, `do` built Stories 2 and 3 of an epic on top of Story 1 before Story 1 had been audited, then sent all three to audit at once.
- **The audit reads tests rather than re-running them** (0.8.2): the auditor no longer re-runs the tests a story's `Evidence` lines cite, since the full-suite run `do` gives it already ran them; it runs a single test only to show that test can't fail. `do` stops naming test modules the auditor may run, and runs the full suite after an audit's fixes so the second audit has a current result. In opus-opus every auditor re-ran three to eight test modules straight after the lead's 400-second full suite had passed them.
- **The flag is only for shared files** (0.8.3): a run without `--parallel` builds stories that share neither files nor runtime state in parallel itself, and suggests the flag only for stories that rule keeps apart, naming what they share. In a `do 00-01` run the lead found Stories 1 and 2 shared no files, suggested `--parallel`, and built them one at a time, because the worktree suggestion read as applying to every batch.
- **A small change gets criteria first** (0.8.4): `do` given a description writes the `docs/quick/` record, with acceptance criteria covering the whole description, before changing code, then builds it through the same steps as a story, with `Evidence` lines in the record, which the auditor checks as the story. A small change used to be "do it, test it": with no written criteria, a run could stop part-way or skip tests and neither it nor the audit had anything to measure the gap against, while the same request through `plan` as a one-story epic came out complete.
- **Later audits are scoped, and a third is allowed for a Critical** (0.8.5): an audit given an earlier audit's findings now checks those findings and the code written to fix them, and outside the fixes reports only a Critical the first audit missed. When the second audit returns a Critical, `do` fixes it and audits a third time, scoped the same way; a fourth never happens. Nothing had stopped a second audit reading the whole story again, which could raise new findings each round, and the user was asking for third audits by hand when the second uncovered something serious. Severity now weighs likelihood as well as impact: each finding says whether the failure comes from normal use, unusual use (a double click, two tabs, a request cut off) or an input no caller can produce; unusual use is a Warning at most and unreachable input a Suggestion, except for security and lost, corrupted or duplicated data, which keep their severity. Audits had reported a double click on a button as Critical. A Critical now decides whether a third audit runs, so it has to mean a failure that will happen.
- **Needs you means action** (0.8.6): `do`'s closing heading **Blocked on me** is now **Needs you**, the name `plan`, `review` and `status` already use. It now holds only what waits on the user, with each line naming the action and what it unblocks, including steps outside the repository the change depends on (a deployed migration, a secret, a service restart). Optional follow-ups stay out of it, and **Found** no longer carries actions. Runs had listed things under the heading that needed nothing from the user, while real actions turned up under **Found**.
- **Needs you, one item at a time** (0.8.7): after the closing headings, `plan`, `review` and `do` take the user through each **Needs you** item in turn: what it is and where, what each answer leads to, and a recommendation, asked as a single AskUserQuestion with the recommendation first and `Leave it for now` last. The skill acts on each answer before raising the next, within its own remit: `plan` amends the document, `review` fixes the story and updates the Remediation entry, `do` amends the criterion or carries out an approved step and then builds what it unblocked. A `**Pivot deferred**` item or a finding reaching back into the spec is still settled by `plan`. `status` writes nothing, so it gives each item a recommendation and leaves the walk-through to the skill that settles it. The list had been left for the user to work through unaided.
- **A spec-scoped unattended run** (0.8.8): `do all {spec}`, for example `do all 43`, runs unattended like `all` but only over the epics of that spec, so a run meant for one spec can't build every other spec's epics too. A bare number stays a story ID. The `cpm-next-models` floor already matches it, since it tests for a leading `all`.
- **Red-first evidence** (0.9.0): for every criterion a test proves, the `Evidence` line now carries the red result: `{test name, file:line} ({command}) — red: {failure text} with {lines undone | mutation of {file:line}: {change}}; green after restore`. The failure must come from the cited assertion, not an error such as a missing class, and the file is reverted from a scratch copy, never with `git checkout` or `stash`. A criterion no test proves records `red: n/a` with a reason (`manual`, `user`, `browser-observed`, `static`). A test cited as evidence can no longer pass for a reason unrelated to the criterion without the line showing it.
- **A missing red is an audit finding** (0.9.0): the auditor reads each recorded red instead of breaking lines itself. A missing red, a red from another test, an error in place of the failing assertion, a change the assertion doesn't depend on, or a missing `green after restore` is a Warning; an `n/a` reason that doesn't fit the criterion's tag is a Critical.
- **Resume adds reds** (0.9.0): on resume, `do` adds a red to each test-proven criterion of an evidenced story that has none, before auditing it. It first restores any file a stopped red left mutated from the directory the story's `**Scratch**` line names, and stops and lists the story under **Needs you** if that directory is gone.
- **Lessons are applied and checked** (0.9.0): before writing an epic's criteria, `plan` decides which library lessons and unretired retro observations bear on it, reflects them in criteria, and names them in a new `**Lessons**` epic field as `{lesson reference} (Story {N})` or `(build)`. `review` gives one persona the check that each `(Story {N})` entry is reflected in a criterion of that story.
- **Recurrences are reported** (0.9.0): when `do` writes a retro observation, a story `**Retro**` line or a quick-record observation that an earlier observation or a library lesson already describes, it adds `**Recurrence**: {lesson reference}`, reports it under **Found**, and, for a library lesson, under **Needs you** as a rule to add to `plan` or the auditor.
- **Per-run scratch directories** (0.9.0): `do` makes a run directory under the session's scratchpad (or with `mktemp -d`), a builder directory per story for red copies and a fresh auditor directory per audit round, passed by absolute path, so builders and auditors never share scratch files.
- **No tests in an unisolated suite** (0.9.0): `do` checks once per run whether the suite is isolated (every test process has its own database and files, and no fixed port). With an isolated suite audits of stories that share no files run in parallel and the auditor may run tests; otherwise audits still run in parallel and the auditor runs no tests. No red is taken while an auditor runs, and two full-suite runs never overlap.
- **Browser and user tags** (0.9.0): the contract adds `[browser]`, a criterion proved only by a rendered page, and `[user]`, one only the user can prove (a production run, a deploy, a sign-off, a third-party account). A `[user]` criterion's `Evidence` line is written only from the user's answer, in the form `Evidence (user, {YYYY-MM-DD}): {what the user reported} — red: n/a — user`; the auditor treats any other form as Critical, and a `[browser]` criterion with neither a test and its red nor a `browser-observed` record as a Warning.
- **Stories waiting on the user are skipped** (0.9.0): an unblocked story, not marked blocked, whose only unproven criteria are `[user]` or ones `do` cannot carry out in the session, is skipped when picking work and counts as done for the finish line; its steps are listed under **Needs you**, and the user's answer writes the `Evidence` line, after which `do` audits the story and closes it.
- **A final user-checks epic** (0.9.0): `plan` puts a spec's `[user]` criteria in one final epic that no other epic is blocked by, and tags and splits criteria by who or what can prove them. `review` flags a `[user]` criterion outside it.
- **claude-in-chrome for `[browser]` criteria** (0.9.0): `do` uses the repo's own browser test tool (`laravel/dusk`, `pestphp/pest-plugin-browser`, `@playwright/test`) when there is one; otherwise the lead drives claude-in-chrome against `APP_URL` on a `localhost`, `127.0.0.1` or `.test` host that already answers, using the browser's existing session. It starts no server, enters no credentials and creates no users; any other case goes to **Needs you**.
- **Negative criteria carry their control** (0.9.0): `plan` writes a criterion that says what must not happen, must not change or never occurs with its own control (the same inputs with the forbidden outcome present fail the check, and a compared set gets a floor that names its members), since a negative assertion with no control passes when the feature does nothing. A `docs/quick/` record gets the same rule, the lesson rule and criterion tags from `do`.
- **Shorter skills** (0.9.0): the skills were rewritten for fewer words, 9,182 words to 8,346 across the six SKILL.md files, keeping their rules; `status` grew, since it now reports blocked stories and stories waiting on a user check. `do`'s worktree rules moved to `skills/do/worktree.md`, which `do` reads only with `--parallel`, `--parallel check`, or when unblocked stories that share files are waiting, so other runs no longer load them.
- **The blocked note** (0.9.0): a story `do` has to stop on (a `Not met` line, an unresolved audit finding, an unexplained failure) keeps its status and adds ` — blocked: {reason}`, so the mods still read its status. `do` neither resumes nor picks such a story, and `status` lists it with its reason. A story waits on a user check only once it is unblocked, which now includes its epic's `**Blocked by**`; naming such an epic or story in `do` builds nothing until those blockers are `Complete`.
- **Existing epics are not back-filled** (0.9.0): reds, `**Lessons**` lines and the new tags apply to work written or built from 0.9.0 on.
- **Signals and class-keyed lessons in the contract** (0.10.0): a `**Signal**` records a failure `do` found, with a class slug, `project` or `process`, and the rule involved; ` — recurs:`, ` — raised`, ` — promoted` and ` — declined` mark its life. Library lessons and amendments carry a `**Class**` and state the rule, how a criterion or check shows it holds, and the owning layer. The story `**Retro**` and epic `**Retro waived**` fields are gone, and retros are legacy input. Most retro observations are about one spec, epic or story and are never useful again; learning now waits for a second occurrence.
- **`do` records signals** (0.10.0): on a finding that holds, a blocked story, and an `**Amended**`, `**Inline change**` or `**Pivot deferred**` line, in the story or the `docs/quick/` record, and writes no epic-completion retro. A worktree subagent reports its failures for the lead to record.
- **`do` finds recurrences** (0.10.0): a new signal is matched against library lessons, signals in other epics and unretired legacy retro observations and confirmed by reading. A recurring `project` signal becomes a promotion candidate under **Needs you**, raised once; a yes writes a `lessons-learned.md` entry, a no marks it declined. A `process` signal and a recurrence of a library lesson go under **Found** only, which replaces the 0.9.0 `**Recurrence**` marker and the **Needs you** routing of a library-lesson recurrence. Audit Suggestions are no longer recorded.
- **`plan`, `review` and `status` read what recurred** (0.10.0): `plan` and `review` read library lessons, recurring signals and unretired legacy observations, and accept a signal reference in a `**Lessons**` line. `status` reports a story with a missing signal as a suspect record, promotion candidates awaiting an answer, and a count of unretired legacy observations; it no longer reports a `Complete` epic without a retro.
- **`library learn` promotes from signals** (0.10.0): it collects recurring signals and legacy observations, proposes the owning layer, writes `project` lessons as constraints with a `**Class**`, marks signals promoted or declined, retires spent observations, and lists `process` candidates for the plugin without writing them. The retro format now lives in `library`.
- **`library sweep`** (0.10.0): `sweep add|remove|list` keeps `~/.claude/cpm-next/repos.txt`; `sweep` reads each listed repository's `process` signals and legacy observations naming a cpm-next rule, groups them by the cpm-next file and step, and reports those found in two or more repositories, so the failures worth changing the plugin for are found without reading retros by hand. It writes nothing in the repositories it reads; on request it writes one discussion record in the current repository for `/cpm-next:plan`.
- **Criteria state the rule, and Pivot deferred names its command** (0.10.0): `plan` states a criterion over the rule it enforces, with a regression for one reported input beside the rule's criterion, and `review` flags a criterion naming one instance where the requirement covers every case. `do` and `status` give each `**Pivot deferred**` item with `/cpm-next:plan {path}`.
- **Size** (0.10.0): `wc -w` over `do`, `plan`, `review`, `library`, `status`, the auditor and the contract gives 10,978 words at 0.9.0 (commit `70c789c`) and 12,748 now; no limit applies.
- **Red passes** (0.11.0): `do` takes a story's reds in one pass after its full-suite run, and the pass keeps its copies in `{git common dir}/cpm-next/scratch/{epic}-{story}/` with a `manifest` of the changed paths and a `tree` file naming the checkout. A matching manifest afterwards shows every file came back, so the suite result from before the pass stands for the audit and no test is re-run green; a mismatch copies back every path that has a copy, and blocks the story only for a difference that remains. The copies are no longer made per red or kept in the session scratchpad, and `Evidence` lines are written after the pass (replacing the 0.9.0 per-red copies, their `green after restore` result and the rule that no red is taken while an auditor runs), in the form `{test, file:line} — red: {message} with {lines undone in {file:lines} | mutation of {file:line}: {change}}` with no `green after restore`. A run restores a stopped pass before anything else, whatever its story.
- **`existing` reds** (0.11.0): a criterion that keeps behaviour the code already had, names no control and is proved by an unchanged test that passed at baseline records `red: n/a — existing (reaches {file:line})` instead of a red, naming a changed line the test executes. The auditor reports misuse as a Warning.
- **Auditor checks and the suite-free handshake** (0.11.0): check 5 reads each recorded failure against what the cited assertion would print, and wants the audit prompt to say a pass ended with a matching manifest. The auditor runs tests and probes only in a suite that is isolated or that the lead says is free, which it does only when it will wait for the audit in the foreground; a red pass may run during an audit only when that auditor runs nothing and the red touches none of the story's files (replacing the 0.9.0 rule that no red is taken while an auditor runs, and the auditor's Warning for a missing `green after restore`). After a batch in one checkout, the lead hands each story's pass to a fresh subagent, one at a time.
- **Commit guard** (0.11.0): `cpm-next` now ships a hooks module that refuses a `git commit` through the Bash tool while a pass directory under `{git common dir}/cpm-next/scratch/` names the session's checkout. It judges every commit against the directory the session runs in, so whether a worktree subagent's own commit is checked depends on the directory the engine reports for it.
- **Waiting on you, in the mods** (0.11.0): a `- Waiting on user:` line under a criterion marks one `do` treats as `[user]` though it is not tagged so, and the contract states how tools read criteria. `whats-next` (0.3.0) lists stories waiting on you apart from the stories to build, never offers one as next, and labels a dependent as waiting on your check; `cpm-next-progress` (0.8.0) shows such a story as Waiting on input whether it is Pending or In Progress, reads the archive for blockers, and no longer shows it in progress. Timings are recorded as before.
- **Browser checks said early** (0.11.0): when the scope holds a `[browser]` criterion the run cannot check, `do` says what is missing in its first message after probing the app and the browser, and asks once before building when the user is present; the checks that fell back become one question at the end, and once the environment is fixed `do` runs them all and takes their stories through the audit.
- **Sweep suggested when a spec finishes** (0.11.0): a `do` run that leaves a spec finished ends with one line suggesting `/cpm-next:library sweep`, or `sweep add` first when this repository is not on the list, and `status` lists the same under **Next**. Nothing runs the sweep by itself.
- **Size** (0.11.0): `wc -w` over `do`, `worktree.md`, the auditor, `status` and the contract gives 8,873 at 0.10.0 (commit `134ece1`) and 10,771 now; no limit applies.
- **Signals carry the version** (0.12.0): a `process` signal ends its description with ` — cpm-next {version}`, the version in the installed plugin's `.claude-plugin/plugin.json`; a `project` signal carries none, and signals written before 0.12.0 have none.
- **The fixed list** (0.12.0): `shared/fixed.md` lists the `process` failures a release fixed (the cpm-next file and step, the class, the version and what changed), seeded from 0.9.0 to 0.11.0, and a release that fixes one adds a row. `library sweep` leaves a group out, and names it as fixed with the version, when rows cover every signal in it, and shows the versions each group was seen under.
- **Sweep outside the plugin's repository** (0.12.0): in the plugin's own source repository `sweep` still offers a discussion record for `/cpm-next:plan`. Anywhere else it writes no record and offers an issue draft instead (class, cpm-next file and step, a generic one-line description, versions and a repository count, with nothing from your repositories), shows it in full, and files it with `gh issue create` against the `repository` field of the plugin's `plugin.json` only on your yes, or gives it as text with the URL. `plugin.json` gains that `repository` field.
- **calibrate retired**: with every skill setting its own model and effort, and the `cpm-next-models` mod holding them across turns, the per-run advice `calibrate` gave for cpm-next skills is built in. The exceptions it still covered (a greenfield `plan` at `high`, a subtle `party` on Opus) are a `/effort` or `/model` away, and model advice for work outside cpm-next is not this plugin's job.

## Upgrading to 0.9.0

`[manual]` criteria keep their meaning (a step `do` performs in the session outside the test suite), except that a criterion `do` cannot carry out in the session, such as a deploy, a production run or a sign-off, is now treated as `[user]`. The `whats-next` and `cpm-next-progress` mods pick by status alone, so a story waiting on the user shows as the next or in-progress work; they are unchanged in this release.

## Upgrading to 0.10.0

Run `/cpm-next:library learn` on existing retros: `do`, `plan` and `review` still read unretired observations, but nothing writes new ones, and `status` counts those that remain. `library sweep` reads other repositories, which raises permission prompts, and with one repository process signals appear only under **Found**. Instructions of your own that name "Retro" items (a progress-tracker rule, for example) should name promotion candidates and **Found** items instead.

## Upgrading to 0.11.0

Reds are taken in passes kept under `.git/cpm-next/scratch/`, and a `git commit` run through Claude is refused while a pass for the session's checkout is open: resume `/cpm-next:do` on the story, or copy the files back. Update `whats-next` and `cpm-next-progress` as well, or a story waiting on your check still shows as the next or in-progress work. Epics built before 0.11.0 keep their old `Evidence` lines; nothing is rewritten.

## Upgrading to 0.12.0

Nothing to migrate: signals written earlier have no version, so a sweep never leaves them out as fixed. A fork that changes the `repository` field in `plugin.json` has its draft filed there.
