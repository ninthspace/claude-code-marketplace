# cpm-next

Six skills that take work from an idea to tested code through Markdown artefacts in `docs/`. They replaced CPM's twenty-one skills, and read CPM v3 artefacts as input. CPM and DPM were withdrawn from the marketplace on 2026-10-08; installation and the companion mods are described in the marketplace README.

| Skill | Absorbs from v3 | Finish line |
|---|---|---|
| `/cpm-next:party` | party, consult | Record concluded, next step named |
| `/cpm-next:plan` | discover, brief, architect, spec, epics, pivot | Artefacts down to the target exist and trace upward |
| `/cpm-next:do` | do, ralph, quick | Stories in scope Complete, suite no worse than baseline |
| `/cpm-next:library` | library, retro learn and retire | Library documents carry complete front-matter; chosen retro lessons promoted and retired at source |
| `/cpm-next:review` | review | Critical and Warning findings fixed in Pending stories or waiting on the user; review record written |
| `/cpm-next:status` | status | One-screen report and the next command; nothing written |

## What changed, and why

- **Outcomes over procedure.** Each skill states what "done" means and when to stop. How to get there is left to the model.
- **State lives in the artefacts.** The discussion record and the epic doc are the state. No progress files, stale-progress checks, compaction hooks or `/cpm:clean`.
- **plan works from inventory.** It takes stock of what exists, asks its questions in one batch, records its own decisions as Assumptions, and writes only what's missing. It covers greenfield and brownfield from any starting state.
- **do stops only when it has to.** Its stop rules follow the Opus 5.5 guidance: keep going when the user isn't needed, and stop for unexplained failures, scope changes and destructive actions. An unattended (`all`) run marks blocked stories instead of stopping.
- **Kept on purpose:** the "unmet isn't wrong" rule from the Change Type Decision, citation-backed amendments, and `**Pivot deferred**` breadcrumbs. This is the one failure mode that is known to be expensive.
- **Dropped:** coverage matrices (`**Satisfies**` carries the traceability), the retro disposition gate, template hints, and the `AskUserQuestion` handoff menus.

## Additions

- **library** (0.2.0): brought over from v3 so reference documents can be imported and consolidated without switching plugins. Same front-matter and amendment formats, now in `shared/artifacts.md`; progress files, the stale-progress check and per-step gates dropped.
- **Per-criterion evidence** (0.2.0): `do` now writes an `Evidence` (or `Not met`) line under each acceptance criterion instead of one story-level `**Evidence**` field. In practice the two blocks drifted apart, and a reader couldn't tell which proof backed which criterion, or whether any criterion had none.
- **library learn, review, status** (0.3.0): `learn` moves durable retro lessons into the library, since otherwise only v3 does it and `consolidate` has nothing to fold in. `review` gives the epics the independent challenge that `plan` gives the spec. `status` is a read-only reading of the artefacts, which are the only state. Retro and review formats and the `**Retired**` marker join the contract, matching v3 so its skills read them unchanged.
- **Prompt audit for Opus 5.5** (0.3.0): `/claude-api prompt-audit` over the skills removed `do`'s self-review of each story's diff and the "Time matters" lines in `do` and `plan`, since Opus 5.5 checks its own work and effort is the control for how long it thinks. It also removed phrasing that only made sense against v3 ("No gate, no dispositions", "Don't present a menu"), and replaced the fixed counts in `review` and `status` with descriptions of what to keep. The persona subagents in `plan` and `review` were flagged and kept, because independent reviewers are the point of those steps. Worth confirming by running one epic with and without the self-review.
- **calibrate** (0.4.0): recommends a model and effort level for an artefact, a skill or a described task, or for a whole set of them as a table, one row per item, with the skill each needs next. It advises rather than setting either, since a skill's `model` and `effort` frontmatter only lasts for the invoking turn and would pin a variable this experiment holds fixed.
- **review personas on Sonnet** (0.4.0): `review` starts its persona subagents on `sonnet`. A per-call model outranks `CLAUDE_CODE_SUBAGENT_MODEL`, so this is the one subagent choice the plugin makes for you; `plan` and `do` subagents follow that variable, or the session model when it's unset. When comparing runs, note that review cost now differs from a v3 review on the same model.
- **Stories close as they finish** (0.4.1): `do` was writing every `Evidence` line and leaving the story `In Progress` and its tasks `Pending`, which also left dependent stories blocked, because the unblocked rule reads only the status. The simplifier pass, which came between verifying and closing, moves ahead of verification. A story now closes in the same edit as its last `Evidence` line, and the epic closes with its last story. `do` re-reads the finished story before starting the next one. On resume, an evidenced story left `In Progress` is closed before any other work.
- **Sonnet builds, Opus plans and audits** (0.5.0): `do` declares `model: sonnet` and starts its parallel subagents on Sonnet; `plan` and `review` declare `model: opus`, and their subagents, including the review personas that 0.4.0 put on Sonnet, now start on Opus. Before closing each story, or a small change, `do` hands it to a new read-only `auditor` agent (`agents/auditor.md`, `model: opus`), which re-runs the cited tests and reads the diff for unmet criteria, defects, scope creep and convention breaches. `do` fixes Critical and Warning findings, audits once more, and records the result in a new `**Audit**` story field; a story that fails the second audit is blocked. This restores a per-story review that the 0.3.0 audit removed on the grounds that Opus checks its own work, which no longer holds once Sonnet builds. Frontmatter models last only for the invoking turn, so a turn that continues a `do` run falls back to the session model unless the `cpm-next-models` mod is installed, which holds the skill's model until another skill runs, the model is switched, or `/clear`; `calibrate` now says so and recommends effort only for these three skills. This pins the model variable the experiment previously held fixed, so compare runs against v3 with that in mind.
- **Model and effort in every skill's frontmatter** (0.6.0): `party` and `library` declare Sonnet at `medium` and `status` Sonnet at `low`, as `calibrate` already recommended; `plan`, `review` and `do` add `effort: medium`. The `cpm-next-models` mod (0.2.0) holds the effort as well as the model, raises `do all` to `high` because Sonnet tends to stop and check in during long runs at `medium`, and lets a later `/effort` win. `do all` stays on Sonnet rather than Opus, which `calibrate` used to recommend for unattended runs: the per-story Opus audit covers the quality risk, and `high` effort covers Sonnet stopping early. `calibrate` now covers only the cases these defaults don't fit, and model advice for work outside cpm-next. Every session no longer runs at the same effort, so the README's comparison protocol no longer holds for `do all` with the mod installed.
- **Effort per story** (0.7.0): stories may carry `**Effort**: low | high` (`medium` when absent), and a `low` story `**Model**: haiku`. `plan` sets `high` where a mistake is costly or hard to see and `low` for mechanical edits. With the `cpm-next-models` mod (0.3.0), `do` sets each story's effort through the mod's `set_story_effort` tool as the story starts, and raises it to `high` (or `xhigh`) for the fix after a failed audit; the model stays Sonnet, so the prompt cache survives. In a `do all` run no story goes below `high`. A Haiku story is built by a Haiku subagent. Subagent and auditor effort are not set per story, because the Agent tool takes a model but not an effort. `status` moves to Haiku. Without the mod, `do` builds at the session's effort as before.
- **scout** (0.7.0): a read-only `scout` agent on Haiku (`agents/scout.md`) answers lookups for `plan` and `do`: where something is defined or used, which files match, what a read-only database query returns. Search output stays out of the main conversation, which every later request would otherwise carry.
- **Parallel by default** (0.7.2): `do` builds unblocked stories in parallel, one subagent each, whenever they share neither files nor runtime state, instead of leaving it as an option; it judges overlap from the files each story touches and asks `scout` when unsure, and builds one at a time when they overlap or the user is working on a single story alongside it.
- **Worktree mode** (0.8.0): `do --parallel` builds unblocked stories together even when they share files, each subagent in its own git worktree, and the lead merges the branches with `--no-ff` so each story's audit reads one merge commit. Same-tree parallel work only ever applied to stories with no shared files, which in most projects is rare. Worktrees isolate files, not runtime state, so the mode is limited to code and tests: stories that need the running app (domains, webhooks, third-party calls), change a lock file or `.env`, or alter a table another story uses run one at a time, and a suite that needs shared services leaves the subagents writing code only. It commits locally, which `do` otherwise leaves to the user. `--parallel check` reports the batches and the suite's isolation without building, and a run without the flag makes the same check whenever two or more stories are unblocked at once, naming any batch that qualifies and the command to run it, but carrying on one at a time; `status` suggests it when two or more stories are unblocked at once.
- **Dependents wait for the audit** (0.8.1): a story's blockers must be `Complete` with an `**Audit**` line before it starts. In opus-opus, `do` built Stories 2 and 3 of an epic on top of Story 1 before Story 1 had been audited, then sent all three to audit at once.
- **The audit reads tests rather than re-running them** (0.8.2): the auditor no longer re-runs the tests a story's `Evidence` lines cite, since the full-suite run `do` gives it already ran them; it runs a single test only to show that test can't fail. `do` stops naming test modules the auditor may run, and runs the full suite after an audit's fixes so the second audit has a current result. In opus-opus every auditor re-ran three to eight test modules straight after the lead's 400-second full suite had passed them.
- **The flag is only for shared files** (0.8.3): a run without `--parallel` builds stories that share neither files nor runtime state in parallel itself, and suggests the flag only for stories that rule keeps apart, naming what they share. In a `do 00-01` run the lead found Stories 1 and 2 shared no files, suggested `--parallel`, and built them one at a time, because the worktree suggestion read as applying to every batch.
- **A small change gets criteria first** (0.8.4): `do` given a description writes the `docs/quick/` record, with acceptance criteria covering the whole description, before changing code, then builds it through the same steps as a story, with `Evidence` lines in the record, which the auditor checks as the story. A small change used to be "do it, test it": with no written criteria, a run could stop part-way or skip tests and neither it nor the audit had anything to measure the gap against, while the same request through `plan` as a one-story epic came out complete.
- **Later audits are scoped, and a third is allowed for a Critical** (0.8.5): an audit given an earlier audit's findings now checks those findings and the code written to fix them, and outside the fixes reports only a Critical the first audit missed. When the second audit returns a Critical, `do` fixes it and audits a third time, scoped the same way; a fourth never happens. Nothing had stopped a second audit reading the whole story again, which could raise new findings each round, and the user was asking for third audits by hand when the second uncovered something serious. Severity now weighs likelihood as well as impact: each finding says whether the failure comes from normal use, unusual use (a double click, two tabs, a request cut off) or an input no caller can produce; unusual use is a Warning at most and unreachable input a Suggestion, except for security and lost, corrupted or duplicated data, which keep their severity. Audits had reported a double click on a button as Critical. A Critical now decides whether a third audit runs, so it has to mean a failure that will happen.
- **Needs you means action** (0.8.6): `do`'s closing heading **Blocked on me** is now **Needs you**, the name `plan`, `review` and `status` already use. It now holds only what waits on the user, with each line naming the action and what it unblocks, including steps outside the repository the change depends on (a deployed migration, a secret, a service restart). Optional follow-ups stay out of it, and **Found** no longer carries actions. Runs had listed things under the heading that needed nothing from the user, while real actions turned up under **Found**.
- **Needs you, one item at a time** (0.8.7): after the closing headings, `plan`, `review` and `do` take the user through each **Needs you** item in turn: what it is and where, what each answer leads to, and a recommendation, asked as a single AskUserQuestion with the recommendation first and `Leave it for now` last. The skill acts on each answer before raising the next, within its own remit: `plan` amends the document, `review` fixes the story and updates the Remediation entry, `do` amends the criterion or carries out an approved step and then builds what it unblocked. A `**Pivot deferred**` item or a finding reaching back into the spec is still settled by `plan`. `status` writes nothing, so it gives each item a recommendation and leaves the walk-through to the skill that settles it. The list had been left for the user to work through unaided.
- **A spec-scoped unattended run** (0.8.8): `do all {spec}`, for example `do all 43`, runs unattended like `all` but only over the epics of that spec, so a run meant for one spec can't build every other spec's epics too. A bare number stays a story ID. The `cpm-next-models` floor already matches it, since it tests for a leading `all`.
- **calibrate retired**: with every skill setting its own model and effort, and the `cpm-next-models` mod holding them across turns, the per-run advice `calibrate` gave for cpm-next skills is built in. The exceptions it still covered (a greenfield `plan` at `high`, a subtle `party` on Opus) are a `/effort` or `/model` away, and model advice for work outside cpm-next is not this plugin's job.
