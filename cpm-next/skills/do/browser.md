# Browser checks

Read this file when the scope holds a `[browser]` criterion, an `**Amended**` line's included, and read it again whenever it is not in context. It is part of `do` (`SKILL.md`, beside this file); a step or section it names is `do`'s unless this file holds it (**Before the first story**, **Step 3** and **Finishing** here are its own).

## Before the first story

If the scope holds a `[browser]` criterion (for a small change, once its record is written) and the repo has no browser test tool that runs in the session (**Step 3**, below), load the claude-in-chrome tools with ToolSearch and list the connected browsers, once per run, and probe the app as **Step 3** does (and again when the user says they have fixed it): `APP_URL`'s host must be `localhost`, `127.0.0.1` or a `.test` host, and one HTTP request must show the app answering there. With a browser connected and the app answering, open the page the criterion needs (or `APP_URL`) in that browser and note whether it lands on a login page; enter no credentials. Tools not found, or no browser listed, count as not connected. When the run then cannot check it (no connected browser, no app answering at a local `APP_URL`, or no login session where one is needed), say what is missing and how to fix it in the first message after the probe and carry on; with the user present, ask once, before building, whether to fix it first.

## Step 3

A `[browser]` criterion: use the repo's own browser test tool when its manifest declares one (`laravel/dusk`, `pestphp/pest-plugin-browser`, `@playwright/test`) and it runs in the session. It gets a red like any test and may start its own server; if it runs outside the project's test command, run it yourself and give its result to the auditor with the story's run. A cited `[browser]` test is in the targeted set. Otherwise the lead, never a subagent, uses claude-in-chrome: take the URL from the project's `APP_URL` when its host is `localhost`, `127.0.0.1` or a `.test` host, confirm with one HTTP request that the app answers there, and record the URL, the steps and a short excerpt of the page text (`red: n/a — browser-observed`). Start no server, enter no credentials, create no users; behind a login, use the browser's existing session. Any other case (another host, no answering server, no connected browser, a login with no session, a browser that disconnects later) goes to **Needs you** and is then treated as `[user]`, with an indented `- Waiting on user: {steps}` line under the criterion.

## Finishing

The `[browser]` criteria that fell back to the user (**Step 3**): ask once for all of them, whether the user will fix the environment (an app answering at the local `APP_URL`, a connected browser, a login session) so that you run them all, or report the results themselves. Once it is fixed, check each through claude-in-chrome as **Step 3** says, record it `browser-observed` and remove its `- Waiting on user:` line, and for each story whose criteria then all have `Evidence`, take step 4, audit it, take its deferred full run if it needs one, and close it as step 6 says; a check that fails gets a `Not met` line in place of its `- Waiting on user:` line and the contract's blocked note on its story; a reported result is written as **Finishing**'s `[user]` item in `do` describes.
