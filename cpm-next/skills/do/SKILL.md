# Do

Build what the epics describe, and prove it. The epic doc is the task list and the run's only state, read by the user, a compacted context and the next session, so keep it current as you go. Formats, status vocabulary and the unblocked-story rule are in `shared/artifacts.md`, two levels above this skill's directory.

## Scope and finish line

Read `$ARGUMENTS`:

| Argument | Scope | Done when |
|---|---|---|
| epic path | that epic | all its stories are Complete |
| story or task ID (`3`, `2.1`) | that item, in the epic the last row picks | that item is Complete |
| `all` | every unfinished, unretired epic, in dependency order | no unblocked story remains |
| `all {spec}` (`all 43`) | the same, limited to epics whose prefix starts with that spec number; stop before building if there is none | no unblocked story remains in those epics |
| a description of a small change | no epic | the change works and is tested |
| nothing | the lowest-numbered In Progress epic with an open story that is unblocked, isn't marked blocked (no `Not met` line or ` — blocked:` note) and isn't waiting on the user; else the lowest-numbered epic with nothing started whose `**Blocked by**` epics are all Complete and that has such a story; stop before building if there is none | that epic's stories are Complete |

A story is waiting on the user when it is unblocked, isn't marked blocked, at least one criterion lacks `Evidence`, and every such criterion is `[user]` or treated as `[user]` (step 3). It is skipped when picking work, and counts as done for the finish lines above.

`--parallel` and `--parallel check` may follow any scope but a small change (see **Worktree mode**); `--parallel check` builds nothing and writes nothing.

The baseline is one full run of the project's suite before anything changes. Each story's runs after it are decided by `shared/test-runs.md` (beside the contract) and recorded in its `**Test run**` line: a targeted run before its audit, and for a story that file makes full, its full run after the audit (the deferred full run). The run is done when every story it closed closed on a passing run of its kind and every epic it closed closed on a passing full run; a failure left in the suite must have been failing at the baseline, or be one `test-runs.md` (**An open story's independent tests**) leaves to its story. A result stands while a fresh snapshot (as `test-runs.md` defines it) hashes the same as the one recorded with it, and only a full run stands for the baseline. A run that closes no epic takes a full run only for a story `test-runs.md` makes full.

For a small change, write the `docs/quick/` record before any code (signals found while building it go there too): without written criteria, neither the build nor the audit can tell that part of the change is missing. Read what **Before the first story** lists that bears on the change (its first bullet always), and the code it touches, then give the record acceptance criteria in the contract's story format for everything the description asks, at each place the same fault or feature occurs, with a tagged test for each criterion code can prove. Write must-not, must-not-change and never criteria as the **Epics** paragraph of `skills/plan/SKILL.md` (beside this skill's directory) says, reflect bearing lessons as its **Lessons** paragraph says, and tag and route each criterion as step 3 does. Where two reasonable readings of the description and code would build different things, show the user the criteria and ask which they mean, in one message, before building; otherwise don't ask. If the criteria exceed one story's work, stop before building and suggest `/cpm-next:plan`; otherwise build it as one story through the steps of **The loop**, taking its deferred full run after its audit, with the `Evidence` lines, the `**Test run**` line and the `**Audit**` line, forms included, in the record, which the auditor checks as the story. A record carrying either `**Audit**` form is resumed as a story is.

## Before the first story

- Restore what a stopped red pass left, before the baseline and any other work, in every run, a small change included. For every directory under `{git common dir}/cpm-next/scratch/` (found as **Scratch directories and isolation** says) whose `tree` file equals the output of `git rev-parse --show-toplevel` run now, whatever its story or quick record: copy its files back to their repository paths (not its `manifest` and `tree` files), delete the directory by its literal, quoted absolute path and remove its `**Scratch**` line. Delete a directory with no `tree` file (its pass stopped before copying anything), and one whose `tree` no longer exists, naming the latter under **Found**; leave one whose `tree` is another existing checkout to that checkout. Remove a `**Scratch**` line whose directory is gone and lay under the common directory (the pass was interrupted after its deletion); a line that names a path outside it (a directory in a session scratchpad) stops the story and goes under **Needs you**, since its files may still be mutated.
- Read `CLAUDE.md`, `docs/library/`, the epic, its source spec and the ADRs it cites; read the library lessons, the signals that recur (a `**Signal**` with a ` — recurs:` suffix) and the unretired legacy retro observations (bullets under a retro's `## Observations` with no `**Retired` marker) that bear on the epic's area.
- Find the test command (library, `composer.json`, `package.json`, `Makefile`, `pyproject.toml`, `Cargo.toml`) and run the full suite for the baseline, noting its snapshot, unless an earlier full result stands.
- A failing test at the baseline that a story with a `full run due` or `fix due` `**Audit**` line explains is that story's regression (`test-runs.md`, **The deferred full run**). A failing test at the baseline that a story closed on a targeted run in an In Progress epic explains is not accepted as pre-existing: it is fixed in the next story this run builds in that epic, named in that story's audit prompt with the failing test, or, when this run builds none there, listed under **Needs you** with the test and the story, with a signal. A baseline failure no such story explains is pre-existing, unless `test-runs.md` (**An open story's independent tests**) gives it to an open story.
- If the scope holds a `[browser]` criterion (for a small change, once its record is written) and the repo has no browser test tool that runs in the session (step 3), load the claude-in-chrome tools with ToolSearch and list the connected browsers, once per run, and probe the app as step 3 does (and again when the user says they have fixed it): `APP_URL`'s host must be `localhost`, `127.0.0.1` or a `.test` host, and one HTTP request must show the app answering there. With a browser connected and the app answering, open the page the criterion needs (or `APP_URL`) in that browser and note whether it lands on a login page; enter no credentials. Tools not found, or no browser listed, count as not connected. When the run then cannot check it (no connected browser, no app answering at a local `APP_URL`, or no login session where one is needed), say what is missing and how to fix it in the first message after the probe and carry on; with the user present, ask once, before building, whether to fix it first.
- Resume honestly: a story `In Progress` from an earlier session may be partly done, so check the code before redoing or skipping anything. A story marked blocked (a `Not met` line or a ` — blocked:` note) is not resumed until the user settles the blocker: list it under **Needs you** with its reason. If every criterion has an `Evidence` line, confirm the evidence holds, take a red pass (step 4) for each test-proven criterion that has neither a red nor an `existing` reason, take its step 4 run first (a `**Test run**` line whose snapshot no longer matches never stands), audit the story if it has no `**Audit**` line, and close it as step 6 says, before other work. A story whose `**Audit**` line carries `full run due` takes its deferred full run with no further audit when its story snapshot still matches, and is audited as a whole story first when it does not; a `fix due` story finishes its fix, takes the fix rerun and retakes the reds `test-runs.md` names, then is audited as a whole story, that audit being its scoped round, before its deferred full run.

## The loop

Take unblocked stories lowest number first. A story is unblocked only when every story in its `**Blocked by**` is `Complete` with an `**Audit**` line, since fixes from that story's audit would rework code built on top of it, and every epic its epic's `**Blocked by**` names is `Complete`. Each story goes through these steps, wherever it is built:

1. Set the story, and the epic if it was Pending, to `In Progress`. Call `mcp__cpm-next-models__set_story_effort` with the story's number and `**Effort**` (`medium` when it has none); without that tool, build at the session's effort. A story whose `**Independent tests**` line reads `due` then takes **Independent tests** (below) before any of its code is written.
2. Build it task by task, setting each task `In Progress` as you start it and `Complete` when done. Follow the project's existing conventions over your own preferences. In a Laravel project, run the `laravel-simplifier` agent over the story's changes, if available, before verifying.
3. Verify every acceptance criterion with the tests its tag names, or with the manual check and what you observed, in an `Evidence` line directly under it, as the contract shows. A criterion without its own evidence isn't met.
   - `[browser]`: use the repo's own browser test tool when its manifest declares one (`laravel/dusk`, `pestphp/pest-plugin-browser`, `@playwright/test`) and it runs in the session. It gets a red like any test and may start its own server; if it runs outside the project's test command, run it yourself and give its result to the auditor with the story's run. A cited `[browser]` test is in the targeted set. Otherwise the lead, never a subagent, uses claude-in-chrome: take the URL from the project's `APP_URL` when its host is `localhost`, `127.0.0.1` or a `.test` host, confirm with one HTTP request that the app answers there, and record the URL, the steps and a short excerpt of the page text (`red: n/a — browser-observed`). Start no server, enter no credentials, create no users; behind a login, use the browser's existing session. Any other case (another host, no answering server, no connected browser, a login with no session, a browser that disconnects later) goes to **Needs you** and is then treated as `[user]`, with an indented `- Waiting on user: {steps}` line under the criterion.
   - A criterion an independent test proves cites it as **Independent tests** says, and a red held from the pre-build run is written into its `Evidence` line here.
   - `[user]`, and any criterion you can't carry out in the session whatever its tag (a deploy, a production run, a sign-off), is treated as `[user]`: never claim it as met, list it under **Needs you**, and write its `Evidence` line only from the user's own answer, never in a run with no user present. A criterion not tagged `[user]` gets the same `- Waiting on user: {steps}` line, which you remove when you write its `Evidence` line.
4. Check the story as the auditor will, before the audit, in this order:
   - Feed the new code inputs it doesn't expect (empty, missing, null, non-numeric, boundary, records that collide on an attribute that is not their key, the same identity twice in one delivery), and read every help text, doc and `Evidence` line the story touched against the code. Fix what either shows.
   - Read `shared/test-runs.md` and decide the story's run by it (before its audit a story takes a targeted run, and a story that file makes full takes its full run after the audit), run it, write the `**Test run**` line (in a `docs/quick/` record too) and fix what it shows, rewriting the line and running again after any change to a non-exempt file until a run needs no fix (in a parallel batch, the lead's run after the batch is that run). A story closes its epic when, at its step 4 run, every other story in the epic is Complete, has only `[user]` criteria (or criteria treated as `[user]`) left, or is in its batch; it and a small change close only on a passing deferred full run against the code being closed. A failing targeted run follows `test-runs.md`'s failing-run rules, in this step and step 5. A story whose diff holds no non-exempt file takes no run and writes `none`, and takes a deferred full run only if it closes its epic, as `test-runs.md` says. A full run covers every test runner the baseline used.
   - Take the reds, in one red pass, once no edit to the story's files remains to be made, after the simplifier pass and against the code being closed. A red is required for every criterion a test proves (any tag the project's Testing Strategy maps to a suite, and any untagged criterion a test proves), except one recorded `red: n/a — existing (reaches {file:line})` on the contract's terms. The auditor reports a misused `existing` as a Warning. An `existing` reason on a criterion for new behaviour, on one naming a control, on a test whose body the story changed, or naming a line the test does not execute is a finding. A story with no test-proven criterion, or only `existing` ones, takes no pass. An independent test whose red came from the pre-build run (**Independent tests**) takes none either. The builder takes the pass in a single build; in a one-checkout parallel batch, the lead's subagent after the batch, as the parallel rules say, never while siblings run; in worktree mode, the subagent in its own worktree, or the lead after merging where subagents write code only.
   - The red pass: create the pass directory, new and empty, at the path the contract's `**Scratch**` field gives, and write its path in a `**Scratch**` line under the story (a worktree subagent skips the line). Write a `manifest` in it, each changed or untracked, not ignored, path with its blob hash (from `git diff HEAD --name-only` and `git ls-files -o --exclude-standard`, hashed with `git hash-object`, a path that no longer exists recorded as `deleted` and not hashed, leaving out the epic doc or `docs/quick/` record, which the pass edits, and diffing against the empty tree when the repository has no commit), and a `tree` file holding the output of `git rev-parse --show-toplevel`. Copy each file the pass will change into the directory at its repository path, once, before its first mutation. Take each red by undoing the lines the cited test covers with the Edit tool and running only that test. Where that leaves it green (a refactor, a characterisation test, code the story didn't change) or makes it error, copy the file back and mutate a covered line instead, which may lie outside the story. The failure must come from the cited assertion: an error (missing class, method, route or table) doesn't count, and a stub that returns a wrong value does. Note the failure text and the undone `{file:lines}` or the mutation, then copy each file back from the pass directory. Never revert with `git checkout`, `git show … >`, `git stash` or `reset`, which take uncommitted work with them. When the last red is taken, recompute the manifest and compare it with the first.
   - On a match, delete the pass directory by its literal, quoted absolute path (never the `scratch/` folder itself, and never a glob) and remove the `**Scratch**` line; only then write each noted red into its criterion's `Evidence` line as the contract shows (a retaken red replaces the earlier one), and a criterion no test proves, or that takes `existing`, records `red: n/a` with its reason. A fix's test for a finding with no criterion takes its red in a pass too, and the red goes in the findings list handed to the next audit. The result from before the pass stands for the audit; re-run no test.
   - On a mismatch, first copy back every path that has a copy in the pass directory (not `manifest` and `tree`) and differs from it, listed or not, and compare again. A path that was not listed and is now untracked is test output: name it under **Found** and leave it, and count the manifest as matching once nothing else differs. Any other difference, or one that remains (a listed path with no copy, such as a tracked file the test run rewrote), marks the story blocked (the contract's note with the paths, and a signal) and lists it under **Needs you**; the pass directory and the `**Scratch**` line are then removed as above.
5. Have the story audited (see **Audit**). On `fix needed`, set the fix's effort with the same tool (`high`, or `xhigh` for a story already at `high`), fix every Critical and Warning finding wherever its mistake occurs, not only where cited, and give each fix a test, its red recorded in the `Evidence` line of the criterion the finding concerns or, for a finding with no criterion, in the findings list handed to the next audit. Update the `Evidence` lines the fix affects, and check the fix as new code as step 4 says, so the next audit has the run for the code as it stands (a fix rerun is the one `test-runs.md` gives, and rewrites the `**Test run**` line); a fix that changes a file a red mutated, or a red's test file, retakes that red in a new pass. A Warning that the run was missing or too narrow is settled by making the run, which needs no test and no red: when it passes, that finding is fixed and needs no further round of its own, and only a failure it shows is fixed through this step. A Warning that the prompt named no deferred full run for a story `test-runs.md` makes full is settled by writing the `full run due` suffix on its `**Audit**` line, with no fix round. Then audit again. If the second audit returns a Critical, fix its findings the same way and audit a third time, saying in one line why. Otherwise, and after any third audit, that audit is the last of this step's rounds: if it still returns `fix needed`, record each unresolved finding in a `Not met` line under the criterion it concerns, or as a signal when it concerns none, and treat the story as blocked (see **Signals**). When the last audit passes for a story that needs a deferred full run, write its `**Audit**` line with the `full run due` suffix and take the deferred full run when `test-runs.md` (**The deferred full run**) says (in a single build, before any other story's work starts); it also gives what a failing run leads to, a regression no story's change explains included, which is still fixed under a scoped round.
6. Close the story in the same edit that writes its `**Audit**` line: set any remaining tasks and the story's `**Status**` to `Complete`, and the epic's too if it was the last open story. A story with a deferred full run due closes only on that run's pass as `test-runs.md` defines it, in the edit that rewrites its `**Audit**` line without the suffix (a scoped round counted in `n findings fixed`).

Before the next story, re-read the one just finished in the epic doc: it must be `Complete` with an `**Audit**` line, be marked blocked (its status kept, with the contract's ` — blocked: {reason}` note, and a `Not met` line under any unmet criterion), wait on the user, or carry a `full run due` or `fix due` `**Audit**` line while it waits for its batch's shared deferred full run or its scoped round, since an evidenced story left `In Progress` blocks its dependents.

Stories unblocked together are built in parallel, one subagent each, when they share neither files nor runtime state (databases, migrations, dependency installs and lock files, cache and queue state, storage directories, `.env`, ports), judged from the files their tasks name and the code they touch; otherwise, or when the user is working alongside you on a single story or task, one at a time. The lead owns everything shared:

- It runs migrations, dependency installs and every test run after a batch: the union of the stories' targeted sets, and one shared deferred full run when any story in the batch needs one, that every story of the batch waits for (`test-runs.md` gives the rules; a story's line reads `closes epic` where the batch leaves no story of its epic open outside it). A story that needs a schema or dependency change goes first, run by the lead, before any fan-out.
- A subagent runs only its own story's tests (its targeted run), and only when the suite is isolated (see **Scratch directories and isolation**); otherwise it writes code only, and the lead runs its tests after it reports. A red pass handed to it, below, is the one exception.
- A subagent leaves `[browser]` criteria to the lead, who checks them after the batch.
- Once the batch has finished and nothing else is running, the lead hands each story's red pass (step 4) to a fresh `opus` subagent, one at a time, giving it the story, the cited tests, the pass directory's absolute path, the absolute path of the contract and the absolute path of this file for step 4's rules on taking each red. The lead creates the pass directory, the `**Scratch**` line, the `manifest` and the `tree` file before the hand-off; the subagent copies files into the directory, takes and restores each red, and reports each failure with its `{file:lines}` or mutation, and does not create, compare or delete the directory or touch the epic doc. The lead then compares the manifest itself, deletes the directory, removes the line, and writes the `Evidence` lines from the reported failures after checking each against the test file. No pass runs while batch siblings run, since a sibling's tests would run the code a red has mutated.
- A subagent has none of this conversation, so its prompt names the resources it must leave alone.
- A subagent building a story with independent tests, in either build mode, is given **Independent tests**' builder's limits and dispute route in its prompt, with the files on the story's line; it carries a dispute to the lead in its report, and the lead writes the story's held reds into their `Evidence` lines when it checks that report.
- The lead checks each report against the files and test output before the story goes to audit, and makes every audit fix, in its own checkout.

Start each parallel subagent on `opus`, and a `**Model**: haiku` story on a `haiku` subagent even when nothing runs beside it.

Hand plain lookups (where something is defined or used, which files a change touches, what a read-only query returns) to the `cpm-next:scout` agent, which keeps search output out of this conversation; read the code yourself when the answer depends on understanding it.

Leave commits, branches and pushes to the user unless they've said otherwise. Asking for `--parallel` is their leave to commit and merge locally on the current branch, never to push.

### Independent tests

A story whose `**Independent tests**` line reads `due` (the field and its forms are in the contract) has its acceptance tests written by the `test-writer` agent (`subagent_type` `cpm-next:test-writer`) before any of its code is written, and is built to them.

- **Order.** In a single build the writer runs after step 1 and before step 2. In a batch the lead starts one writer per marked story, in parallel, after any schema-first story it runs and before fan-out; a schema-first story that is itself marked has its writer run before the lead builds it.
- **The prompt**, as **Audit** lists the auditor's: the story and the epic doc's path; the spec; the paths of the samples its **Data Sources** section names; the absolute paths of the contract and of `skills/plan/SKILL.md` (beside this skill's directory); the test command and the project's formatter; a fresh writer directory (**Scratch directories and isolation**); and, on a resumed story whose line still reads `due`, the files a stopped writer left, found by `{epic file stem}-{story}` in their paths. A test sent back to the writer adds its file, why it came back, the failure text, citation or audit finding, and the files the story's build has changed.
- **The pre-build run.** The lead checks the writer's report against the files, then runs each story's independent tests, one story at a time and never beside another test run. This run does not rewrite `**Test run**`. A test that errors for a cause other than the boundary not existing yet (a syntax error, a bootstrap failure, a missing fixture) goes back to the writer. A test that passes is kept when it proves a must-not or never criterion or asserts behaviour the code already has, and otherwise goes back to the writer. Each test goes back at most once for each cause; after that, an error marks the story blocked with a signal, and a pass raises its criterion through **When a criterion looks wrong**.
- **The red before the build.** A failure in this run that meets the contract's conditions for the `before the build` red is that test's red. The lead holds its failure text in the run directory and writes no `Evidence` line before the build; step 3 writes it into the criterion's `Evidence` line in the contract's form. Every other independent test, and one whose held red was lost when a run stopped, takes its red in the red pass (step 4).
- **The field.** After the last return to the writer, and in worktree mode after the commit before fan-out (a commit hook can reformat a file), the lead rewrites the line in the contract's form over every file the writer wrote.
- **The builder's limits.** No file on the line is edited, and neither the simplifier (step 2) nor the project's formatters run over them. Each criterion an independent test proves cites that test in its `Evidence` line, beside any test of the builder's.
- **A dispute.** A builder that finds an independent test wrong cites what contradicts it: a requirement, another criterion, or a `file:line` the story did not write. The lead, never a parallel subagent (whose report carries the dispute to the lead), starts a fresh writer with the prompt above, the test and the citation. The writer keeps or revises the test; a revision rewrites that file's blob on the line, appends the contract's ` — revised` note, and takes its red in the red pass. An audit finding that an independent test is wrong or proves too little is a dispute too, the finding being its citation: no fix edits the test, and a test the writer keeps leaves the finding dismissed with the writer's reason, given to the next audit. Each test is disputed once: a test kept after its dispute leaves the story to build to it or be marked blocked, with a signal.
- **No writer.** When the `test-writer` agent is not available, the lead rewrites the line `skipped — test-writer unavailable`, builds the story as an unmarked one and says so under **Found**.

### Worktree mode

With `--parallel` or `--parallel check`, read `worktree.md` in this skill's directory before building, and follow it: it says which stories a worktree batch may hold, when a worktree's test results count, what each subagent's prompt adds, how the lead merges, and what `--parallel check` reports.

Without `--parallel`, stories that share neither files nor runtime state are still built in parallel; the flag is never needed for them. When unblocked stories that rule keeps apart are waiting, read `worktree.md` and check them as `--parallel check` would, without the report. If a batch qualifies, say so in one line with the next tool call, naming the stories, what they share and `/cpm-next:do {scope} --parallel`, carry on one at a time, and repeat the line under **Found**. Don't switch to worktree mode unasked, since it commits.

### Scratch directories and isolation

At the start of a run, make a run directory under the session's scratchpad, or with `mktemp -d` when there is none. Inside it the lead creates, and passes by absolute path, a fresh auditor directory per audit round (`audit-{epic}-{story}-r{n}`, or `audit-quick-{nn}-r{n}`), and a fresh writer directory per test-writer it starts (`writer-{epic}-{story}-{n}`). No two agents share one. A red pass's directory is not there: it is `{git common dir}/cpm-next/scratch/{epic file stem}-{story}/` (`quick-{nn}/` for a small change), the common directory found with `git rev-parse --path-format=absolute --git-common-dir`, so it outlives the session and every worktree of the repository shares it. If that path already holds a directory whose `tree` is another checkout (an abandoned worktree's), the pass does not run: mark the story blocked with the reason and a signal.

A suite is isolated when every test process, including a single run without a parallel flag, gets its own database and its own copy of every file tests write (fake disks, SQLite database files, file caches, compiled views, result caches), and no test binds a fixed port. Check this once per run, before the first audit, from the test config and a few tests, whatever the build mode.

A red pass may run while an audit runs only when it mutates no file the audited story changed and that auditor was told to run no tests and no probes, scope being judged from the file list the auditor was given; two test runs, full or targeted, or a test run and a red pass, never overlap in one checkout.

## Audit

Start the `auditor` agent with the Agent tool, `subagent_type` `cpm-next:auditor`. One auditor checks one story, with no limit on its length and nothing in its checklist narrowed, since a shared or capped audit leaves findings for the next round. It has none of this conversation, so give it:

- the epic path and story number, or the `docs/quick/` record;
- the files the story changed, or a worktree story's merge commit;
- the files on the story's `**Independent tests**` line, in every build mode;
- the test command, the story's `**Test run**` line, the path of `shared/test-runs.md` and the result of the run made after the story's last change (counts, and any failing test). A targeted run's tests are listed as the run's coverage, not for the auditor to run; the result covers every test it lists, which the `Evidence` lines cite, so the auditor reads the tests and their recorded red results and runs none to reproduce a red. For a story that needs a deferred full run, that the full run follows the audit, with its reasons;
- the fixes made outside the story's files to answer a failure a run or the baseline showed, each with the test whose failure it answers;
- when the story took a red pass, that the pass ended with a matching manifest;
- the absolute path of the contract (`shared/artifacts.md`, resolved from this skill's directory);
- its auditor directory, for probe scripts, test output and `TMPDIR`;
- whether the suite is isolated or free; in a suite that is neither, the auditor runs no tests and no probes and works from the tests and the run result it was given. The lead may say an unisolated suite is free only when it will wait for that audit in the foreground and make no test-running call, start no red pass and start no other test-running audit until it reports;
- the resources it must leave alone.

Audits of stories that share no files may run in parallel, isolated suite or not. A later audit also gets the previous audit's findings as it wrote them, which you dismissed and why, and the files the fixes changed, but no description of the fixes: it audits the fix code as new code. A scoped round gets the prompt `test-runs.md` sets out in place of findings.

Check each finding against the code before acting on it, and drop any that don't hold up. Suggestions are neither fixed nor recorded. A finding that contradicts the criterion rather than the code goes through **When a criterion looks wrong**.

Record the outcome as `**Audit**: pass ({YYYY-MM-DD})`, adding `, {n} findings fixed` when the first audit returned `fix needed` (a scoped round counts too), and for a story that needs a deferred full run the contract's `full run due` suffix. If the `auditor` agent isn't available, write `**Audit**: skipped — auditor unavailable` (with the same suffix) and say so under **Found**.

## Signals

Write a `**Signal**` on the story, or in the `docs/quick/` record (form and slug rule in the contract), when an audit finding holds, when you mark a story blocked (step 5, **When to stop**), and when you write an `**Amended**`, `**Inline change**` or `**Pivot deferred**` line (**When a criterion looks wrong**): one per class per story. An unresolved finding that concerns no criterion is a signal too. A `process` signal names the cpm-next file and step involved and ends its description with ` — cpm-next {version}`, the `version` in the installed plugin's `.claude-plugin/plugin.json` (at the plugin root, two levels above this skill's directory); a `project` signal carries no version. Before choosing a slug, grep the `**Signal**:` lines in `docs/epics/`, `docs/archive/epics/` and `docs/quick/`, the library's `**Class**` lines and the contract's seed slugs, and reuse one that fits.

After writing each signal, separately, check whether it recurs. Look in this order: a library lesson with that `**Class**` (or, for a lesson with none, one that describes the failure); a signal with that slug in a different epic or quick record, `docs/archive/` included; an unretired legacy retro observation (read them once per run or, with more than 20 retro files, have `scout` list those matching the signal's terms). Read both to confirm they describe the same failure, and on a match append ` — recurs: {reference} ({why it matches, one clause})`. A match within the same epic is not a recurrence. A rejected `**Class**` or signal match gives the signal a different slug, matched once more under it; after a rejected description match, carry on down the order.

Route a recurrence by its kind. A `project` signal that recurs with no library lesson, none of whose matches carries a ` — declined` or ` — promoted` mark, goes under **Needs you** with the matching signals and the constraint proposed (the rule, how a criterion or check shows it holds, and the owning layer), and is marked ` — raised {YYYY-MM-DD}`. A signal matching a declined one is marked ` — declined` too and not raised. A `process` signal, and a signal that recurs against a library lesson, go under **Found** only. A signal that matches a candidate still waiting for its answer, or any signal listed with or joined to it, whatever its epic, joins that candidate instead of becoming another, and is marked ` — raised` too. One that matches an answered candidate takes its answer: declined after a no, whatever the epic, and after a yes a recurrence against the new lesson, under **Found**. A signal that never recurs is never reported.

## When to stop and when to keep going

A message without a tool call ends the turn, and the work stops until someone replies. While stories in scope remain open, don't end a turn on a progress summary announcing a next step you haven't taken, an offer to carry on, a list of decisions none of which blocks the remaining work, or a report because a story finished or the turn ran long. Put status notes and recommendations in the message with the next tool call, and carry on with whatever doesn't depend on an answer.

Stop and ask only when:

- a test fails for a reason you can't explain after investigating it;
- a criterion contradicts reality and resolving it would change scope (below);
- the next action is destructive or reaches outside this repository: deleting data, rewriting history, touching shared infrastructure.

In an `all` run, with or without a spec, or whenever the user has said they won't be watching, don't stop for the first two: mark the story blocked with the reason (and a signal), and move on to other unblocked work. The third always stops the run.

A story isn't finished while a subagent or background command it started is still running: wait for its output and check it.

## When a criterion looks wrong

A criterion that is hard to meet is not wrong. "The tests fail", "this approach didn't work" and "it's slower than the target" are reports about this implementation, and never justify changing the criterion: leave it standing, mark the story blocked, and record what was tried in a `Not met` line under it, with a signal.

A criterion is wrong only when you can cite what contradicts it: a `file:line`, a named spec requirement (`FR3`, `AD1`), or another criterion in the same epic that can't be satisfied at the same time.

- A wording fix with no change of scope: edit it and add an `**Inline change**` line, with a signal.
- A change of scope, with the user present: ask, showing the citation.
- A change of scope in an unattended run: amend the criterion in this epic only, with an `**Amended**` line carrying the citation, and add a `**Pivot deferred**` line for each upstream document that now disagrees. Leave the spec and every other document untouched; `plan` resolves those later with the user.

## Finishing

End every run with three headings, in this order:

- **Needs you**: only what won't happen unless the user acts, each line naming the action and what it unblocks: a decision only they can make, a blocked story and what would unblock it, a `**Pivot deferred**` item (with `/cpm-next:plan {path of the upstream document}`), a promotion candidate, a `[user]` criterion of a story waiting on the user, with its steps, a destructive step you held back from, and any step outside the repository the change depends on (a migration on a deployed database, a secret or environment value, a service to restart). Leave out optional follow-ups, things worth a look and anything already done; say "Nothing" if so.
- **Changed**: stories completed, the main files touched, how many full and targeted runs the run made (the baseline and each story's `**Test run**` counts, a shared deferred run counted once), each story's last result, and any failure left with whether it failed at the baseline.
- **Found**: anything surprising about the codebase, the plan or the tests. Nothing here asks the user to act; an action it implies goes under **Needs you**.

When the run leaves a spec finished (every one of its epics `Complete`, or open only for stories waiting on the user), add one line after the headings suggesting `/cpm-next:library sweep`, which looks across repositories for failures a cpm-next rule could have prevented; when `~/.claude/cpm-next/repos.txt` does not list this repository, suggest `/cpm-next:library sweep add {its path}` first. It is a suggestion, not a **Needs you** item.

Then take the **Needs you** items one at a time, the one blocking most work first. For each, say in a few lines what it is and where (`file:line`, or the epic and story), what each way of settling it leads to, and which you recommend and why. Ask with one AskUserQuestion call holding that one question, your recommendation as the first option and `Leave it for now` as the last, and act on the answer before raising the next item:

- a criterion the user changes: amend it with an `**Amended**` line citing their decision, and clear its `Not met` line, and the story's ` — blocked:` note once no other `Not met` line or unresolved finding remains;
- a destructive step they approve: carry it out;
- a step outside the repository: give the exact steps, and ask only when what you do next depends on it being done;
- a `**Pivot deferred**` item: recommend `/cpm-next:plan`, and leave the upstream document to it;
- a promotion candidate: on a yes, write the lesson as an entry in the library's `lessons-learned.md` (an existing file ending in `lessons-learned.md` counts) in the contract's form, unless the library already holds a lesson with that `**Class**` or one describing the rule; create the file with its front-matter when missing, add the entry's scope values to the file's `scope` and set `last-reviewed` to today, leaving an existing file's header alone when it has no front-matter; then mark the candidate, each signal it matched and each signal that joined it ` — promoted {YYYY-MM-DD}`. On a no, mark them ` — declined {YYYY-MM-DD}`. Write no amendment to any other library document: `library learn` does that;
- the `[browser]` criteria that fell back to the user (step 3): ask once for all of them, whether the user will fix the environment (an app answering at the local `APP_URL`, a connected browser, a login session) so that you run them all, or report the results themselves. Once it is fixed, check each through claude-in-chrome as step 3 says, record it `browser-observed` and remove its `- Waiting on user:` line, and for each story whose criteria then all have `Evidence`, take step 4, audit it, take its deferred full run if it needs one, and close it as step 6 says; a check that fails gets a `Not met` line in place of its `- Waiting on user:` line and the contract's blocked note on its story; a reported result is written as the next item describes;
- a `[user]` criterion: ask for the result of its steps. On success, write `Evidence (user, {YYYY-MM-DD}): {what they reported} — red: n/a — user` under it, and once no criterion in the story lacks `Evidence`, take step 4 for the story, audit it, take its deferred full run if it needs one, and close it as step 6 says; on failure, write a `Not met` line and mark the story blocked with the contract's note;
- a blocked story: once the user settles the blocker (a decision, a fix, or an amended criterion), clear its `Not met` lines for what is settled and, when nothing else blocks it, its note, then resume the story through the loop.

An item left for now stays recorded where it is. Once the last item is settled, build the stories the answers unblocked through the loop, and end that run with the three headings again.
