Getting Started with DPM

A practical guide to database-backed planning in Claude Code.
What it is, how it works, and what changes if you know CPM.
23 skills · SQLite-backed · tuned for Claude Opus 5

Overview

What is DPM?

  • A planning plugin for Claude Code — the same slash-command "skills" as CPM
  • Each skill handles a planning stage through guided conversation, unchanged
  • The difference is where answers land: rows with typed columns, not prose in a file
  • Markdown under docs/ is a generated projection — committed so diffs read well, but never read back
  • Skills write through typed MCP tools, so no skill contains SQL and nothing parses prose

The planning pipeline

Requirements + test strategy

Stories, tasks + coverage rows

⚙ Do
Execute, test & verify

Each step feeds the next as rows. Publish is the one stage CPM has no equivalent of — it renders docs/ from the database.

Supporting Skills

The rest of the toolkit

/dpm:publishNEW

Regenerate the markdown and the committed dump from the database — names every removal and asks first

/dpm:party

Multi-persona discussion — the whole roster is in the room, two or three answer each turn

/dpm:consult

Focused consultation with one persona or a small panel — you control who is in the room

/dpm:review

Adversarial review of an epic — findings carry severity and category as typed references

/dpm:audit

Codebase health across the project's dimensions, pinned to the commit it was taken at

/dpm:inspect

What a change set did and where it sits — joined to the planning rows that record intent

/dpm:retro

Retrospective over a finished epic — observations are rows that keep their origin

/dpm:pivot

Amend an artefact, then walk everything hanging off it, gating each change on its own

/dpm:present

Turn planning rows into communications — regenerable, because sources are an edge not a sentence

/dpm:library

Import reference docs and record their scope as rows the Library Check filters on

/dpm:templates

Every document kind this project can hold, where its file lands, and a rendered example

/dpm:archive

Stamp archived_at on settled work — found by reading columns, not by moving files

/dpm:quick

Small change, root-caused and closed against its own criteria — no pipeline ceremony

/dpm:ralph

Autonomous loop across epics, or a spec worked from scratch — readiness read from the graph

/dpm:status

Reconnaissance over the rows and read-only git history. Writes nothing

/dpm:clean

Remove leftover session rows — lists every one, deletes only what you name

/dpm:artifact

The register of published pages and the documents they came from, so a URL can be found again

Decision Guide

When to use what

⚡ Quick fix

Small, well-defined change. Use /dpm:quick for traceability without ceremony, or skip DPM entirely for trivial one-liners.

🎯 Known scope

Feature is clear, just need structure. Jump to /dpm:spec or /dpm:epics.

🤔 Unclear requirements

Not sure what to build or why. Start at /dpm:discover to understand the problem first.

🚀 Major initiative

New product, big feature, cross-cutting change. Use the full pipeline from discover through do.

Artefacts

Where things live

.dpm/ ← the planning data itself
dpm.db ← the database. Never committed — gitignored automatically
dpm.sql ← its committed text form. A fresh clone rebuilds from this
docs/ ← GENERATED. One-way projection — written by publish, never read back
discussions/ ← /dpm:party and /dpm:consult
plans/ ← problem briefs from /dpm:discover
briefs/ ← product briefs from /dpm:brief
specifications/ ← specs from /dpm:spec · ADRs render inside them
epics/ ← epics and coverage matrices from /dpm:epics
reviews/ retros/ quick/ ← /dpm:review, /dpm:retro, /dpm:quick
communications/ audits/ runbooks/ library/

Do not hand-edit anything under docs/. There is no architecture/ directory — an ADR is rendered inside the document that raised it. There is no archive/ either: archiving stamps a column.

Render docs/ and the dump, then commit both together
Tips

Getting the most out of DPM

  • 🎯
    Start anywhere. The pipeline is a suggestion. Jump to whatever skill matches where you are.
  • 📤
    Publish before you commit. Nothing renders docs/ as a side effect of writing. Skip it and the pre-commit guard refuses and names the command — nothing is lost, and nothing is written behind you.
  • ✋
    Never hand-edit a generated file. The guard catches it rather than letting the next publish quietly destroy it. If the content is wrong, change the row.
  • 🔄
    Use pivot, not start over. /dpm:pivot amends the artefact and walks what hangs off it, gating each downstream change on its own.
  • 📚
    Feed the library — and set its scope. A library document without a scope imports cleanly and is read by nothing. That is the most common way a setup ends up half-done.
If You Know CPM

What actually changes

  • The conversation does not. Twenty-two skills are the CPM pipeline one for one — same gates, same roster, same facilitation.
  • One new skill. /dpm:publish, because in CPM the file was the artefact and here it is a rendering of one.
  • Two new habits. Publish before committing, and never hand-edit under docs/.
  • There is no importer, and that is a decision rather than a gap — reading prose is the thing DPM was built to stop doing. Your CPM history stays exactly where it is.
  • One move before you run anything: git mv the twelve generated folders into docs/cpm/, which DPM never walks. See MIGRATION.md — or ask CPM to walk you through it while you still have both installed.
